# System Design

embraOS is built on a 7-layer continuity architecture (descended from the OpenClaw identity model and the Talos service-oriented OS design):

| Layer | What it is | Where it lives |
|---|---|---|
| **Invariant Kernel** | Sealed IDENTITY+SOUL graph — operator-defined values, constraints, purpose as nodes + relations (legacy instances: flat document; see [IDENTITY-GRAPH.md](MULTI-GRAPH/IDENTITY-GRAPH.md)). SHA-256 verified at every boot. | `soul.invariant` in WardSONDB; hash at `/embra/state/soul.sha256` |
| **World-State Model** | Active session, current provider, in-flight tool calls, profile context. | `crates/embra-brain/src/brain/`, sessions in WardSONDB |
| **Continuity Engine** | Health checks, restart policies with exponential backoff, soul verification gate. | `crates/embrad/src/{supervisor,reconcile}.rs` (5-second health checks) |
| **Influence & Propagation** | Tool dispatch, LLM provider routing, Guardian dynamic-tool gateway. | `crates/embra-brain/src/{tools,provider,guardian}/`; 120 tools, 4 providers |
| **Action Layer** | Tool calls that touch the world — filesystem, git, HTTP, SSH, cron. | `crates/embra-brain/src/tools/registry.rs` |
| **Governance & Guardrails** | Soul injection into the system prompt, workspace path restriction, RFC 1918 SSH constraint, Guardian capability broker. | `crates/embra-brain/src/brain/prompts.rs`; tool-layer enforcement |
| **Memory & Knowledge** | Session history + cross-session knowledge graph (entries / semantic / procedural / typed edges) with auto-enrichment on every turn (score ≥ 0.3 and a relevance floor). | `crates/embra-brain/src/knowledge/` |

The runtime services that implement those layers:

| Service | Port | Role |
|---|---|---|
| `wardsondb` | 8090 | Rust JSON document database. Holds soul, memory, knowledge graph, sessions, schedules, and Guardian tool definitions. |
| `embra-trustd` | 50001 | Soul SHA-256 verification + PKI (Root CA 10y, service certs 1y). |
| `embra-apid` | 50000 / 8443 | gRPC + REST gateway, proxies brain RPCs. REST: `GET /health`, `/version`, `/status` — `/status` is the brain's `GetSystemStatus` (2 s timeout, 503 when the brain is away) and carries the LLM provider probe as `llm-provider` / `llm-provider.detail`. gRPC `WatchActivity` streams the brain's activity feed: a snapshot, then a tick every 200 ms while something happens; names and numbers only. `WatchToolCalls` streams one record per tool call — name, session, origin, timing, the input and the result each cut at 64 KiB — the one feed that carries content; `ListToolCalls` reads `tools.turn_trace` back, newest first, 2 KiB previews. |
| `embra-brain` | 50002 | LLM runtime — provider abstraction, 120 tools, session manager, knowledge graph, Learning Mode. |
| `embra-web` | 3345 | HTTPS web console (default UI); wraps embra-console in xterm.js over a PTY→WebSocket bridge. `/ws/activity` fans the brain's activity feed out to every browser for the top bar's activity strip; `/ws/tools` fans the tool-call feed out with a backlog of the last 200 calls, and `/api/tools` pages the record, for the sidebar's Tools tab. Every request carries the console's access token: in the URL once (the boot banner prints it, and the display console's menu shows it again: `GET /api/console-url`, answered to a loopback peer alone), then in a cookie; 401 otherwise. A WebSocket handshake or a write from a page on another origin is refused (403). `GET /api/backups/<name>` streams a backup the OS took as a download, and `PUT` takes one back, piped to `embra-update import` ([OPERATIONS/UPDATES-AND-BACKUPS.md](OPERATIONS/UPDATES-AND-BACKUPS.md)). The app is served at `/embraOS` alone, with the machine's theme on its root element (the name in `/embra/state/theme`, one of `embra_tools_core::theme::THEMES`): `/api/status` names the theme, an open page follows it at its next poll, and `POST /api/theme` stores the choice of the theme picker. |
| `udevd` | — | eudev, for the display console's input (libinput enumerates what udev tagged); started after embra-web, seeded with the input devices (`udevadm trigger --subsystem-match=input`); no hardware database, no module loading; not essential — a boot without it keeps the web console. |
| `embra-kiosk` | — | cog (WPE WebKit, the DRM platform) rendering the web console on the machine's display: `https://127.0.0.1:3345/embraOS?token=…&kiosk=1` from `COG_URL`, Mesa's kms_swrast on the card (no GPU driver, no compositor), keyboard and mouse through libinput; registered when a `/dev/dri/card*` exists and `embra.kiosk=0` is not on the line; not essential. |
| `embra-console` | — | Conversational TUI (serial; PTY-child of embra-web in default mode). The web console is the primary interface; the serial TUI is functional but is preferred for debugging. |
| `embrad` | PID 1 | Init, service supervisor, soul verification gate, 5-second reconciliation loop. |
| `embra-update` | — | The OS's backups, updates and installs: snapshots and restores of STATE and DATA, an uploaded backup checked and taken in, the signed release fetched, verified and written into the inactive slot, the installer of the ISO, and DATA grown to the disk's end ([OPERATIONS/UPDATES-AND-BACKUPS.md](OPERATIONS/UPDATES-AND-BACKUPS.md)). Not a service: run by `embrad` in the maintenance boots, before a trial boot's services and at every normal boot, by the brain for `/backup` and `/update`, for its own check for a newer release and for the `update_check` tool, and by `embra-web` for an uploaded backup. |
| `embra-guardian` | in-process | `syn` validator + `wasmtime` sandbox for dynamic tools — both authoring paths (operator paste, intelligence proposal) gated by a soul-spec replicant check; intelligence proposals additionally operator-approved; three tools (`web_search`, `http_request`, `websocket`) ship with the image and are installed at boot; capability-broker host imports, and the WebSocket connections a tool holds open between calls live in the brain (`guardian/ws.rs`). |

embrad also keeps helper processes that are no services of this table: one `udhcpc` for each card on DHCP and one `wpa_supplicant` for each Wi-Fi card, started and stopped as the cards come and go (the boot chain, below).

### Boot chain and disk layout

The disk image is a GPT aligned to 1 MiB — partition 1 starts at sector 2048 — with five partitions (`buildroot/board/embraos/genimage.cfg.in`; the sizes and the names in `layout.sh`): `esp` (64 MiB vfat, the EFI System Partition: GRUB at `EFI/BOOT/BOOTX64.EFI` or `BOOTAA64.EFI`, `grub.cfg` and `grubenv`), `rootfs_a` and `rootfs_b` (2 GiB each since the firmware joined the image: an OS slot is one SquashFS that carries its own kernel and initramfs under `/boot`, the line GRUB shows for it in `/boot/embraos-slot.cfg` and its release stamp at `/etc/embraos-release`; slot B is empty until the first OS update), `state` (256 MiB ext4, STATE) and `data` (4 GiB ext4, DATA). The disk is a whole number of MiB, 8514: 1 MiB before the first partition, the partitions, and 1 MiB that holds the backup GPT on the last sector — the shape every hypervisor's own tools produce, and a capacity VMware's sparse-extent format can cut into whole 64 KiB grains (`layout.sh` computes the size, `post_image.sh` and `assert_image_layout` read it back from the image). The firmware runs GRUB from the ESP's removable-media path, so no NVRAM entry is needed. `grub.cfg` reads `grubenv` (`slot_active`, `slot_try`, `tries_left`, a status per slot), boots a staged slot with `embra.trial=1` on the kernel line while it has tries left (a 3-2-1-0 ladder, counted down with `save_env`) and marks it failed at zero, and loads the slot's kernel and initramfs from its SquashFS with `embra.slot=a|b` on the line. The menu, three seconds by default, offers each slot, a Diagnostics submenu (the serial TUI, a boot without the display console, debug logging, database request logging, make a slot the default, boot a slot once, clear the failed marks, the boot state, the command-line knobs), Update embraOS, Backup and restore, Reboot, Halt and Firmware setup; `e` opens GRUB's editor on an entry, and a knob added at the end of its first line, after the title, reaches the kernel line (the entry hands its arguments to `boot_slot`). `run-qemu.sh` passes its host-side knobs as one SMBIOS OEM string that `grub.cfg` appends to the line. `embra-init`, the initramfs `/init` (`crates/embra-init`, synchronous, no runtime), mounts `/proc`, `/sys` and `/dev`, finds the slot's partition, STATE and DATA by their GPT names through `embra-boot` (the kernel's uevents, no udev; a line without a slot tries slot A, then the Phase 1 name `rootfs`, then `/dev/vda2`), mounts the rootfs read-only at `/mnt/root`, STATE at `/embra/state` and DATA at `/embra/data`, both `nosuid,nodev,noexec`, and a tmpfs capped at 512 MiB at `/embra/ephemeral` (`noexec`) for the service logs and the Guardian builds' cargo homes. It moves the three pseudo-filesystems into the new root, removes every file of the initramfs but the new root's mount point (the classic switch_root behaviour; the firmware and microcode initrds GRUB loaded beside it would otherwise stay in RAM for the life of the boot, and the freed amount is one of its lines), switches root with a move mount and `chroot` (`pivot_root` fails from an initramfs) and executes `/sbin/embrad`. GRUB loads three initrds for a slot, in this order: `ucode.cpio`, the CPU microcode as an uncompressed newc archive the kernel's early loader reads (Intel's files from the bundle `buildroot/package/embra-intel-microcode` pins by version and sha256, AMD's from linux-firmware; the empty archive on aarch64), `firmware.cpio.gz`, the blobs the built-in drivers that probe before the rootfs is mounted ask for (i915, the E800's DDP package, qed, cxgb4), and `initramfs.cpio.gz`, the repository's; the direct kernel path of `run-qemu.sh` passes the initramfs alone and carries no firmware or microcode. Every linux-firmware family is on the rootfs under `/lib/firmware`, with the licence texts under `/usr/share/licenses/linux-firmware`, and the image build prints the firmware names each built-in driver declares against what is present. A step that fails prints its reason, pauses for the serial line and halts the machine. With `embra.mode=install` (the installer ISO's entries) embra-init instead tries every block device as ISO 9660 until one carries `/embraos/install.manifest` (30 s; `embra.media=` names one), attaches the medium's `rootfs.squashfs` to a loop device and mounts it as the root, makes STATE and DATA tmpfs, moves the medium to `/run/embra/media` and continues the same way; embrad then runs `embra-update install` on both consoles instead of the services (`embra.install=<disk>` makes it unattended). On a disk that already holds an installation the installer offers an upgrade in place beside the clean install (`embra.upgrade=<disk>` unattended): the medium's OS goes into the slot that is not the default, GRUB's loader and `grub.cfg` are replaced with the medium's, the slot is staged in `grubenv` as an OS update stages one, and the partition table, STATE and DATA are not written. For a clean install the installer writes the layout's five partitions to the chosen disk, DATA to the disk's end, with sgdisk, mkfs.fat, mke2fs and `slot::write_image` (the rootfs verified by the manifest's sha256 as streamed and as read back), copies the ESP tree and writes a fresh `grubenv` (slot A active), verifies the result and reboots. At every normal boot embrad runs `embra-update grow-data` before the services (`modes::run_grow_data`): when a gibibyte or more follows DATA, on an installed disk or a VM's disk enlarged since, the partition and its filesystem grow to the disk's end.

The kernel line GRUB builds names two consoles, `console=tty0` and then the serial line (`console=ttyS0` on x86_64, `console=ttyAMA0` on aarch64): the kernel's messages go to both, and `/dev/console` — embrad's stdio, the serial TUI's terminal, the one a plain write reaches — is the serial line, the last `console=` named. embra-init and embrad therefore write every boot message to it and to `/dev/tty0` as well (`embra_boot::console::BootConsole`, which skips the second copy when `/dev/console` is the display itself; in embrad the tracing lines go through `console::BootLog` until the log redirect that follows the operator UI's start, the DIAG lines and the banner through `console::emit` and `console::emit_bytes`, and after the redirect what is meant for the operator is written to both directly: a halt's reason from `halt_system`, the console's URLs after `/web-token rotate`, the line before a power-off; a maintenance boot's job, `embra-update` under `--console`, speaks and listens on both through `BootConsole::prompt_line`, the first line typed on either console answering a prompt), so a display shows GRUB's menu, the boot log, the banner with the console URL and the reason a boot stopped; after the banner the display becomes the display console: embrad starts `udevd` and `embra-kiosk` (cog's DRM platform on WPE WebKit; the web process renders through Mesa's software path into shared-memory buffers and cog copies them to the card's scanout buffer, so no DRM render node and no cursor plane are needed — simpledrm, bochs and Hyper-V's video have neither; six patches carried under `buildroot/patches/` make Mesa and cog behave on such a card, the fourth handing WebKit the pointer's buttons under the numbers it knows, the fifth opening a card libdrm's enumeration leaves out, as Hyper-V's on the VMBus is, the sixth giving xkbcommon one press of a held key, so that a modifier is released with its key), which loads the console page with the access token and `kiosk=1` (the page draws the pointer, focuses the terminal, offers no downloads and no mobile view, and draws its own menu on the right mouse button, the launcher drawing none: Copy and Paste on a clipboard that is the page's own, the paste going to the terminal as one bracketed paste or into the page's text field that was clicked, and This console's URL, the banner's URLs with the token read back from embra-web) and is one more client of `/ws/terminal` under the arbiter; `embra.kiosk=0` leaves the display a boot console; the display console asks for 1920x1080 where the display offers it, the width that holds the page's status row on one line, and `embra.kioskmode=<width>x<height>|native` asks for another mode or the display's own: GRUB's `boot_slot` turns the knob into `video=efifb:` for the kernel's EFI stub, which sets the firmware framebuffer's mode before simpledrm takes it, and embrad names the mode to cog in `COG_PLATFORM_DRM_VIDEO_MODE` when every connected display lists it (`kiosk_video_mode`; cog takes a named mode or none), the device scale following the mode in use (1 below 2560 pixels of width and 2 from there, `device_scale`; `embra.kioskscale=1|2` sets it for a boot); a list that lacks the mode is read a second time after `detect` is written to each connector's `status` (`redetect_displays`), because the kernel's own console shortens a connector's list to its framebuffer's size after every display event (a monitor plugged in, a VM window reporting its size), and never on a kernel line whose `video=` option forces a connector; the mode is set once, at boot; on a machine without a serial port `/dev/console` is a UART that is not there, which the kernel opens all the same and which refuses every write, and the display's copy does not depend on it. The kernel (two fragments: `buildroot/board/embraos/linux.fragment` for both architectures and `linux-x86_64.fragment` for the x86-only symbols, every line of both read back against the built configuration by the image build, which refuses a symbol the merge dropped, so a fragment names the subsystems its drivers need built in; the wireless drivers and the 802.11 stack under them are the kernel's only modules on x86_64, and the image build refuses any other module in that rootfs) drives the firmware's framebuffer (sysfb, simpledrm, fbcon), QEMU's standard VGA (bochs) and virtio-gpu, and for bare metal the BMC video of servers (ASPEED, Matrox); the wired NICs of servers and desktops (Intel's igb, igc, ixgbe, i40e and ice, Broadcom's bnx2, bnx2x and bnxt, Mellanox's mlx4 and mlx5, Aquantia, Atheros's alx, Realtek's 8139cp, QLogic's qed and qede, Chelsio's T4 to T6, beside the e1000, e1000e, r8169, tg3, sky2, 8139too and forcedeth of the base configuration) and the USB adapters of docks and dongles (usbnet with the Realtek 8152, ASIX, CDC Ethernet, NCM, EEM and RNDIS drivers); the RAID and SAS controllers of servers (MegaRAID SAS, mpt3sas, mpi3mr, SmartPQI, HPSA, aacraid, arcmsr), SD and eMMC, the remaining SATA controllers, NVMe behind Intel's VMD, USB 3 sticks as UAS, Thunderbolt and PCIe hotplug; laptop input (multitouch HID, HID over I2C through ACPI with Intel's LPSS I2C controllers and pin controllers, Elantech and Synaptics touchpads, the RMI4 bus); the TPM, the EFI variables, the DMI tables, the CPU temperature sensors, UDF, and the console fonts the kernel picks from by display size; virtio, AHCI, IDE (`ata_piix`, with its entry for VMware's PIIX4), NVMe and virtio-scsi disks; virtio-net, e1000 and e1000e; VMware's pvscsi and vmxnet3 (the devices the x86_64 `embraos.ova` declares, `scripts/lib/embraos.ovf.in`: ESXi 8.0 U2 imports them as written, its firmware boots from the pvscsi disk and the kernel mounts it; QEMU's OVMF has no driver for one, so under QEMU a pvscsi disk boots on the direct kernel path alone; the kernel builds pvscsi for x86 alone, so the aarch64 descriptor, rendered from the same template, declares an NVMe controller in its place and a USB 3 controller for the keyboard and the pointer); VMware's LSI Logic Parallel and SAS controllers (the Fusion MPT drivers `mptspi` and `mptsas`, ESXi's defaults for most guest types); and Hyper-V's synthetic storage, network, video, keyboard and mouse (a generation 2 VM with Secure Boot off). nf_tables is built and unused until the packet filter. The network: embrad brings up every network card the kernel has, whatever its name (`crates/embrad/src/net.rs`; a card is an interface of Ethernet type with a device behind it, `crates/embra-boot/src/net.rs`), and keeps a DHCP client on each: BusyBox `udhcpc` in the foreground, which asks for as long as the card is there and is never stopped for being slow. The lease script `/usr/share/embra/udhcpc.script` applies the address and the card's default route with the card's metric (a wired card before a Wi-Fi card, then the kernel's order) and writes the card's record, `/embra/ephemeral/net/<card>.lease`. embrad writes `/embra/ephemeral/resolv.conf`, the file `/etc/resolv.conf` links to, from the records: the resolvers of one card alone, the best-routed one that has any, since musl asks every listed server at once. The boot waits for a first address on any card, ten seconds at most, and goes on without one. A keeper thread then looks every two seconds, in a maintenance boot too: a card that appears is brought up, a card that goes loses its client and its record, a link that returns is asked again. A second thread keeps the clock while the services run (`clock::keep_checked`): it asks the same servers every hour after an answer, a quarter of an hour after a check that came to nothing or an answer more than a quarter of a second off, and within seconds when a card gets an address, a link returns or the operator stores other time servers. A difference under half a second is slewed (`adjtimex`: the clock runs 0.5 ms a second fast or slow, and no reading goes backwards); a larger one is stepped and the hardware clock written; an answer more than fifteen minutes from a clock that a time server already set this boot is recorded and not applied, and a boot that got no answer takes its first one whole; a server that answers with a kiss-of-death is left alone for a day. Each check rewrites `/run/embra/clock-status`. Nothing stands in for a lease that did not come; QEMU's own DHCP server leases `10.0.2.15`. The operator's settings are a file on STATE, `/embra/state/network/settings` (`crates/embra-boot/src/net_settings.rs`), which the brain writes for `/network` and embrad reads at boot and whenever it changes: a card with an address of its own, stored by its hardware address, gets that address, its route and a record with `source=static`, and no DHCP client; and the machine's name is the operator's, else the one a DHCP server assigned, else `embraos` (`sethostname`, with `/etc/hostname` and `/etc/hosts` as links into the ephemeral tmpfs). Wi-Fi: the drivers of the card families linux-firmware serves (Intel iwlwifi; Realtek rtw88, rtw89, rtl8xxxu and rtlwifi; Qualcomm Atheros ath9k to ath12k; MediaTek mt76 and Ralink rt2800; Broadcom brcmfmac; rtw89's RTL8852AU over USB through the eighteen upstream commits of `buildroot/patches/linux`, which are newer than the pinned kernel) are kernel modules, the only ones this image loads: every Wi-Fi driver asks for its firmware when it probes, which a built-in driver does before the root filesystem is there. embrad matches the devices on the PCI, USB and SDIO buses against `/usr/share/embra/wireless.alias` (the lines of `modules.alias` whose module is a wireless driver, written by `post_build.sh`) and runs `modprobe` for what a device asks for, at boot and when an adapter is plugged in later (`crates/embrad/src/wifi.rs`); `embra.wifi=0` on the kernel line loads none. Nothing in embrad waits for a radio. A driver's load runs its card's probe and a card's start runs the driver's own, each seconds on a USB adapter: `modprobe` is started and looked at again at a later look, the card is brought up by its supplicant in the supplicant's own process, and a supplicant is started once the wired cards have had their turn (a card with a link until its address, five seconds at most; one without a link three), because a driver's start holds the kernel's network lock and no address is set on any card meanwhile. For the same reason embrad reads a card's link from `operstate` and `flags` and never from `carrier`, which waits for that lock, and the web console and the trust service read the machine's addresses on their blocking pool. A USB adapter that shows itself as a driver disk is switched first (`usb_modeswitch`, when its data names the device). The firmware is `/lib/firmware`, completed at build time from the linux-firmware tree for what Buildroot's package leaves out (`board/embraos/wireless.sh`; the build fails on a driver none of whose firmware names is served). On every Wi-Fi card embrad keeps `wpa_supplicant` (nl80211; WPA2 and WPA3 personal, and open networks) with a configuration rendered from the networks the operator stored (`/embra/state/network/wifi`, mode 0600, written by `/network wifi join`; `crates/embra-boot/src/wifi.rs`) into `/embra/ephemeral/net/secret/`, which the tools' read jail refuses; the supplicant reads it again when the stored networks change. A card that has joined a network is then a card like any other: a DHCP client, a record, a default route behind every wired card's. The brain asks the supplicant's control socket what is in range and what the card is on (`/network wifi`): what the card is on and what the scan before found first, then a scan, whose end it waits for twelve seconds at most. The access points are read from the supplicant's table a page at a time (`BSS RANGE=<id>-`, each page from the id after the last one read): one answer of the supplicant holds 4096 bytes, some forty access points, and its one-answer list (`SCAN_RESULTS`) is cut there without a word. A radio that was idle is started again for a scan inside the supplicant's call into the kernel, and the supplicant answers nothing meanwhile, so an answer that comes before the scan's end shows the scan before and says so; after a question that went unanswered nothing more is asked on that socket, since the protocol numbers no answer and a late one would be read as the next question's; `system_status`'s `network` block carries the name of the network a card is on, asked of the same socket with one `STATUS` and a wait of a second, and nothing else of Wi-Fi. When a network is stored, a Wi-Fi card or its driver is there and no wired card has a link, the boot waits up to twenty-five seconds for the first address. The boot banner prints the console URL through QEMU's port forward and one more for every address the machine holds on a network; the web console's certificate names the machine as its network sees it: `localhost`, the machine's name when the CA admits it (`embraos` and the operator's own under a CA that limits its names; any plain name under a CA from before v0.23.0, which has no limits), the two loopback addresses and every private address a card holds (`embra_boot::names::leaf_names`); a public address, an IPv6 link-local address and a name with a domain are not on it. embra-web asks embra-trustd without naming anything and trustd fills the names in; embra-web asks again when the machine's name or addresses change, after the clock was set and thirty days before the certificate ends, and serves the new certificate to the next connection (`crates/embra-web/src/tls.rs`). The CA that signs it is the machine's own, which no browser knows: `GET /api/ca.crt` hands its certificate out, behind the token, for a browser to import once (`crates/embra-web/src/ca.rs`); `/network` lists the names and the route.

`embrad` (PID 1) first checks the clock against the image's build time: a hardware clock that reads earlier has certainly lost its time (a board whose clock battery ran down), and the clock resumes from the last time the machine saved, or from the build time (`apply_floor` in `crates/embrad/src/clock.rs`; the save is the clock itself, written to `/embra/state/last-known-time` once a minute while the services run and once more when the machine is stopped, and read only when the hardware clock is earlier than the build time). It then drops every inherited environment variable but `PATH`, `HOME` and `TERM` — the kernel hands init every undotted `KEY=value` of the boot line — reads the kernel line once (the `embra.*` knobs, the last occurrence of each: `embra.web` and `embra.tui` for the UI, `embra.cols` and `embra.rows`, `embra.loglevel`, `embra.dbverbose`, `embra.graphics`, `embra.kiosk`, `embra.kioskmode`, `embra.kioskscale` and `embra.kbd` for the display console, `embra.slot`, `embra.trial`, `embra.mode`, `embra.install`, `embra.media`, `embra.upgrade` and `embra.downgrade` for the installer, `embra.ntp` for the time server, `embra.wifi` for the wireless drivers), asks a time server for the time now that the network is up (`sync_at_boot_from`: SNTP to the server `embra.ntp=<host>[:<port>]` names for this boot, else to the ones the operator stored with `/network time`, else to two of the time servers the DHCP leases name and then to `time.cloudflare.com`; none with `embra.ntp=off` or `/network time off`; one request per address of a name, three addresses at most, and five seconds at most for the whole list; the clock set from the first answer, and the hardware clock with it when that was a second or more off; an answer earlier than the build time refused; the outcome in `/run/embra/clock-status`, which the banner and the brain read), and runs a maintenance mode (`embra.mode=update|backup|restore`, the menu's entries, or `install`, the ISO's) instead of the services when one is named. Otherwise it starts the services in one order (`register_services` in `crates/embrad/src/supervisor.rs`): `wardsondb` on 8090, `embra-trustd` on 50001, then the soul gate — trustd verifies the seal; a first boot (no soul document and no stored hash) continues into Learning Mode, a verified seal continues, and anything else halts with the reason in `/embra/state/halt_reason` — then `embra-apid` on 50000 and 8443, `embra-brain` on 50002, and `embra-web` on 3345, or `embra-console` on the serial line when the serial TUI is selected (`embra.tui=1` on the kernel line; `EMBRA_TUI=1` in `run-qemu.sh`). Once every service is healthy, a trial boot is confirmed: embrad mounts the ESP for one write under a lock (`embra_boot::esp::with_env_mut`), makes the booted slot `slot_active`, clears the trial and unmounts; every boot publishes `/run/embra/boot-status` (the slot, the trial, the mode, the confirmation, the release and `grubenv`'s fields) for the brain's `system_status` and for embra-update. `/reboot now` sends SIGTERM to PID 1 and `/reboot halt` SIGUSR2: embrad stops the services in reverse order, ends every process that is left, unmounts the workspace, DATA and STATE, and restarts the machine through the menu or powers it off. Any exit of a supervised service is restarted under the budget described under Supervision below. embrad also reaps the orphans a tool's child leaves behind (a git or ssh that outlived its parent), answers a shutdown signal during a restart's backoff, stops a service with SIGTERM first and SIGKILL five seconds later, and remounts its bind of the workspace at `/embra/workspace` `nosuid,nodev,noexec` like the partition it lives on.

The Cargo workspace has fourteen members — `embra-init`, `embra-boot` (the boot contract: the kernel line, partitions by GPT name, `grubenv`, the release stamp, the boot console (the serial line and the display both), the boot's record of the clock, the network's cards, lease records and settings, the names a certificate carries, the stored Wi-Fi networks, the web console's access token; `libc` is its one dependency), `embra-update` (the OS's backups and updates: snapshots and restores of STATE and DATA, the signed release into the inactive slot), `embrad`, `embra-trustd`, `embra-apid`, `embra-brain`, `embra-guardian`, `embra-console`, `embra-web`, `embra-common`, `embra-tool-macro`, `embra-tools-core` and the vendored `wardsondb` — and one excluded crate, `embra-web-ui`, the Leptos frontend built for `wasm32` with Trunk and embedded into `embra-web`.

### Trust boundaries

What the model's tools reach, as the code enforces it:

- **Writes** land under `/embra/workspace/` only. Every writer checks the real path (`crates/embra-brain/src/tools/jail.rs`): a symlink inside the workspace that leads outside it is refused before anything is created, and a path is removed by its name, never through a link. The Guardian's `save_to` sink runs the same check.
- **Reads** reach everything on the system by real path except the places that hold the operator's secrets: `/proc`, the STATE partition except its drop-in directories and four plain files, the database files under `/embra/data/wardsondb`, the backups under `/embra/data/backups` (each carries a copy of STATE), the workspace SSH key, and the Wi-Fi supplicant's configuration under `/embra/ephemeral/net/secret` (it holds the stored passphrases). `get` returns the configuration document with its credential fields redacted.
- **Nothing is written under a `.git` component, under the workspace `.ssh` directory, under the workspace `.config/git` directory or under the Guardian build tree `.guardian`**, by name or through a link (`jail.rs::fence_owned_dirs`): a planted hook would run with the next git tool, an ssh client configuration there would be read by every ssh the OS runs, git's included, `$HOME` is the workspace, so git would read attributes and ignore files there, and the build tree holds the projects the Guardian compiles and the artifacts boot reconcile loads.
- **A Guardian tool runs only what its own build produced.** The build runs cargo from the pinned in-OS toolchain with the environment cleared, in a `CARGO_HOME` of the build's own on the ephemeral tmpfs — created empty, removed after, and cargo's working directory, so cargo's configuration discovery meets no directory a tool can write — offline, with zero dependencies and no build script (`build = false`), so nothing runs at compile time but the compiler (`crates/embra-guardian/src/build.rs`). The hash of the artifact a build loaded is recorded with the tool, and boot reconcile loads an artifact only when the file on DATA hashes to it (`crates/embra-brain/src/guardian/mod.rs::artifact_check`).
- **A Guardian tool reaches the network through the broker's guards alone.** A request is `https://` and a connection `wss://`, never with userinfo; a public address passes, a private one when the operator listed its host (`/guardian egress allow`), a loopback, link-local, multicast or reserved one never (`crates/embra-guardian/src/caps.rs::check_destination`). A WebSocket connection is dialed at the addresses that check classified and at no other, and it is the brain's, held for the tool that opened it (`crates/embra-brain/src/guardian/ws.rs`): a tool reaches its own alone, four at once and eight over all tools, each closed after ten minutes without a call and after sixty minutes at the latest, when its host is denied or its secret removed, when its tool is deleted or built again, and by the operator (`/guardian connections`). The journal has one line at an open and one at a close, never a frame.
- **The web console's resources are bounded, and it is never framed.** The PTY bridge's input and resize queues hold 256 and 16 frames and a fast browser waits at its socket; a WebSocket message or frame is at most 1 MiB; each TLS handshake runs in its own task under a 10 s timeout, so a client that connects and says nothing holds one task and not the accept loop; every page and asset carries `Content-Security-Policy: frame-ancestors 'none'` and `X-Frame-Options: DENY` (`crates/embra-web/src/pty_bridge.rs`, `ws.rs`, `server.rs`, `assets.rs`).
- **Every git the brain runs is hardened** (`crates/embra-brain/src/tools/engineering/git.rs::git_command`): no system configuration, the global file under STATE, the hooks path pinned to an empty directory through the environment, no terminal prompt, the network transports alone (`GIT_ALLOW_PROTOCOL=https:http:ssh:git`), the pinned ssh command, and the tokens in the configuration environment, never on the command line. A git tool runs in a directory under the workspace by its real path, so a workspace link to a repository outside it is refused before git runs, and a git that talks to a remote ends after 120 seconds.
- **A stored credential never leaves through a tool's input or output.** The dispatcher refuses the input of an outbound tool that carries one, by value in any of its forms (as stored, percent-encoded, base64), naming the kind and never the value, and replaces every stored value by its kind in a tool's text and in a handler's error (`SecretSet::redact`); the Guardian broker refuses a request that carries one before the save pre-flight, the DNS lookup and the transport. The brain's HTTP clients follow a redirect to the same origin only, so a provider key or a git token never travels to a third host. The one other host is the operator's choice: while `/local-ai-gateway` is on, every provider request goes to WSDS Local AI Gateway's unified listener, which forwards the key to the provider the path prefix names and to nothing else; a URL is stored only once the listener has identified itself with the gateway's `x-local-ai-gateway` header ([OPERATIONS/LOCAL-AI-GATEWAY.md](OPERATIONS/LOCAL-AI-GATEWAY.md)). The brain's HTTP clients and the TLS of a Guardian WebSocket connection trust the operator's CA drop-ins in `/embra/state/ca-certificates/` and the certificate authorities the image was built with (`/usr/share/embra/ca-certificates/`, the builder's `Imported_CAs/` baked in at build time) beside the compiled-in roots, read at the first client a boot builds and again after `/ca import` and `/ca remove`, so the gateway over HTTPS with its own certificate authority, a self-hosted GitLab and a Guardian tool's private host verify; `web_search`'s client keeps the compiled-in roots alone, and the database client, loopback and plain HTTP, trusts nothing. A certificate authority is added by the operator alone: `/ca import` is a slash command that takes the certificate by its SHA-256, no tool runs a slash command, and no tool writes STATE.
- **The web console answers the pages it serves.** A WebSocket handshake, or a write (`POST`, `PUT`), that carries a browser's `Origin` must name the console it reached — `https://` and the request's own host — because the `SameSite=Strict` cookie compares sites, not origins, and a page on another port of the same host would get it attached. Another port, another scheme, another host and `null` are refused with 403; a request without `Origin` passes on the token alone (`crates/embra-web/src/access.rs::admit`).
- **A document id reaches the database as itself or not at all.** The client refuses an id or a collection name the URL parser would rewrite (`..`, `/`, `\`, `?`, `#`, `%`), so no id reaches another document.
- **PID 1 never exits.** A fatal boot error or a panic in embrad halts with the reason in `/embra/state/halt_reason`; a sealed hash with no soul document halts rather than re-learning. PID 1 reaps every orphan a tool's child leaves, answers a shutdown signal during a restart's backoff, and stops a service with SIGTERM before SIGKILL. A signal says how the machine is stopped once the services are: SIGTERM (`/reboot now`) or SIGINT restarts it, SIGUSR2 (`/reboot halt`) powers it off. Before either, embrad ends every process that is left and unmounts the workspace, DATA and STATE (a filesystem something still holds is remounted read-only), so that neither journal is replayed at the next boot. STATE, DATA, the workspace bind and the ephemeral tmpfs are mounted `noexec` (with `nosuid,nodev`), so nothing written at run time executes as a program. `security_check` prints the five mounts with their options against these flags, and the seal's state.
- **What stays open.** The provider sees the conversation; a secret the operator pastes into it and never stores is not in the set the guard matches.

**Persistence:** [WardSONDB](https://github.com/ward-software-defined-systems/wardsondb) — a Rust JSON document database. It is the single durable store for runtime state: soul, memory entries, the knowledge graph, sessions, schedules, and Guardian dynamic-tool definitions.

**Supervision:** `embrad` (PID 1) runs a 5-second reconciliation loop (`crates/embrad/src/reconcile.rs`) over every service in `crates/embrad/src/supervisor.rs`. Any exit — a clean status 0 included — is logged and restarted: a supervised service is meant to outlive the boot. Restarts back off exponentially, `1 s · 2^n` capped at 30 s (`RestartPolicy::default()`: `backoff_base` 1 s, `backoff_max` 30 s). `max_restarts` (10) is a burst limit, not a per-boot total: a restarted service that runs continuously for `stable_after` (60 s — pinned above `backoff_max`, so a crash loop pacing itself at the cap can never reset its own budget) gets its `restart_count` back to 0. Ten restarts inside that window exhaust the budget, and the exit after them leaves the service `Halted` for the rest of the boot. The soul gate is separate: `Supervisor::verify_soul` calls `halt_system` on a hash mismatch; a first boot with no soul continues into Learning Mode. PID 1 never exits: a fatal boot error, a soul verification failure or a panic in embrad halts the machine with the reason written to `/embra/state/halt_reason` (`crates/embrad/src/main.rs`: the panic hook and `run()`); a signal handler that cannot be installed is logged and never awaited, and a service log file that cannot be opened sends that stream nowhere rather than failing the spawn.

**AI Model:** A pluggable LLM provider abstraction routes the Brain through one of four backends, selected at first boot and switchable at runtime via `/provider <kind>`:

- **Anthropic Claude** — Opus 5 (default), Opus 5.5, Opus 4.8, Fable 5.1, or Fable 5, selectable at the first-boot wizard, in `/provider --setup anthropic` (the model step after the key) and via `/model`; the `EMBRA_ANTHROPIC_MODEL` env var is a development override, which embrad does not pass to the brain in the image (Opus 4.7 is retired from selection — an instance persisted on that alias keeps resolving to its real API id via legacy canonicalization in the model resolver, but `/model` no longer offers it). Requests sent with `output_config.effort` (default `max`, runtime-tunable via `/effort`) and `thinking.display=summarized` (`=omitted` when `/show-reasoning off`) — the request shape is identical across supported models: thinking is always `adaptive` and never disabled, the effort is always sent explicitly (Opus 5.5's API default of `medium` therefore never applies), and `tool_choice` is only ever `auto` (Opus 5.5 and Fable 5.1 reject a forced tool choice). Summarized thinking deltas stream live to the expression panel; on Opus 5.5 and the Fable models the notes the model writes between tool calls arrive as thinking blocks too, so they appear in that panel and are not part of the persisted transcript; signed thinking blocks still round-trip via `Block::ProviderOpaque` for the model's own continuity. Native ephemeral prompt caching with three breakpoints: the system prompt, the last tool of the manifest and the second-to-last message of the conversation (see Prompt Caching below). Transient API errors (408/409/429/5xx — including 529 overloaded) are retried with exponential backoff (1 s → 60 s ladder, `Retry-After` honored) before surfacing as an error; established streams are never retried mid-flight. Note: Fable 5 and Fable 5.1 require 30-day API data retention (a zero-data-retention org gets a 400 on every request). Requests go to `api.anthropic.com`, or to the provider gateway's `/anthropic` prefix while `/local-ai-gateway` is on ([OPERATIONS/LOCAL-AI-GATEWAY.md](OPERATIONS/LOCAL-AI-GATEWAY.md)).
- **Google Gemini** — Gemini 3.1 Pro (`gemini-3.1-pro-preview`, default) or Gemini 4 Argon (`gemini-4-argon`), selectable at the first-boot wizard, in `/provider --setup gemini` (the model step after the key) and via `/model`; the `EMBRA_GEMINI_MODEL` env var is a development override, which embrad does not pass to the brain in the image; `SystemConfig.gemini_model` holds the alias (`gemini-3.1-pro`, `gemini-4-argon`), which the model resolver maps to the API id. Requests sent with `thinkingLevel=high` by default (operator-tunable via `/effort`: `low`/`medium`/`high`, the ladder of both models; `xhigh`/`max` clamp to `high`; Argon requires the field and its own default would be `medium`), `includeThoughts=true` (`false` when `/show-reasoning off`), and `maxOutputTokens=64000`, under the 65,536 a synchronous request of either model may produce (Argon's long decode, past 64K, is not used); 429/5xx retried with the same exponential-backoff ladder as the Anthropic backend. Thought-flagged parts stream live to the expression panel; thoughtSignatures stay on `Block::ProviderOpaque`. Gemini 3.1 Pro uses a native explicit context cache via a `GeminiCacheManager` singleton with `(session, fingerprint, TTL)` validation; Gemini 4 Argon has none and relies on Google's implicit caching (below). Every model call logs one `gemini::usage` line: the model, whether the explicit cache was used, and the prompt, cached, thinking, output and total token counts. Requests, the explicit cache's `cachedContents` and the image endpoint go to `generativelanguage.googleapis.com`, or to the provider gateway's `/gemini` prefix while `/local-ai-gateway` is on.
- **Ollama** (Sprint 5) — local or remote-style OpenAI-compat backend. `/v1/chat/completions` POST to the configured endpoint (default `http://localhost:11434`). Supports gpt-oss family (with `reasoning_effort: "high"`), DeepSeek-R1/R2, and standard non-reasoning models. Bearer authentication optional. While `/local-ai-gateway` is on, requests go to the provider gateway's `/ollama` prefix and the gateway's own upstream answers; the stored endpoint is used again when it is off.
- **LM Studio** (Sprint 5) — local OpenAI-compat backend, default `http://localhost:1234`. Same wire shape as Ollama. Runs on Apple Silicon through the `llmster` daemon with an MLX backend. Measured against Ollama with the same BF16 weights on the Mac Studio ([NEMOTRON-VS-QWEN3.8-BENCHMARK.md](LOCAL-MODELS/NEMOTRON-VS-QWEN3.8-BENCHMARK.md)): Ollama generates 1.7–2× faster, LM Studio reads prompts 2–7% faster. While `/local-ai-gateway` is on, requests go to the provider gateway's `/lmstudio` prefix, as for Ollama.

The loop driver consumes a neutral intermediate representation (`Block::{Text, Image, ToolCall, ToolResult, ProviderOpaque}` and `TurnOutcome::{EndTurn, ToolUse, MaxTokens, Pause, EarlyStop}`); each provider owns its own wire types, streaming parser, and tool schema translator. All 120 tools work identically across all four backends. Sessions are pinned to the provider that recorded them — cross-provider session attach is hard-blocked. The brain probes the active provider's endpoint ~30 s after boot (the model check the config load never did), every 5 minutes, and right after a `/provider` switch, a setup flow or a `/local-ai-gateway` change — reachability, model presence, key state, latency, and the host reached (the gateway's while one is on) — and publishes the result to `/status`, the `system_status` tool and the `GetSystemStatus` RPC, which apid's REST `/status` proxies for the web console's `provider` pill (and, from the configuration, its `local-ai-gateway` pill: lit while a stored gateway is on, dimmed and reading `off` while it is off); state changes reach the operator as notifications. Ollama and LM Studio share a single `OpenAICompatProvider` with a `ProviderKind` discriminator, and either preset reaches **any** OpenAI-compatible server — vLLM, Together, Fireworks, OpenRouter, a remote Ollama — by pointing its endpoint there via `/provider --setup <ollama|lm_studio>`: enter the base URL without `/v1` (`http://vllm-host:8000`, `https://api.together.xyz`, `https://api.fireworks.ai/inference`, `https://openrouter.ai/api`) and the API key at the Bearer step; https endpoints keep their implicit 443 (only bare hosts and `http://` get the preset's default port). The status bar keeps showing the preset's label. No further named presets are planned. Terminal `refusal` and `max_tokens` outcomes surface operator-facing error/warning frames (refusal detail parsed from the API's `stop_details`; history persists an explicit marker instead of a silent `(no response)`) — and a refusal is never silently re-served by another model: the Anthropic API's opt-in `fallbacks` parameter is deliberately unused, because embraOS binds a single model to a sealed identity. The operator can also interrupt a turn (`/stop` / Esc / the mobile ■ button — built for local-model reasoning loops that the tool-iteration cap never catches): the signal travels as an out-of-band unary `StopTurn` RPC because the Converse loop processes requests sequentially, and it works at every point of a turn: before an answer has begun the request itself is dropped, and inside an answer every provider's stream parser ends when nobody listens — closing the HTTP connection is what actually stops a local server's generation. A stopped turn keeps its partial text, marked `(response interrupted by operator stop)`. A model call that fails is a terminal outcome of its own on every provider (`CallFailed`; a stream that ends without its closing event counts): the turn is saved with what it had and a marker, the failed call is kept in memory for `/continue`, and the next turn carries an `<interrupted_turn>` block that names the tool calls on record. A turn is on record from its start: its message and its text so far sit on the session's meta document (`open_turns`) until the turn is saved, the brain has the kernel write DATA out at each of those writes (`syncfs`), and a record left by a restart or a power cut is written into its session at the next boot. The Ollama and LM Studio presets wait through a server's silence for the model wait (`/model-wait`, 120 minutes unless set), which the brain counts from the request and again from every piece of the answer.

**Reasoning controls per family:**
- **Operator override (`/effort`)** — while an Ollama or LM Studio preset is active, `/effort <low|medium|high|xhigh|max>` stores a level for the active model (`openai_compat.ollama_effort_by_model` / `lm_studio_effort_by_model`; each model keeps its own, so a switch never carries one to another model) that is sent **verbatim** as `reasoning_effort` in place of the auto-map below; the accepted set belongs to the model and the server validates (`/effort` warns when the level is outside the model's documented set). Unset = the auto-map, byte-identical to before the knob existed.

- **The Ollama Cloud models** — DeepSeek-V4-Pro (any name containing `deepseek-v4-pro`, incl. `:cloud`), DeepSeek V4.1 Flash, GLM 5.3 and Kimi K3: embraOS sends `reasoning_effort: "max"` automatically, the top of each model's levels on ollama.com (`low`/`high`/`max`). **Bearer storage (OpenAI-compat):** STATE files at `/embra/state/bearer_<preset>` with mode `0600` (security retroactively applied to Anthropic/Gemini api_key files in Sprint 5). Per-call resolution from `EMBRA_OLLAMA_BEARER` / `EMBRA_LM_STUDIO_BEARER` env vars so post-swap turns pick up the new value without a brain restart.

**Prompt Caching:** embraOS uses each provider's native caching mechanism to minimize token costs.

*Anthropic — ephemeral prompt caching* (three cache breakpoints, each a `cache_control: {"type": "ephemeral"}`):

1. **System prompt** — the soul, identity, operator profile and instructions, rendered from the sealed document (`crates/embra-brain/src/provider/anthropic/mod.rs`). It carries no tool inventory and does not change between turns, so it is cached on the first call and hit on every later one within the session.
2. **Tool manifest** — the registry's schemas, sorted by name, with the breakpoint on the last entry (`tool_schema.rs::build_tools_snapshot`); the same bytes on every turn.
3. **Conversation history** — a rolling breakpoint on the second-to-last message caches all prior turns. Only the newest message is uncached.

Cache TTL is 5 minutes (ephemeral), refreshed on every hit. Active conversations keep the cache warm indefinitely — longer sessions get progressively cheaper per message.

*Gemini — explicit context caching on Gemini 3 and 2.5, implicit on Gemini 4* (one cache handle per session):

Google documents explicit caching for Gemini 3 and 2.5 models, and "Explicit caching is not supported for Gemini 4 Argon (`gemini-4-argon`) and onward". The provider attaches a cache manager only to a `gemini-3.*`, `gemini-3-*` or `gemini-2.5-*` id (`explicit_cache_supported`); any other model, Argon included, sends `systemInstruction` and `tools` with every request, where Google's implicit caching serves a repeated prefix (from 4,096 tokens), and never calls `cachedContents`.

A `GeminiCacheManager` singleton stores one cached-content handle in WardSONDB at `provider.gemini_cache:current`. On each turn, the stored handle is validated by `(session, fingerprint, TTL)` and either reused (`cache:hit`), deleted-and-recreated (`cache:miss` — `session_changed` / `stale` / `expired`), or freshly created (`cache:create`). The fingerprint is `sha256(system_prompt || \x00 || tools_json || \x00 || model_id)` truncated to 16 hex chars, so any soul/tool drift, and any switch of model, produces a clean miss: a cached content belongs to the model it was made for and is never sent with a request to another. If `cachedContents.create` returns 4xx, the call falls back to per-request `systemInstruction` + `tools` and the system continues to function. Server-side GC of a cache mid-session is detected at request time (`403/404 CachedContent not found`) and recovered with a single inline retry. The `gemini::usage` line's `cached_tokens` shows what a cache served, explicit or implicit.

*Ollama / LM Studio — server-side keep-warm* (no client-side cache):

OpenAI-compat backends don't expose a caching mechanism on the wire. Ollama keeps the model warm via `OLLAMA_KEEP_ALIVE` (operator-configured server-side, transparent to embraOS); LM Studio handles resident model state internally. embraOS sends the full system + history on every request — the cost optimization happens server-side via the loaded model staying in GPU/Metal memory between turns. No mid-turn cache invalidation race because there's no cache handle to invalidate.
