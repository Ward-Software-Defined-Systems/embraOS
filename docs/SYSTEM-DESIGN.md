# System Design

embraOS is built on a 7-layer continuity architecture (descended from the OpenClaw identity model and the Talos service-oriented OS design):

| Layer | What it is | Where it lives |
|---|---|---|
| **Invariant Kernel** | Sealed IDENTITY+SOUL graph — operator-defined values, constraints, purpose as nodes + relations (legacy instances: flat document; see [IDENTITY-GRAPH.md](MULTI-GRAPH/IDENTITY-GRAPH.md)). SHA-256 verified at every boot. | `soul.invariant` in WardSONDB; hash at `/embra/state/soul.sha256` |
| **World-State Model** | Active session, current provider, in-flight tool calls, profile context. | `crates/embra-brain/src/brain/`, sessions in WardSONDB |
| **Continuity Engine** | Health checks, restart policies with exponential backoff, soul verification gate. | `crates/embrad/src/{supervisor,reconcile}.rs` (5-second health checks) |
| **Influence & Propagation** | Tool dispatch, LLM provider routing, Guardian dynamic-tool gateway. | `crates/embra-brain/src/{tools,provider,guardian}/`; 118 tools, 4 providers |
| **Action Layer** | Tool calls that touch the world — filesystem, git, HTTP, SSH, cron. | `crates/embra-brain/src/tools/registry.rs` |
| **Governance & Guardrails** | Soul injection into the system prompt, workspace path restriction, RFC 1918 SSH constraint, Guardian capability broker. | `crates/embra-brain/src/brain/prompts.rs`; tool-layer enforcement |
| **Memory & Knowledge** | Session history + cross-session knowledge graph (entries / semantic / procedural / typed edges) with auto-enrichment on every turn (score ≥ 0.3 and a relevance floor). | `crates/embra-brain/src/knowledge/` |

The runtime services that implement those layers:

| Service | Port | Role |
|---|---|---|
| `wardsondb` | 8090 | Rust JSON document database. Holds soul, memory, knowledge graph, sessions, schedules, and Guardian tool definitions. |
| `embra-trustd` | 50001 | Soul SHA-256 verification + PKI (Root CA 10y, service certs 1y). |
| `embra-apid` | 50000 / 8443 | gRPC + REST gateway, proxies brain RPCs. REST: `GET /health`, `/version`, `/status` — `/status` is the brain's `GetSystemStatus` (2 s timeout, 503 when the brain is away) and carries the LLM provider probe as `llm-provider` / `llm-provider.detail`. gRPC `WatchActivity` streams the brain's activity feed: a snapshot, then a tick every 200 ms while something happens; names and numbers only. `WatchToolCalls` streams one record per tool call — name, session, origin, timing, the input and the result each cut at 64 KiB — the one feed that carries content; `ListToolCalls` reads `tools.turn_trace` back, newest first, 2 KiB previews. |
| `embra-brain` | 50002 | LLM runtime — provider abstraction, 118 tools, session manager, knowledge graph, Learning Mode. |
| `embra-web` | 3345 | HTTPS web console (default UI); wraps embra-console in xterm.js over a PTY→WebSocket bridge. `/ws/activity` fans the brain's activity feed out to every browser for the top bar's activity strip; `/ws/tools` fans the tool-call feed out with a backlog of the last 200 calls, and `/api/tools` pages the record, for the sidebar's Tools tab. Every request carries this boot's access token: in the URL once (the boot banner prints it), then in a cookie; 401 otherwise. A WebSocket handshake or a write from a page on another origin is refused (403). The app is served at `/embraOS` alone. |
| `embra-console` | — | Conversational TUI (serial; PTY-child of embra-web in default mode). The web console is the primary interface; the serial TUI is functional but is preferred for debugging. |
| `embrad` | PID 1 | Init, service supervisor, soul verification gate, 5-second reconciliation loop. |
| `embra-guardian` | in-process | `syn` validator + `wasmtime` sandbox for dynamic tools — both authoring paths (operator paste, intelligence proposal) gated by a soul-spec replicant check; intelligence proposals additionally operator-approved; two tools (`web_search`, `http_request`) ship with the image and are installed at boot; capability-broker host imports. |

### Boot chain and disk layout

The disk image is a GPT with four partitions (`buildroot/board/embraos/genimage.cfg.in`): `boot` (64 MiB vfat, the kernel), `rootfs` (the SquashFS, mounted read-only), `STATE` (256 MiB ext4) and `DATA` (2 GiB ext4). `embra-init`, the initramfs `/init` (`crates/embra-init`, synchronous, no runtime), mounts `/proc`, `/sys` and `/dev`, then the rootfs from `/dev/vda2` at `/mnt/root`, STATE from `/dev/vda3` at `/embra/state`, DATA from `/dev/vda4` at `/embra/data`, and a tmpfs capped at 512 MiB at `/embra/ephemeral` for the service logs. It moves the three pseudo-filesystems into the new root, switches root with a move mount and `chroot` (`pivot_root` fails from an initramfs) and executes `/sbin/embrad`.

`embrad` (PID 1) starts the services in one order (`register_services` in `crates/embrad/src/supervisor.rs`): `wardsondb` on 8090, `embra-trustd` on 50001, then the soul gate — trustd verifies the seal; a first boot (no soul document and no stored hash) continues into Learning Mode, a verified seal continues, and anything else halts with the reason in `/embra/state/halt_reason` — then `embra-apid` on 50000 and 8443, `embra-brain` on 50002, and `embra-web` on 3345, or `embra-console` on the serial line when the serial TUI is selected (`EMBRA_TUI=1` in `run-qemu.sh`). Any exit of a supervised service is restarted under the budget described under Supervision below.

The Cargo workspace has twelve members — `embra-init`, `embrad`, `embra-trustd`, `embra-apid`, `embra-brain`, `embra-guardian`, `embra-console`, `embra-web`, `embra-common`, `embra-tool-macro`, `embra-tools-core` and the vendored `wardsondb` — and one excluded crate, `embra-web-ui`, the Leptos frontend built for `wasm32` with Trunk and embedded into `embra-web`.

### Network exposure

What each port answers to, as the code binds it and as `scripts/run-qemu.sh` forwards it. Every port is a literal in embrad's `register_services` (`crates/embrad/src/supervisor.rs`), and every service binds the literal `0.0.0.0`; neither is configurable.

| Port | Service | Protocol | TLS | Authentication | Binds in the guest | From the host (QEMU) | From the host's network |
|---|---|---|---|---|---|---|---|
| 8090 | `wardsondb` | HTTP REST | no | none (embrad passes no `--api-key`) | every interface | no | no |
| 50001 | `embra-trustd` | gRPC, plaintext h2c | no | none (`GenerateCertificate` answers any caller) | every interface | no | no |
| 50000 | `embra-apid` | gRPC, plaintext h2c | no | none | every interface | loopback only (`hostfwd=tcp:127.0.0.1:50000`) | no |
| 8443 | `embra-apid` | HTTP REST | no | none | every interface | loopback only (`hostfwd=tcp:127.0.0.1:8443`) | no |
| 50002 | `embra-brain` | gRPC, plaintext h2c | no | none | every interface | no | no |
| 3345 | `embra-web` (web mode only) | HTTPS + WebSocket | yes: a certificate from the embraOS CA, minted by `embra-trustd` at every start | a per-boot access token: embrad mints it and prints it in the boot URL, the first visit sets a cookie, 401 without either; a WebSocket handshake or a write whose `Origin` is not the console's own is refused with 403; among the holders the arbiter (one writer, read-only observers, explicit take-over) governs who types | every interface | every host interface (`hostfwd=tcp::3345`) | yes, with the token |

The image has no firewall; QEMU's user-mode network is the only isolation. A port QEMU does not forward is reachable from inside the guest only: the brain's own `port_scan` and `ssh_*` tools included, Guardian tools excluded (`crates/embra-guardian/src/caps.rs` refuses a loopback address always, and a private one unless the operator listed its host with `/guardian egress allow`). Outside QEMU's user-mode network, on a bridged VM or on hardware, all six ports are reachable on the guest's address. Transport security between the services is Phase 5 work ([ROADMAP.md](ROADMAP.md)).

### Trust boundaries

What the model's tools reach, as the code enforces it:

- **Writes** land under `/embra/workspace/` only. Every writer checks the real path (`crates/embra-brain/src/tools/jail.rs`): a symlink inside the workspace that leads outside it is refused before anything is created, and a path is removed by its name, never through a link. The Guardian's `save_to` sink runs the same check.
- **Reads** reach everything on the system by real path except the places that hold the operator's secrets: `/proc`, the STATE partition except its drop-in directories and four plain files, the database files under `/embra/data/wardsondb`, and the workspace SSH key. `get` returns the configuration document with its credential fields redacted.
- **Nothing is written under a `.git` component or under the workspace `.ssh` directory**, by name or through a link (`jail.rs::fence_owned_dirs`): a planted hook would run with the next git tool, and an ssh client configuration there would be read by every ssh the OS runs, git's included.
- **Every git the brain runs is hardened** (`crates/embra-brain/src/tools/engineering/git.rs::git_command`): no system configuration, the global file under STATE, the hooks path pinned to an empty directory through the environment, no terminal prompt, the network transports alone (`GIT_ALLOW_PROTOCOL=https:http:ssh:git`), the pinned ssh command, and the tokens in the configuration environment, never on the command line.
- **A stored credential never leaves through a tool's input or output.** The dispatcher refuses the input of an outbound tool that carries one, by value in any of its forms (as stored, percent-encoded, base64), naming the kind and never the value, and replaces every stored value by its kind in a tool's text and in a handler's error (`SecretSet::redact`); the Guardian broker refuses a request that carries one before the save pre-flight, the DNS lookup and the transport. The brain's HTTP clients follow a redirect to the same origin only, so a provider key or a git token never travels to a third host.
- **The web console answers the pages it serves.** A WebSocket handshake, or a write (`POST`, `PUT`), that carries a browser's `Origin` must name the console it reached — `https://` and the request's own host — because the `SameSite=Strict` cookie compares sites, not origins, and a page on another port of the same host would get it attached. Another port, another scheme, another host and `null` are refused with 403; a request without `Origin` passes on the token alone (`crates/embra-web/src/access.rs::admit`).
- **A document id reaches the database as itself or not at all.** The client refuses an id or a collection name the URL parser would rewrite (`..`, `/`, `\`, `?`, `#`, `%`), so no id reaches another document.
- **PID 1 never exits.** A fatal boot error or a panic in embrad halts with the reason in `/embra/state/halt_reason`; a sealed hash with no soul document halts rather than re-learning.
- **What stays open.** The provider sees the conversation; a secret the operator pastes into it and never stores is not in the set the guard matches.

**Persistence:** [WardSONDB](https://github.com/ward-software-defined-systems/wardsondb) — a Rust JSON document database. It is the single durable store for runtime state: soul, memory entries, the knowledge graph, sessions, schedules, and Guardian dynamic-tool definitions.

**Supervision:** `embrad` (PID 1) runs a 5-second reconciliation loop (`crates/embrad/src/reconcile.rs`) over every service in `crates/embrad/src/supervisor.rs`. Any exit — a clean status 0 included — is logged and restarted: a supervised service is meant to outlive the boot. Restarts back off exponentially, `1 s · 2^n` capped at 30 s (`RestartPolicy::default()`: `backoff_base` 1 s, `backoff_max` 30 s). `max_restarts` (10) is a burst limit, not a per-boot total: a restarted service that runs continuously for `stable_after` (60 s — pinned above `backoff_max`, so a crash loop pacing itself at the cap can never reset its own budget) gets its `restart_count` back to 0. Ten exits inside that window exhaust the budget and the service goes `Halted` for the rest of the boot. The soul gate is separate: `Supervisor::verify_soul` calls `halt_system` on a hash mismatch; a first boot with no soul continues into Learning Mode. PID 1 never exits: a fatal boot error, a soul verification failure or a panic in embrad halts the machine with the reason written to `/embra/state/halt_reason` (`crates/embrad/src/main.rs`: the panic hook and `run()`); a signal handler that cannot be installed is logged and never awaited, and a service log file that cannot be opened sends that stream nowhere rather than failing the spawn.

**AI Model:** A pluggable LLM provider abstraction routes the Brain through one of four backends, selected at first boot and switchable at runtime via `/provider <kind>`:

- **Anthropic Claude** — Opus 5 (default), Opus 5.5, Opus 4.8, Fable 5.1, or Fable 5, selectable at the first-boot wizard, in `/provider --setup anthropic` (the model step after the key), via `/model`, or the `EMBRA_ANTHROPIC_MODEL` env var (Opus 5 adopted as default on its 2026-07-24 release day; Opus 4.7 retired from selection — an instance persisted on that alias keeps resolving to its real API id via legacy canonicalization in the model resolver, but `/model` no longer offers it). Requests sent with `output_config.effort` (default `max`, runtime-tunable via `/effort`) and `thinking.display=summarized` (`=omitted` when `/show-reasoning off`) — the request shape is identical across supported models: thinking is always `adaptive` and never disabled, the effort is always sent explicitly (Opus 5.5's API default of `medium` therefore never applies), and `tool_choice` is only ever `auto` (Opus 5.5 and Fable 5.1 reject a forced tool choice). Summarized thinking deltas stream live to the expression panel; on Opus 5.5 and the Fable models the notes the model writes between tool calls arrive as thinking blocks too, so they appear in that panel and are not part of the persisted transcript; signed thinking blocks still round-trip via `Block::ProviderOpaque` for the model's own continuity. Native ephemeral prompt caching with three breakpoints: the system prompt, the last tool of the manifest and the second-to-last message of the conversation (see Prompt Caching below). Transient API errors (408/409/429/5xx — including 529 overloaded) are retried with exponential backoff (1 s → 60 s ladder, `Retry-After` honored) before surfacing as an error; established streams are never retried mid-flight. Note: Fable 5 and Fable 5.1 require 30-day API data retention (a zero-data-retention org gets a 400 on every request).
- **Google Gemini** — Gemini 3.1 Pro (`gemini-3.1-pro-preview`, default) or Gemini 4 Argon (`gemini-4-argon`), selectable at the first-boot wizard, in `/provider --setup gemini` (the model step after the key), via `/model`, or the `EMBRA_GEMINI_MODEL` env var; `SystemConfig.gemini_model` holds the alias (`gemini-3.1-pro`, `gemini-4-argon`), which the model resolver maps to the API id. Gemini 4 Argon passed live in QEMU on 2026-10-14. Requests sent with `thinkingLevel=high` by default (operator-tunable via `/effort`: `low`/`medium`/`high`, the ladder of both models; `xhigh`/`max` clamp to `high`; Argon requires the field and its own default would be `medium`), `includeThoughts=true` (`false` when `/show-reasoning off`), and `maxOutputTokens=64000`, under the 65,536 a synchronous request of either model may produce (Argon's long decode, past 64K, is not used); 429/5xx retried with the same exponential-backoff ladder as the Anthropic backend. Thought-flagged parts stream live to the expression panel; thoughtSignatures stay on `Block::ProviderOpaque`. Gemini 3.1 Pro uses a native explicit context cache via a `GeminiCacheManager` singleton with `(session, fingerprint, TTL)` validation; Gemini 4 Argon has none and relies on Google's implicit caching (below). Every model call logs one `gemini::usage` line: the model, whether the explicit cache was used, and the prompt, cached, thinking, output and total token counts.
- **Ollama** (Sprint 5) — local or remote-style OpenAI-compat backend. `/v1/chat/completions` POST to the configured endpoint (default `http://localhost:11434`). Supports gpt-oss family (with `reasoning_effort: "high"`), DeepSeek-R1/R2, and standard non-reasoning models. Bearer authentication optional.
- **LM Studio** (Sprint 5) — local OpenAI-compat backend, default `http://localhost:1234`. Same wire shape as Ollama. Runs on Apple Silicon through the `llmster` daemon with an MLX backend. Measured against Ollama with the same BF16 weights on the Mac Studio ([NEMOTRON-VS-QWEN3.8-BENCHMARK.md](LOCAL-MODELS/NEMOTRON-VS-QWEN3.8-BENCHMARK.md)): Ollama generates 1.7–2× faster, LM Studio reads prompts 2–7% faster.

The loop driver consumes a neutral intermediate representation (`Block::{Text, ToolCall, ToolResult, ProviderOpaque}` and `TurnOutcome::{EndTurn, ToolUse, MaxTokens, Pause, EarlyStop}`); each provider owns its own wire types, streaming parser, and tool schema translator. All 118 tools work identically across all four backends. Sessions are pinned to the provider that recorded them — cross-provider session attach is hard-blocked. The brain probes the active provider's endpoint ~30 s after boot (the model check the config load never did), every 5 minutes, and right after a `/provider` switch or setup flow — reachability, model presence, key state, latency — and publishes the result to `/status`, the `system_status` tool and the `GetSystemStatus` RPC, which apid's REST `/status` proxies for the web console's `provider` pill; state changes reach the operator as notifications. Ollama and LM Studio share a single `OpenAICompatProvider` with a `ProviderKind` discriminator, and either preset reaches **any** OpenAI-compatible server — vLLM, Together, Fireworks, OpenRouter, a remote Ollama — by pointing its endpoint there via `/provider --setup <ollama|lm_studio>`: enter the base URL without `/v1` (`http://vllm-host:8000`, `https://api.together.xyz`, `https://api.fireworks.ai/inference`, `https://openrouter.ai/api`) and the API key at the Bearer step; https endpoints keep their implicit 443 (only bare hosts and `http://` get the preset's default port). The status bar keeps showing the preset's label. No further named presets are planned. Terminal `refusal` and `max_tokens` outcomes surface operator-facing error/warning frames (refusal detail parsed from the API's `stop_details`; history persists an explicit marker instead of a silent `(no response)`) — and a refusal is never silently re-served by another model: the Anthropic API's opt-in `fallbacks` parameter is deliberately unused, because embraOS binds a single model to a sealed identity. The operator can also interrupt a turn (`/stop` / Esc / the mobile ■ button — built for local-model reasoning loops that the tool-iteration cap never catches): the signal travels as an out-of-band unary `StopTurn` RPC because the Converse loop processes requests sequentially, and it works because every provider's streaming pump exits when its receiver is dropped — severing the HTTP connection is what actually stops a local server's generation. A stopped turn keeps its partial text, marked `(response interrupted by operator stop)`.

**Reasoning controls per family:**
- **Operator override (`/effort`)** — while an Ollama or LM Studio preset is active, `/effort <low|medium|high|xhigh|max>` stores a level for the active model (`openai_compat.ollama_effort_by_model` / `lm_studio_effort_by_model`; each model keeps its own, so a switch never carries one to another model) that is sent **verbatim** as `reasoning_effort` in place of the auto-map below; the accepted set belongs to the model and the server validates (`/effort` warns when the level is outside the model's documented set). Unset = the auto-map, byte-identical to before the knob existed.
- **gpt-oss / OpenAI o-series / DeepSeek-R1·R2 / `-thinking` variants** — embraOS sends OpenAI-compat `reasoning_effort: "high"` automatically (route table `reasoning_effort_for_model`).
- **The Ollama Cloud models** — DeepSeek-V4-Pro (any name containing `deepseek-v4-pro`, incl. `:cloud`), DeepSeek V4.1 Flash, GLM 5.3 and Kimi K3: embraOS sends `reasoning_effort: "max"` automatically, the top of each model's levels on ollama.com (`low`/`high`/`max`, read 2026-10-22). For V4-Pro that engages the Max-thinking mode (per [DeepSeek's docs](https://api-docs.deepseek.com/guides/thinking_mode)), operator-confirmed in production (2026-07-10); V4.1 Flash is vetted and the preferred cloud pick since 2026-10-23 (it takes image input); GLM 5.3 and Kimi K3 are under evaluation. Route table `reasoning_effort_for_model` in `crates/embra-brain/src/provider/openai_compat/mod.rs`. A `:cloud` tag is served by ollama.com, not locally.
- **Qwen3 family** (Qwen3, Qwen3.6, including `*-A3B` MoE) — thinking is integrated into the same model and toggled via `/think` and `/no_think` directives in user/system messages. `reasoning_effort` is omitted by default to avoid `No valid custom reasoning fields found` server warnings. **Qwen3.8** is the exception: it accepts `reasoning_effort` `low`/`medium`/`xhigh` (default `xhigh`, per its model card), and embraOS sends `xhigh` automatically on both servers; Ollama's own default for it would be `medium` (`server/model_thinking.go` in Ollama's source). `/effort` sets another level. See `RECOMMENDED-LOCAL-MODELS.md` for the vetted roster and server configuration.
- **Standard non-reasoning models** — no reasoning controls; embraOS omits all reasoning parameters.

**Bearer storage (OpenAI-compat):** STATE files at `/embra/state/bearer_<preset>` with mode `0600` (security retroactively applied to Anthropic/Gemini api_key files in Sprint 5). Per-call resolution from `EMBRA_OLLAMA_BEARER` / `EMBRA_LM_STUDIO_BEARER` env vars so post-swap turns pick up the new value without a brain restart.

**Prompt Caching:** embraOS uses each provider's native caching mechanism to minimize token costs.

*Anthropic — ephemeral prompt caching* (three cache breakpoints, each a `cache_control: {"type": "ephemeral"}`):

1. **System prompt** — the soul, identity, operator profile and instructions, rendered from the sealed document (`crates/embra-brain/src/provider/anthropic/mod.rs`). It carries no tool inventory and does not change between turns, so it is cached on the first call and hit on every later one within the session.
2. **Tool manifest** — the registry's schemas, sorted by name, with the breakpoint on the last entry (`tool_schema.rs::build_tools_snapshot`); the same bytes on every turn.
3. **Conversation history** — a rolling breakpoint on the second-to-last message caches all prior turns. Only the newest message is uncached.

Cache TTL is 5 minutes (ephemeral), refreshed on every hit. Active conversations keep the cache warm indefinitely — longer sessions get progressively cheaper per message.

*Gemini — explicit context caching on Gemini 3 and 2.5, implicit on Gemini 4* (one cache handle per session):

Google documents explicit caching for Gemini 3 and 2.5 models, and "Explicit caching is not supported for Gemini 4 Argon (`gemini-4-argon`) and onward". The provider attaches a cache manager only to a `gemini-3.*`, `gemini-3-*` or `gemini-2.5-*` id (`explicit_cache_supported`); any other model, Argon included, sends `systemInstruction` and `tools` with every request, where Google's implicit caching serves a repeated prefix (from 4,096 tokens), and never calls `cachedContents`.

A `GeminiCacheManager` singleton stores one cached-content handle in WardSONDB at `provider.gemini_cache:current`. On each turn, the stored handle is validated by `(session, fingerprint, TTL)` and either reused (`cache:hit`), deleted-and-recreated (`cache:miss` — `session_changed` / `stale` / `expired`), or freshly created (`cache:create`). The fingerprint is `sha256(system_prompt || \x00 || tools_json || \x00 || model_id)` truncated to 16 hex chars, so any soul/tool drift, and any switch of model, produces a clean miss: a cached content belongs to the model it was made for and is never sent with a request to another. If `cachedContents.create` returns 4xx, the call falls back to per-request `systemInstruction` + `tools` and the system continues to function. Server-side GC of a cache mid-session is detected at request time (`403/404 CachedContent not found`) and recovered with a single inline retry. The `gemini::usage` line's `cached_tokens` shows what a cache served, explicit or implicit.

*Ollama / LM Studio — server-side keep-warm* (no client-side cache):

OpenAI-compat backends don't expose a caching mechanism on the wire. Ollama keeps the model warm via `OLLAMA_KEEP_ALIVE` (operator-configured server-side, transparent to embraOS); LM Studio handles resident model state internally. embraOS sends the full system + history on every request — the cost optimization happens server-side via the loaded model staying in GPU/Metal memory between turns. No mid-turn cache invalidation race because there's no cache handle to invalidate.
