# Operation

Day-to-day use of embraOS once it is running.

**The web console is the primary interface.** Uploads (📎, paste, drop) and downloads, the sidebar with its Tools tab, the activity strip and the mobile chat are in the web console only. The serial TUI (`EMBRA_TUI=1`) is functional but is preferred for debugging.

## The Session Model

Every interaction with embraOS happens in a persistent session. Sessions survive disconnections. When you reconnect, the full conversation history is restored, and if the session has been idle for 30 minutes or more the intelligence opens with a briefing on where things left off (quick reconnects — a phone unlocking, a browser tab waking — resume silently; `/switch`ing to a session always briefs). The briefing also covers what happened in embraOS while you were away from that session: memory entries created, sessions created or deleted, cron jobs that ran (with each job's latest result) and reminders that fired since the session was last active. The brain reads these from its own records and hands them to the briefing turn; they are not written into the session's history. Every other turn carries the same kind of block for what happened since the session's last turn — the reminders that fired and the cron results recorded, in every mode, so the intelligence sees them at your next message whether or not a briefing ran; the model-facing text carries it, the history does not. A reminder (`countdown … act=true`) or a cron job (`cron_add … act=true`) can also ask for a turn of the intelligence's own when it fires: the console that holds the notification channel runs it in the active session, the turn is saved as `[Reminder fired] …` or `[embraCRON acted] …`, and at most twelve such turns run an hour; a trigger that cannot run (no session, a turn in flight, a setup waiting for your answer) is shown with its reason under the notice.

You can run multiple named sessions for different contexts:

```
/new research         # Create a research-focused session
/new monitoring       # Create a monitoring session
/switch main          # Switch back to the main session
/sessions             # List all sessions and the provider each is pinned to
```

All sessions share the same intelligence — same memory, same identity, same soul. But each has its own conversation history and context.

**Stopping a stuck turn**: if the intelligence gets caught in a reasoning loop (far more common on local models than frontier ones), press **Esc** in the console while the turn is streaming, type `/stop`, or tap the **■** button that replaces Send on mobile. Generation stops immediately — the connection to the model server is severed — and the partial response stays in history marked as interrupted. Stops are fail-safe: they only ever affect the turn that was running when you pressed them, and they work during Learning Mode too.

**Deleting a session** is a conversation, not a keystroke: `/sessions delete <name>` has the intelligence summarize the session and ask why you're removing it. Your reply is the reason and the approval: durable learnings are preserved to the knowledge graph (`remember`) as memories of that session, and only then does the system soft-delete it. The system then records the deletion and your reason as a memory, linked to what was preserved; the session's summary goes with the session. Deletion is soft for 7 days — the session disappears from listings and can't be attached, but `/sessions restore <name>` brings it back intact until the database's TTL reaper removes the data for good. Any slash command during the flow cancels it; a declining reply aborts it; the `learning` session (the sealed identity record) can never be deleted.

## Keyboard Shortcuts

**embraOS TUI** — in-conversation:

| Key | Action |
|---|---|
| `Enter` | Send message (or newline in `/ml` multi-line mode; a multi-line paste is sent whole, with what was typed before and after it) |
| `Up/Down` | Scroll history (`PageUp/PageDown` = 10 rows) |
| `Shift+Up/Down` | Scroll the expression/reasoning panel (`Shift+PageUp/PageDown` = 5 rows; snaps back to the tail on your next message, on errors, or when new expression content arrives) |
| `Esc` | Stop the current turn (only while it is thinking/streaming — idle Esc is a no-op) |

*There is no exit or detach chord. The console is a supervised child on both transports — embra-web respawns it after 1 s (`crates/embra-web/src/pty_bridge.rs`), embrad supervises it on serial (`crates/embrad/src/supervisor.rs`) — so there is nothing to detach from: leave the web console by closing the tab, the serial console with QEMU's `Ctrl+A X` below. `Ctrl+<letter>` chords are deliberate no-ops. Enter sends whatever modifier is held (`Shift+Enter` and `Alt+Enter` send too — the console's Enter arm ignores modifiers, `crates/embra-console/src/terminal/mod.rs`); `/ml` and a multi-line clipboard paste are the multi-line paths, on both transports; `Backspace` on an empty input drops a staged paste.*

*When the console cannot do its work it says why and exits — code 2 when it cannot reach `embra-apid`, code 1 when its conversation or its screen fails, code 3 when the gateway ended the conversation stream (apid or the brain restarted, or the connection was reset), code 4 when that stream failed — and its supervisor starts it again. In the web console the reason and the wait are shown in the terminal pane (`[embra-web] embra-console exited (code 3: the gateway ended the conversation stream) — restarting in 1 s…`) and logged by embra-web, which also logs each browser's attach, takeover and detach with the bytes it typed, and each chat message received by its kind and size, never its text; a console that keeps exiting early is started again more slowly, 1 s doubling to 30 s, for as long as it takes. On the serial console the console's own log is `/embra/ephemeral/embra-console.log` (`system_logs` with `service: embra-console`): its lines from the start to the exit, the exit cause among them, each with its time and level; the serial terminal shows the same lines without the time, and the restarted console's screen covers them there.*

*In the web console's `/ml` editor modal: Enter = newline, Ctrl/⌘+Enter or Send = submit, Esc/Cancel = discard.*

*Web console layout (the URL embraOS prints at boot — `https://localhost:3345/embraOS?token=…`, this boot's access token in it; the console lives at `/embraOS` and nothing on `:3345` answers without the token; desktop): the top bar carries the brand and version, the **activity strip** (three stations on one link row: the model, embra-brain and the knowledge graph; text streams from the model to the brain as particles, database traffic moves between the brain and the graph, each tool call rises from the brain as a chip with its name and duration, and a readout under each station gives the model with its token rate, what the brain is doing, and the node count with the request rate; hover a station for its numbers; the strip reads the brain's activity feed over `/ws/activity`, names and numbers only, never content, and reads *activity feed offline* while the brain is away; **/provider --setup** is in the sidebar's Model group and the ⌘ palette), the role badge — **● Writer**, or **○ Read-only · operator N** with a **Take control** button (one writer at a time; other tabs observe), **⌘ Commands** (a filterable palette), **📎 Attach** (upload an image or a text file; dropping or pasting one on the terminal does the same — a text file lands in `/embra/workspace/uploads/` and rides your next message) and **↗ mobile** (the chat view, automatic at ≤ 768 px; there a tool call is one line — name, the result's first line, `▸` — tap to expand, and a session picked in the sessions sheet replaces the timeline with that session's bubbles). The left sidebar has two tabs, remembered per browser. **Commands** is the command list — a filter box above eight collapsible groups, the same groups as [COMMAND-REFERENCE.md](COMMAND-REFERENCE.md): groups start collapsed, click a title to expand it (remembered per browser), type in the filter to narrow every group to its matches (Esc clears). **Tools** is every tool call the intelligence made, newest first — time, name, status, the call number on a live call (it counts from one at each boot, so a call read back from the record shows none), and under it the duration and the session or the cron job — with a filter, a *feed offline* line while the brain is away, and the running call at the top (the count on the tab is this boot's calls; the rows read back from the record are history and are not counted); the list is fed by `/ws/tools` (the brain's tool-call feed through apid; embra-web keeps the last 200 calls, so a reload has them), fills from the record (`/api/tools`, `tools.turn_trace`, 2 KiB previews marked `rec`) after a restart, and **Load older** pages further back. Click a row and the call opens in a sheet beside the sidebar, over the left part of the terminal, which keeps its size: the input pretty-printed and highlighted, the result, and a note when the brain cut a side (64 KiB each), each section scrolling on its own so a long input never hides the result; Esc closes it. In the terminal each call is one dim marker line, `⚙ #17  14:02:11  file_read  0.8s` (`!` and `ERR` on an error) — click the marker to open the call in the sheet; `/show-tools full|marker|off` changes the rendering (console-local). A `/switch` replaces the transcript with the session's history, rows marked `history`. Above the terminal, a full-width status strip shows one pill per service plus the CPU / memory / DATA / STATE / load meters, refreshed from a 5-second `GET /api/status` poll; a `provider` pill joins them once the brain has probed the active LLM endpoint (~30 s after boot) and reads down while the endpoint is unreachable; a `local-ai-gateway` pill appears while a provider gateway is stored (`/local-ai-gateway`), green while every provider request goes through it and grey while it is off. Buttons inject commands; the console is authoritative.*

**QEMU** — host-level (`run-qemu.sh` uses `-serial mon:stdio`, so `Ctrl+A` is the escape prefix):

| Key | Action |
|---|---|
| `Ctrl+A X` | Exit QEMU (powers off the VM) |
| `Ctrl+A C` | Switch between serial console and QEMU monitor |
| `Ctrl+A H` | Show all QEMU escape sequences |

## Current Limitations

- **API or remote LLM** — Anthropic Claude / Google Gemini require internet + a paid API key. The Ollama and LM Studio presets connect to an OpenAI-compatible server: a local one you operate (typically a Mac Studio or similar) or any hosted one — vLLM, Together, Fireworks, OpenRouter — via `/provider --setup <ollama|lm_studio>` (base URL without `/v1`, key at the Bearer step; https endpoints keep their implicit 443). Inference still happens on a separate host — on-device inference inside embraOS itself belongs to Phase 5's sovereign-intelligence options ([ROADMAP.md](../ROADMAP.md)).
- **Verified under QEMU, ESXi, Hyper-V, VMware Fusion and Parallels Desktop** — x86_64 on Ubuntu is the reference build; the [aarch64 / Apple Silicon](../BUILD/AARCH64-BUILD.md) and [Intel Mac](../BUILD/INTEL-MAC-BUILD.md) guides each carry their own verification banner (both re-verified end-to-end 2026-07-19 under the named-volume Docker Buildroot flow; the toolchain bump to 1.98.1, the embedding-model step and the hardened Buildroot hooks since then passed on the Apple Silicon build of 2026-10-25 and on the Intel Mac build of 2026-11-07; the Phase 2 UEFI boot is validated on x86_64, on Apple Silicon — 2026-11-06 — and on the Intel Mac — 2026-11-07 — each Mac with the display window and a bridged network). The disk boots itself through UEFI and GRUB and carries the drivers ESXi and Hyper-V present ([SYSTEM-DESIGN.md](../SYSTEM-DESIGN.md)); `embraos.ova` boots on ESXi 8.0 U2 as imported — hardware version 20, the pvscsi disk and the VMXNET3 adapter its descriptor declares, no serial port, the display as the console (2026-11-08) — and `embraos.vhdx` boots on Hyper-V as a generation 2 VM with Secure Boot off, nested in an Azure VM, takes a DHCP lease on an internal NAT switch and serves the console (2026-11-08), and `embraos.vmx` with its VMDK converts into a Parallels Desktop 26.5 machine on an Intel Mac and boots to the web console (2026-11-11); the VM templates and bare metal are Phase 2 scope (the image factory) and Kubernetes Phase 5 ([ROADMAP.md](../ROADMAP.md))
- **Tested on limited platforms** — built and verified on Ubuntu 24.04 + 26.04 under QEMU 8.2.2 (OVMF; the disk on virtio, AHCI, IDE, NVMe, virtio-scsi and pvscsi, the NIC virtio-net, e1000e and vmxnet3); the bootable image also runs under QEMU on Intel and Apple Silicon Macs, from `embraos.ova` and installed from `embraos.iso` on ESXi 8.0 U2, from `embraos.vhdx` and installed from `embraos.iso` on Hyper-V generation 2, installed from the aarch64 `embraos.iso` under VMware Fusion on Apple Silicon, and imported from `embraos.vmx` and installed from `embraos.iso` on Parallels Desktop 26.5 on an Intel Mac
- **The display console and the installer are validated under QEMU, on ESXi, on Hyper-V and on Parallels Desktop, the installer under VMware Fusion as well** — the web console on the machine's display (keyboard, the page-drawn pointer, the wheel, a drag that selects text, the shared session with a remote browser) is validated on QEMU's standard VGA and virtio-gpu displays under OVMF; the click and the 1920x1080 mode are validated under QEMU, on ESXi 8.0 U2 and on Hyper-V generation 2, and the page and the keyboard on the two hypervisors with them (2026-11-09). On aarch64 the display console is validated under QEMU on Apple Silicon on a virtio-gpu display (2026-11-10: the page, the keyboard, the pointer, a click and the 1920x1080 mode), and in QEMU's window on an Intel Mac with the same five (2026-11-10, virtio-gpu; the mode on an image from `1ba8df5` on). On Apple Silicon it is validated on the firmware's framebuffer as well (QEMU's `ramfb`, 2026-11-10: the page, the keyboard, the pointer and a click, at 800x600, the mode that firmware driver starts in). The click and Hyper-V's display rest on the third and fourth patches carried on cog (`buildroot/patches/cog/`, 2026-11-09; [OPEN-PROBLEMS.md](../OPEN-PROBLEMS.md)): an image built before them presses no tab or button from the display and shows no display console on Hyper-V. On Parallels Desktop 26.5 (Intel Mac, 2026-11-11) the display console comes up at 1920x1080 on the machine imported from `embraos.vmx`, which Parallels gives its virtio display adapter, and letters sent as key events from the host arrive in the console; the pointer and a click on Parallels are **TBD** until run. On bare metal the display console is validated on one machine, a YouYeeToo X1 single-board computer installed from the ISO (2026-11-11): the console on the board's HDMI display, with a wireless USB keyboard, and the pointer and a click there as well (recorded 2026-11-12). The display console's mode is set at boot, 1920x1080 where the display offers it (`embra.kioskmode=` for another, [QUICK-START.md](../BUILD/QUICK-START.md)), and does not follow a VM window resized later. The installer ISO (`embraos.iso`) is UEFI only, needs Secure Boot off, writes one disk and no NVRAM boot entry (the firmware boots the ESP's removable-media path), and is validated under OVMF as a DVD onto a virtio disk and as a USB stick onto an AHCI disk (each installed disk boots on its own), on ESXi 8.0 U2 (2026-11-09; the installed disk boots behind VMware's LSI Logic SAS and LSI Logic Parallel controllers as well) and on Hyper-V generation 2 (2026-11-09; the installed disk boots to the display console), a second install over an installed disk included; with the stick attached as UAS the installer's run is validated under QEMU from the medium's kernel on (2026-11-10; OVMF reads no UAS device, so that kernel was started through its EFI stub); the aarch64 medium is validated on Apple Silicon under QEMU and under VMware Fusion (2026-11-11); on Parallels Desktop 26.5 on an Intel Mac the medium installs on a machine set to UEFI with Secure Boot off (2026-11-11; [QUICK-START.md](../BUILD/QUICK-START.md)); on bare metal the medium boots from a USB stick and installs on a YouYeeToo X1 single-board computer, onto the board's eMMC (`mmcblk1`), the prompts answered at the board's HDMI display with a wireless USB keyboard, and the installed machine boots on its own (2026-11-11); 4096-byte-sector disks are **TBD**. The display console's web process holds about 700 MB of memory on the console page (measured under QEMU); a machine with 2 GiB or less boots with `embra.kiosk=0`. The bare-metal drivers, the firmware and the microcode are in the image and the kernel boots with them under QEMU; on real hardware the image has booted one machine, that YouYeeToo X1 (2026-11-11: the installed disk on eMMC, the display on HDMI, a USB keyboard, a DHCP lease, a host on the network reached by name, the web console reached from a browser on another machine), and every other machine is **TBD**
- **An installed disk is upgraded in place from the installer medium** — on a disk that holds an installation the installer offers it beside the clean install: the medium's OS into the slot that is not the default, GRUB's loader and `grub.cfg` replaced, the slot staged as an OS update stages one; the partition table, STATE and DATA not written ([UPDATES-AND-BACKUPS.md](UPDATES-AND-BACKUPS.md)). Validated with the new installer run in a scratch VM on the image's kernel, the built ISO as its medium and copies of the built image as its disks (2026-11-13): another build of the same version upgraded at the prompt and unattended, into slot B and, with slot B the default, into slot A; the upgraded disk booting through its own GRUB under OVMF, the staged slot tried, the snapshot taken and the slot confirmed; a staged slot that cannot pass its trial given up after three tries and the slot before it booted; every refusal and every declined question leaving each partition byte for byte as it was; the clean install chosen at the question, on a blank disk and unattended, its disk booting. From a built medium the upgrade in place passed on bare metal (the YouYeeToo X1, 2026-11-13), where the installer had first refused it from a medium of the other storage engine. Under QEMU the installer started from a built medium (the medium's menu, both consoles) is **TBD**.
- **The kernel's log is read through the intelligence** — the installed machine boots `quiet`, has no shell and shows the kernel's lines on no console; `system_logs` with `service: kernel` reads the kernel's ring buffer (the drivers and their firmware, USB and disk events, the microcode revision, each warning and error marked with its level). Validated on the image's kernel as the first process of a scratch VM (2026-11-12: the log read whole, 477 lines, a warning marked; on an emulated CPU that announces no hypervisor, the `microcode: Current revision` line found by its filter); through a session on bare metal it is validated on the YouYeeToo X1 (2026-11-12): the intelligence read the kernel's microcode lines by their filter, `microcode: Current revision: 0x24000026` and `microcode: Updated early from: 0x2400001e`.
- **The clock is set at boot and not kept** — embrad resumes a clock that reads earlier than the image's build time from the last time the machine saved (the clock, written to STATE once a minute), or from the build time, then asks a time server once per boot (`time.cloudflare.com`, or `embra.ntp=<host>`; [QUICK-START.md](../BUILD/QUICK-START.md), The clock). Nothing corrects the clock while the OS runs, the answer (plain SNTP) is not authenticated, and an installed machine has no stored setting for the time server: a kernel-line knob is typed in GRUB's editor at each boot. A boot without an answer keeps the hardware clock's time, and says so on the banner when that was earlier than the build. Validated under QEMU on a VM whose hardware clock read 2018 (2026-11-11), and on bare metal on the YouYeeToo X1, whose clock battery is dead: installed from the ISO and booted with the firmware's date left as it was, the installer's boot and the installed OS set the clock themselves (2026-11-12). The saved time is validated under QEMU across power cuts (2026-11-12); a boot of that board without a network is **TBD** ([OPEN-PROBLEMS.md](../OPEN-PROBLEMS.md))
- **No MCP server modules** — the tool surface is the 119 built-in tools plus Guardian dynamic tools: two shipped with the image and installed at boot (`web_search`, inert until `/guardian key brave`, and `http_request`, a guarded curl that needs no key), the rest operator-authored (`/guardian-define`) or intelligence-proposed (`guardian_propose`), both replicant-checked against the sealed soul, proposals operator-approved before they compile ([TOOL-REFERENCE.md](TOOL-REFERENCE.md), [REPLICANT-CHECK.md](../GUARDIAN/REPLICANT-CHECK.md)). MCP server modules through the Guardian governance proxy are Phase 3 scope ([ROADMAP.md](../ROADMAP.md))
- **No on-device LLM inference** — the conversational model always runs on another host or a hosted API; only the knowledge graph's sentence-embedding model (`bge-small-en-v1.5`, [KNOWLEDGE-GRAPH.md](../MULTI-GRAPH/KNOWLEDGE-GRAPH.md)) runs in-process. `embraOS-QNM-Core` for sovereign on-host inference is Phase 5 scope; the OpenAI-compat presets (Ollama, LM Studio) are the local-inference path that shipped in Phase 1 — Sprint 5 ([ROADMAP.md](../ROADMAP.md)).
