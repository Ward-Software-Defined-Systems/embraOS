# Operation

Day-to-day use of embraOS once it is running.

**The web console is the primary interface.** Uploads (📎, paste, drop) and downloads, the sidebar with its Tools tab, the activity strip and the mobile chat are in the web console only. The serial TUI (`EMBRA_TUI=1`) is functional but is preferred for debugging.

## The Session Model

Every interaction with embraOS happens in a persistent session. Sessions survive disconnections. When you reconnect, the full conversation history is restored, and if the session has been idle for 30 minutes or more the intelligence opens with a briefing on where things left off (quick reconnects — a phone unlocking, a browser tab waking — resume silently; `/switch`ing to a session briefs whatever the idle time, once the soul is sealed and the session has history). The briefing also covers what happened in embraOS while you were away from that session: memory entries created, sessions created or deleted, cron jobs that ran (with each job's latest result), reminders that fired, and a newer embraOS release the update check first saw, since the session was last active. The brain reads these from its own records and hands them to the briefing turn; they are not written into the session's history. Every other turn carries the same kind of block for what happened since the session's last turn — the reminders that fired, the cron results recorded and a newer embraOS release first seen, in every mode, so the intelligence sees them at your next message whether or not a briefing ran; the model-facing text carries it, the history does not. A reminder (`countdown … act=true`) or a cron job (`cron_add … act=true`) can also ask for a turn of the intelligence's own when it fires: the console that holds the notification channel runs it in the active session, the turn is saved as `[Reminder fired] …` or `[embraCRON acted] …`, and at most twelve such turns run an hour; a trigger that cannot run (no session, a turn in flight, a setup waiting for your answer) is shown with its reason under the notice.

A turn runs on when the console that started it goes away (a phone that loses its connection, a browser tab that is reloaded). A console that attaches to the session while the turn runs is told so: when the turn began, with which message, and how many of its model calls are done. It shows the turn as running, so Esc, `/stop` and the phone's stop button end it from there, and it receives the turn's reply when the turn ends. No briefing is started beside a running turn.

You can run multiple named sessions for different contexts:

```
/new research         # Create a research-focused session
/new monitoring       # Create a monitoring session
/switch main          # Switch back to the main session
/sessions             # List all sessions and the provider each is pinned to
```

All sessions share the same intelligence — same memory, same identity, same soul. But each has its own conversation history and context.

**Stopping a stuck turn**: if the intelligence gets caught in a reasoning loop (far more common on local models than frontier ones), press **Esc** in the console while the turn is running, type `/stop`, or tap the **■** button that replaces Send on mobile. A stop works at any point of a turn: while a model server reads the prompt and has not begun to answer, while it answers, and while a tool runs. Generation stops immediately — the connection to the model server is severed — and the partial response stays in history marked as interrupted. Stops are fail-safe: they only ever affect the turn that was running when you pressed them, and they work during Learning Mode too.

**While a turn waits for the model**: once a minute has passed, the web console says for how long, on every provider: `Embra is thinking (12 min)...` in the console, `thinking… 12 min` on the phone's page. Each console counts from the moment it was told that the turn is thinking, so a phone that reconnects counts from there. The count ends when the answer's first text arrives, and the serial console's line carries no time.

**When a turn is cut**: a turn is cut when a model call fails before the turn has finished. The provider refuses the request, the connection is lost, a local model server sends nothing for the whole [model wait](../LOCAL-MODELS/RECOMMENDED-LOCAL-MODELS.md#how-long-embraos-waits-for-a-local-model), or the answer breaks off: an error arrives inside it, or the provider closes the stream before the reply is finished. It is the same on every provider (Anthropic, Gemini, Ollama, LM Studio). embraOS says what happened, and saves the turn as far as it got: your message, the reply so far, and a marker after it (`(response interrupted by a failed model call)`). A turn that had written nothing is saved with the marker alone (`(turn interrupted by a failed model call)`). Nothing you typed is lost.

- `/continue` sends the call that failed once more, with everything the turn held: the results of its tool calls and the intelligence's earlier steps, which a saved history does not carry. The reply is saved after the cut turn as a turn of its own, whose row in your place reads `[continue the turn that was cut]`. It needs the provider and the model the turn ran on. One cut turn is kept, the machine's last: a turn cut later takes its place, in any session and a reminder's or a cron job's turn among them, and in another session `/continue` names the session to switch to.
- A message of yours instead starts a new turn. The intelligence is told at its start that the turn before was cut and which tool calls had finished; it reads their previews with `turn_trace` or runs a tool again. After such a message `/continue` has nothing left to send.
- A turn that was running when embraOS restarted (a reboot, an update) is in its session after the boot as far as its last finished step: the text up to there with `(response interrupted by an embraOS restart)` after it, or `(turn interrupted by an embraOS restart)` alone when no step had finished. The text of an answer that was still arriving is not kept. The next turn is told of it the same way; there is nothing to continue then.
- A power cut is survived the same way. A turn is written out to the disk when it starts, after each of its model calls that goes on, after the tools of each step and when it is saved: the brain has the kernel write DATA out each time. A turn that the power cut is in its session after the boot as far as its last finished step, and a turn that had ended is there whole. The seal is made the same way: the soul is written out to the disk before its hash is stored. What the database wrote outside a turn in its last half minute (a reminder that fired, a cron job's record) can be lost with the power: the database hands its writes to the kernel, which writes them out in its own time.

A prompt that Gemini blocks is no cut turn: embraOS says so with Gemini's block reason, nothing was generated, and there is nothing to continue, since the same request meets the same block. Your message is saved with `(request declined by provider: refusal)` in the reply's place, so the later requests of that session carry it.

In Learning Mode a call that fails ends no phase: the phase stays where it was, and your next message is one more turn of it.

**Deleting a session** is a conversation, not a keystroke: `/sessions delete <name>` has the intelligence summarize the session and ask why you're removing it. Your reply is the reason and the approval: durable learnings are preserved to the knowledge graph (`remember`) as memories of that session, and only then does the system soft-delete it. The system then records the deletion and your reason as a memory, linked to what was preserved; the session's summary goes with the session. Deletion is soft for 7 days — the session leaves the listings (`/sessions` ends with one line that names the deleted sessions still in their grace period) and can't be attached, but `/sessions restore <name>` brings it back intact until the database's TTL reaper removes the data for good. Any slash command during the flow cancels it (but for the four the console answers itself, `/help`, `/ml`, `/media` and `/show-tools`, and for `/stop`, which is no command to the brain but a call of its own); a declining reply aborts it; the `learning` session (the sealed identity record) can never be deleted.

## Keyboard Shortcuts

**embraOS TUI** — in-conversation:

| Key | Action |
|---|---|
| `Enter` | Send message (or newline in `/ml` multi-line mode; a multi-line paste is sent whole, with what was typed before and after it) |
| `Up/Down` | Scroll history (`PageUp/PageDown` = 10 rows) |
| `Shift+Up/Down` | Scroll the expression/reasoning panel (`Shift+PageUp/PageDown` = 5 rows; snaps back to the tail on your next message, on errors, or when new expression content arrives) |
| `Esc` | Stop the current turn (only while it is thinking/streaming — idle Esc is a no-op) |

*There is no exit or detach chord. The console is a supervised child on both transports — embra-web respawns it after 1 s (`crates/embra-web/src/pty_bridge.rs`), embrad supervises it on serial (`crates/embrad/src/supervisor.rs`) — so there is nothing to detach from: leave the web console by closing the tab, the serial console with QEMU's `Ctrl+A X` below. `Ctrl+<letter>` chords are deliberate no-ops. Enter sends whatever modifier is held (`Shift+Enter` and `Alt+Enter` send too — the console's Enter arm ignores modifiers, `crates/embra-console/src/terminal/mod.rs`); `/ml` and a multi-line clipboard paste are the multi-line paths, on both transports; `Backspace` on an empty input drops a staged paste.*

*When the console cannot do its work it says why and exits — code 2 when it cannot reach `embra-apid`, code 1 when its conversation or its screen fails, code 3 when the gateway ended the conversation stream (apid or the brain restarted, or the connection was reset), code 4 when that stream failed — and its supervisor starts it again. In the web console the reason and the wait are shown in the terminal pane (`[embra-web] embra-console exited (code 3: the gateway ended the conversation stream) — restarting in 1 s…`) and logged by embra-web, which also logs each browser's attach, takeover and detach with the bytes it typed, and each chat message received by its kind and size, never its text; a console that keeps exiting early is started again more slowly, 1 s doubling to 30 s, for as long as it takes. On the serial console the console's own log is `/embra/ephemeral/embra-console.log` (`system_logs` with `service: embra-console`): its lines from the start to the exit, the exit cause among them, each with its time and level; the serial terminal shows the same lines without the time, and the restarted console's screen covers them there.*

*In the web console's `/ml` editor modal: Enter = newline, Ctrl/⌘+Enter or Send = submit, Esc/Cancel = discard.*

*Web console layout (the URL embraOS prints at boot — `https://localhost:3345/embraOS?token=…`, the console's access token in it, and the same URL once more for each address a card holds that another machine can reach; the console lives at `/embraOS` and nothing on `:3345` answers without the token; desktop): the top bar carries the brand and version, the **activity strip** (three stations on one link row: the model, embra-brain and the knowledge graph; text streams from the model to the brain as particles, database traffic moves between the brain and the graph, each tool call rises from the brain as a chip with its name and duration, and a readout under each station gives the model with its token rate, what the brain is doing, and the node count with the request rate; hover a station for its numbers; the strip reads the brain's activity feed over `/ws/activity`, names and numbers only, never content, and reads *activity feed offline* while the brain is away; **/provider --setup** is in the sidebar's Model group and the ⌘ palette), the role badge — **● Writer**, or **○ Read-only · operator N** with a **Take control** button (one writer at a time; other tabs observe), **⌘ Commands** (a filterable palette), **📎 Attach** (upload an image or a text file; dropping or pasting one on the terminal does the same — a text file lands in `/embra/workspace/uploads/` and rides your next message; a certificate, `.pem` or `.crt`, lands there as well, and the page types `/ca import uploads/<file>` ([COMMAND-REFERENCE.md](COMMAND-REFERENCE.md)) for it and leaves the Enter to you; on the machine's own display, which has no file picker, the button says so and shows this console's URL for a browser on another machine) and **↗ mobile** (the chat view, automatic at ≤ 768 px; there a tool call is one line — name, the result's first line, `▸` — tap to expand, and a session picked in the sessions sheet replaces the timeline with that session's bubbles). The left sidebar has two tabs, remembered per browser. **Commands** is the command list — a filter box above eight collapsible groups, the same groups as [COMMAND-REFERENCE.md](COMMAND-REFERENCE.md): groups start collapsed, click a title to expand it (remembered per browser), type in the filter to narrow every group to its matches (Esc clears). **Tools** is every tool call the intelligence made, newest first — time, name, status, the call number on a live call (it counts from one at each boot, so a call read back from the record shows none), and under it the duration and the session or the cron job — with a filter, a *feed offline* line while the brain is away, and the running call at the top (the count on the tab is this boot's calls; the rows read back from the record are history and are not counted); the list is fed by `/ws/tools` (the brain's tool-call feed through apid; embra-web keeps the last 200 calls, so a reload has them), fills from the record (`/api/tools`, `tools.turn_trace`, 2 KiB previews marked `rec`) after a restart, and **Load older** pages further back. Click a row and the call opens in a sheet beside the sidebar, over the left part of the terminal, which keeps its size: the input pretty-printed and highlighted, the result, and a note when the brain cut a side (64 KiB each), each section scrolling on its own so a long input never hides the result; Esc closes it. In the terminal each call is one dim marker line, `⚙ #17  14:02:11  file_read  0.8s` (`!` and `ERR` on an error) — click the marker to open the call in the sheet; `/show-tools full|marker|off` changes the rendering (console-local). A `/switch` replaces the transcript with the session's history, rows marked `history`. Above the terminal, a full-width status strip shows one pill per service plus the CPU / memory / DATA / STATE / load meters, refreshed from a 5-second `GET /api/status` poll; a `provider` pill joins them once the brain has probed the active LLM endpoint (~30 s after boot) and reads down while the endpoint is unreachable; a `local-ai-gateway` pill appears while a provider gateway is stored (`/local-ai-gateway`), lit while every provider request goes through it, dimmed and reading `off` while it is off. Buttons inject commands; the console is authoritative.*

**QEMU** — host-level (`run-qemu.sh` uses `-serial mon:stdio`, so `Ctrl+A` is the escape prefix):

| Key | Action |
|---|---|
| `Ctrl+A X` | Exit QEMU: a power cut for the VM. `/reboot halt` stops embraOS first and then powers the VM off, which ends QEMU too |
| `Ctrl+A C` | Switch between serial console and QEMU monitor |
| `Ctrl+A H` | Show all QEMU escape sequences |

## Themes and Accessibility

The web console has eight themes. A theme is the look of the web console in every browser, of the phone's page and of the display console, which are one page: one theme is in force for the whole machine. The serial console keeps the colours of the terminal it runs in.

| Theme | What it is |
|---|---|
| `ember` | Flame orange on warm black. The default |
| `nebula` | Pink and cyan on deep violet |
| `lagoon` | Turquoise and coral on deep teal |
| `forest` | Lime and gold on dark green |
| `cobalt` | Yellow and sky blue on navy. No state is told by red against green |
| `daylight` | Dark ink on warm paper |
| `contrast-dark` | High contrast on black |
| `contrast-light` | High contrast on white |

- **Choosing one.** In the web console, `/theme` in the sidebar's System group (on the phone: `/theme` in the command list) opens a picker that shows each theme in its own colours. A press shows a theme on that page alone; **Apply** keeps it for the machine; **Cancel** (**×** on the phone's sheet), Escape or a press beside the picker puts back what was shown. Typed, `/theme` lists the themes, `/theme <name>` sets one and `/theme reset` goes back to `ember`. Both ways work before the first session. The picker types nothing into the console, so it also works from a browser that only observes.
- **Where it is kept.** The theme's name is one file on STATE (`/embra/state/theme`), so it travels with a backup. A page is drawn in the stored theme from its first paint, and an open page and the display follow a change within a few seconds. A stored name the running release does not know (after a rollback, or a restore of a later release's backup) is shown as `ember`, and the file is left as it is.
- **Contrast.** In every theme, text holds at least 4.5:1 against what it is read on, the contrast WCAG 2.1 asks at level AA. In `contrast-dark` and `contrast-light` it holds 7:1, level AAA. A field's edge and the ring around the control the keyboard is on hold 3:1, and so does the wordmark, a logotype. The terminal holds a character to the theme's figure against its own cell, whatever colour a program named: a coloured word on a bar is drawn lighter or darker than the program asked. It leaves two kinds of character out: text a program marks faint is held to half the figure, and line-drawing and block characters keep the colour they were given. Tests compute the figures from the stylesheet (`crates/embra-web/src/theme_contract.rs`).
- **Beyond colour.** The control the keyboard is on is ringed; in the terminal the cursor says so, filled while the keyboard is there and an outline while it is not. A service pill that is not up says `down` or `off` beside its dot, the phone's health dot carries a mark, and an error or a warning on the phone's page begins with the word. For a reader who has asked the system for less motion, the page's animations and transitions, the cursor's blink and the activity strip's moving parts stop; the strip's fades and the thinking line's dots remain. No text is set under 12 pixels.
- **What is not claimed.** The figures above are computed from the stylesheet's colours. The rest of WCAG 2.1 (what a screen reader says of each control, every path of the keyboard, text spacing, reflow at 400%) has not been audited.

## Current Limitations

- **API or remote LLM** — Anthropic Claude / Google Gemini require internet + a paid API key. The Ollama and LM Studio presets connect to an OpenAI-compatible server: a local one you operate (typically a Mac Studio or similar) or any hosted one — vLLM, Together, Fireworks, OpenRouter — via `/provider --setup <ollama|lm_studio>` (base URL without `/v1`, key at the Bearer step; https endpoints keep their implicit 443). Inference still happens on a separate host — on-device inference inside embraOS itself belongs to Phase 5's sovereign-intelligence options ([ROADMAP.md](../ROADMAP.md)).
- **Platforms** — embraOS runs as a virtual machine under QEMU, VMware ESXi, Microsoft Hyper-V, VMware Fusion and Parallels Desktop, and on bare metal. x86_64 on Ubuntu is the reference build; the [aarch64 / Apple Silicon](../BUILD/AARCH64-BUILD.md) and [Intel Mac](../BUILD/INTEL-MAC-BUILD.md) guides cover those build hosts. What has been run on each platform, and what has not been run yet, is in [VALIDATION-STATUS.md](../VALIDATION-STATUS.md). Kubernetes is Phase 5 scope ([ROADMAP.md](../ROADMAP.md)).
- **The installer is UEFI only** — `embraos.iso` needs Secure Boot off, writes one disk and no NVRAM boot entry: the firmware boots the EFI System Partition's removable-media path ([QUICK-START.md](../BUILD/QUICK-START.md), Install on bare metal).
- **The display console's mode is set at boot** — 1920x1080 where the display offers it (`embra.kioskmode=` for another, [QUICK-START.md](../BUILD/QUICK-START.md)); it does not follow a VM window resized later. The display console's web process holds about 700 MB of memory on the console page: on a machine with 2 GiB or less, add `embra.kiosk=0` to the kernel line: nothing checks the memory for you.
- **The kernel's log is read through the intelligence** — the installed machine boots `quiet`, offers no login and shows the kernel's lines on no console; `system_logs` with `service: kernel` reads the kernel's ring buffer (the drivers and their firmware, USB and disk events, the microcode revision, each warning and error marked with its level).
- **The time server's answer is not authenticated** — embrad resumes a clock that reads earlier than the image's build time from the last time the machine saved (the clock, written to STATE once a minute), or from the build time, then asks a time server at boot, every hour while the OS runs, and when the network arrives or returns: the time servers a DHCP lease names and then `time.cloudflare.com`, or the ones `/network time` stores, or `embra.ntp=<host>` for one boot ([QUICK-START.md](../BUILD/QUICK-START.md), The clock). The answer is plain SNTP, and a host on the path can forge it. On a running machine one bound holds: once a time server has set the clock in a boot, an answer more than fifteen minutes away from it is recorded and not applied. A boot without an answer keeps the hardware clock's time, says so on the banner when that was earlier than the build, and asks again every quarter of an hour and when the network arrives ([OPEN-PROBLEMS.md](../OPEN-PROBLEMS.md)).
- **Wi-Fi is WPA2 and WPA3 personal, and open networks** — a company network that asks for a user name or a certificate (802.1X), WPS and an access point of the machine's own are not supported. The drivers are those of the card families linux-firmware serves (Intel, Realtek, Qualcomm Atheros, MediaTek and Ralink, Broadcom), loaded for the card embrad finds; a card of another family is not brought up ([QUICK-START.md](../BUILD/QUICK-START.md), Wi-Fi).
- **No MCP server modules** — the tool surface is the 121 built-in tools plus Guardian dynamic tools: three shipped with the image and installed at boot (`web_search`, inert until `/guardian key brave`; `http_request`, a guarded curl that needs no key; `websocket`, a client whose connections stay open between calls), the rest operator-authored (`/guardian-define`) or intelligence-proposed (`guardian_propose`), both replicant-checked against the sealed soul, proposals operator-approved before they compile ([TOOL-REFERENCE.md](TOOL-REFERENCE.md), [REPLICANT-CHECK.md](../GUARDIAN/REPLICANT-CHECK.md)). MCP server modules through the Guardian governance proxy are Phase 3 scope ([ROADMAP.md](../ROADMAP.md))
- **No on-device LLM inference** — the conversational model always runs on another host or a hosted API; only the knowledge graph's sentence-embedding model (`bge-small-en-v1.5`, [KNOWLEDGE-GRAPH.md](../MULTI-GRAPH/KNOWLEDGE-GRAPH.md)) runs in-process. `embraOS-QNM-Core` for sovereign on-host inference is Phase 5 scope; the OpenAI-compat presets (Ollama, LM Studio) are the local-inference path that shipped in Phase 1 — Sprint 5 ([ROADMAP.md](../ROADMAP.md)).
