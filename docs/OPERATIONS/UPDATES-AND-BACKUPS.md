# Updates and backups

How embraOS keeps itself whole across an OS update and how an operator takes a backup from inside the OS. The host-side script `scripts/embraos-backup.sh` stays the path for carrying STATE and DATA across an image rebuild on the build host ([BUILD/QUICK-START.md](../BUILD/QUICK-START.md)); everything below runs on the machine itself, and a backup taken there leaves the machine through the web console and comes back through it.

## The disk and the two OS slots

The image is a GPT aligned to 1 MiB with five partitions (`buildroot/board/embraos/layout.sh` names them, in order):

| Partition | Size | Content |
|---|---|---|
| `esp` | 64 MiB | The EFI System Partition: GRUB (`EFI/BOOT/BOOTX64.EFI` or `BOOTAA64.EFI`), `grub.cfg`, `grubenv` |
| `rootfs_a` | 2 GiB | OS slot A: one SquashFS with the kernel, the initramfs, the probe-time firmware and microcode archives and the slot's version line under `/boot`, the release stamp at `/etc/embraos-release` |
| `rootfs_b` | 2 GiB | OS slot B, empty until the first update |
| `state` | 256 MiB | STATE: the seal, the CA, the operator's settings and drop-ins |
| `data` | 4 GiB | DATA: the database, the workspace, and the backups under `backups/` |

The slots were 1 GiB until 2026-11-08 and are 2 GiB since the firmware for bare metal joined the image; a slot's size is fixed on the disk that carries it, and the updater refuses a release larger than the slot partition it would write, so a disk installed or deployed with the older layout takes no release that outgrows 1 GiB. DATA is the last partition, and it grows to the disk's end at boot when a gibibyte or more follows it: the installer leaves no gap, but a VM's virtual disk enlarged afterwards has one. `embra-update grow-data` runs before the services at every normal boot (embrad, the database stopped): sgdisk moves the backup GPT to the new end and recreates the entry from the same start, the kernel is told the new length (`BLKPG_RESIZE_PARTITION`, while the partition is mounted), and resize2fs grows ext4 online; it says so on both consoles when it grows (what follows DATA, then the old and the new size), nothing when there was nothing to do, and a failure is a line and a normal boot with the partition as it was. The disk is 8514 MiB, a whole number of MiB: 1 MiB before the first partition, the partitions, and 1 MiB that holds the backup GPT on the last sector (`layout.sh` computes the size; the build reads it back from the image). The converted disks in the folders beside the raw image, `vmware/embraos.ova` and `vmware/embraos.vmdk`, `hyper-v/embraos.vhdx` and `parallels/embraos.vmdk`, have the same capacity.

GRUB boots the active slot by default and shows its menu for three seconds: each slot that holds a release, a Diagnostics submenu, Update embraOS, Backup and restore, Reboot, Halt and Firmware setup. A slot without `/boot/embraos-slot.cfg` has no entry and no "Make slot … the default" or "Boot slot … once" line under Diagnostics: a fresh image lists slot A alone, and slot B appears after the first update. `grubenv` holds the A/B state (`slot_active`, a staged `slot_try` with its `tries_left`, a status per slot). A slot an update staged is booted with `embra.trial=1` while it has tries left; embrad confirms it once every service is healthy, and GRUB marks it failed and falls back to the previous slot when the tries run out.

## Backups

A backup is a snapshot of STATE and DATA: a `tar.gz` under `/embra/data/backups/<timestamp>_<label>/` with a `backup.json` record beside it (the label, who took it, the release, the database engine, the counts, the sizes, the archive's SHA-256, what was left out). It holds STATE whole but the halt reason, the next-boot marker and the machine's saved clock (`last-known-time`, which a restore leaves in place: it belongs to the machine, not to the snapshot), DATA's database directory whole, and DATA's workspace but the Guardian's build tree (its built artifacts are kept) and cargo home. Links stay links; special files are skipped and named in the record.

A snapshot runs only while the database is stopped, so a copy of its files is consistent: before the services start. Two ways to ask for one:

- **From a session:** `/backup create [label]` schedules it for the next boot and `/reboot now` boots; embrad takes the snapshot before WardSONDB starts and the boot continues into the session. `/backup status` shows what is scheduled.
- **From the boot menu:** Backup and restore → Back up STATE and DATA. embrad takes the snapshot, its progress on both consoles (the serial line and the display), and reboots to the menu.

The free-space rule: DATA must have the snapshot's size plus 256 MiB free, or the snapshot is refused with both figures. `/backup list` shows every backup, newest first, each complete one with its download route (`web: /api/backups/<name>`): the web console streams the archive to the browser behind the console's token, with no size cap. `/backup delete <name>` removes one. The automatic snapshots an update takes (labels `pre-v<version>`) rotate: the newest two stay; a snapshot with any other label is never removed on its own, and neither is an uploaded backup, whatever its label.

The archives are outside the workspace and the model's tools are refused them (`file_read` and the rest answer that the backups carry the operator's STATE). The host script's backup of DATA leaves `backups/` out: each is a copy of STATE and DATA already.

### Uploading a backup

A download is the archive alone, `<name>.tar.gz`; its record stays on the machine. The way back is the web console: `PUT /api/backups/<name>` takes the archive as the request's body, behind the console's token, and pipes it to `embra-update import <name>` as it arrives. The limits of the console's other uploads do not apply (an attachment is 12 MiB at most). DATA's room does: the archive has to fit beside the same 256 MiB reserve, or the upload is refused with both figures and none of it is written, and the updater ends an upload that takes DATA under the reserve on the way. One upload runs at a time.

The archive is checked while it is written:

- It is one gzip stream that holds one tar archive, read to its end with its checksum.
- Every member is a directory, a regular file or a link.
- Every path is under `state/`, `data/wardsondb/` or `data/workspace/`, named once, in a directory the archive named before it.
- None is a STATE entry a snapshot leaves out (the halt reason, the next-boot marker, the saved clock, `lost+found`).

A snapshot the OS took passes. A file that is no backup, a damaged one, one cut short and a name that is taken are refused with the reason, the member named where one is at fault, and nothing of the upload is kept. What passes gets its record made again from the archive: the SHA-256, the counts and the sizes, the database engine from the archive's own marker, the stamp and the label from a name of a snapshot's shape. It is listed as `uploaded`, and the release that took it is not known. An uploaded backup is the operator's: the rotation never removes it, and it never passes for the snapshot an update takes before a release's first run.

The check is against a wrong file and a damaged one. What an archive holds is restored as it is, so whoever uploads a backup is trusted with the machine, as whoever restores one is.

Two ways to upload:

- **From a browser on another machine:** the sidebar's `/backup` form, action `upload`, then the file. The name is the file's without `.tar.gz` and without the ` (1)` a browser adds to a second download, or the one typed in the form. A card on the page shows the progress and then the machine's answer. Nothing is typed into the console: the upload needs neither the console nor the brain, so it works at any stage, the first-boot wizard and Learning Mode among them. The display console has no file picker and says so.
- **From a command line:** `curl -T <name>.tar.gz 'https://<host>:3345/api/backups/<name>?token=<token>'`, with `--cacert` and the machine's CA certificate, or with `-k`: the console's certificate is from the machine's own CA. The answer is JSON, 201 with the record or the refusal with its reason. A refusal that does not depend on the archive (the name, the room, another upload running) is answered at once to a client that waits for the go-ahead, as `curl` does for a file over 1 MiB, and after the body has been read and dropped to one that is already sending: an answer written into a connection that still carries the upload is lost when it closes. `GET /api/backups/<name>/upload-check?bytes=<size>` says beforehand what an upload of that size under that name would be told; the browser's form asks it first.

A machine that is installed again starts with empty STATE and DATA. Download the backup before the install, upload it after the first boot, then `/backup restore <name>`, its confirmation, and `/reboot now` in the console, at the wizard's first prompt: `/backup` and `/reboot` are answered before any session exists (below). The boot menu's Restore entry does the same.

Validated under QEMU on 2026-11-12 from a command line, with two scratch machines of one build. The first took a backup of itself in a maintenance boot (`embra.mode=backup`) and served it: 127 files, 125 KiB. That download and an archive of 4.30 GiB made from it were uploaded with `curl` to the second, a fresh install on which nothing had been set up, on a disk DATA had grown on. Each record matched its archive (the hash, the counts, the engine), and the large one downloaded again was the file that was sent. After a power cut the restore job (`embra.mode=restore`) listed both as `uploaded` and restored the large one; the second machine then carried the first one's CA and the uploaded files byte for byte. Refused, each with its reason and nothing kept: a `tar.gz` that is no backup, a backup cut short, a text file, an archive with a next-boot marker, a name that is taken, a name no backup can have, an upload without the token and one from another origin. `upload-check` refused a size DATA has no room for, and a second upload while one ran. An upload cut off by its client left nothing. On bare metal the whole flow passed (a YouYeeToo X1 single-board computer, 2026-11-12): the board installed again, the backup uploaded through the form from a browser, then restored from the wizard's first question (Before a session, below).

## Restoring

A restore replaces STATE and DATA's database and workspace with a snapshot and keeps the other backups; an uploaded backup restores like one taken on the machine. It runs before the services start, like a snapshot:

- **From a session:** `/backup restore <name>` answers with the confirmation to type, `restore <name>`; anything else, a slash command included, cancels. Confirmed, the next boot restores and reboots: `/reboot now` when ready.
- **Before a session:** the same two commands are answered during the first-boot configuration wizard, Learning Mode and the identity import's dialogue, where no other command is (each gets one line that says so). The confirmation is taken there and is never the wizard's answer or a line of the learning conversation. A restore at that point replaces the setup in progress. In the console a command is typed at a question that takes text (the wizard's first one, the name, among them) and anywhere in Learning Mode; while a list of choices is on the screen, Enter sends the highlighted choice, so that question is answered first. Validated under QEMU on 2026-11-12, typed through the web console's terminal socket: at the wizard's first question an uploaded backup was listed and restored (`/backup restore`, the confirmation, `/reboot now`) and the machine came back as the install the backup was taken on; in Learning Mode, reached through the wizard against a stand-in model server, the same commands ran, a plain line reached the model, and neither a command nor the confirmation did. On bare metal the wizard's part passed (the same board, 2026-11-12): after an upload through the form, `/backup restore <name>`, its confirmation and `/reboot now` typed at the name question. Learning Mode on bare metal: **TBD**.
- **From the boot menu:** Backup and restore → Restore STATE and DATA. A numbered list on both consoles, the number asked twice and answered on whichever console the operator types on (the first line typed wins and is echoed on the other), anything else reboots without restoring.

A restore refuses an incomplete entry (a `.partial` directory a crash left, which `/backup delete` removes), an archive that does not match its record, and a snapshot whose database engine is not the running release's (a database of the other engine cannot be opened; `seed-state.sh --wipe data` on the host is the way to start over). The sealed identity comes back whole: STATE's `soul.sha256` and DATA's soul document are from one snapshot, so trustd's seal check passes at the next boot.

## Updates

An OS update is a new slot image written into the inactive slot and tried by GRUB; the running slot is untouched and is where GRUB returns if the new release does not come up. The operator decides: `/update apply` in a session, or Update embraOS in the boot menu. The intelligence has no tool for it.

### What a release publishes

`scripts/release-update.sh --tag <vX.Y.Z-phaseN> --arch <x86_64|aarch64> --engine <fjall|rocksdb> --key <private.pem>` prepares, per architecture and engine, six files under `output/update/` and prints their upload lines (uploading to the GitHub release is the operator's step; the private key never enters the repository or CI): the three of the update, in the table below, and the installer medium with its checksum line and that line's signature, described further down.

| File | Content |
|---|---|
| `embraos-<tag>-<arch>-<engine>.rootfs.squashfs` | The slot image the build produced: one SquashFS with the five files GRUB reads under `/boot` (the kernel, `ucode.cpio`, `firmware.cpio.gz`, `initramfs.cpio.gz`, `embraos-slot.cfg`) and the release stamp at `/etc/embraos-release` |
| `embraos-<arch>-<engine>.manifest.json` | `update.v1`: the version, tag, build id, architecture, engine, schema version, kernel, the rootfs file's name, size and SHA-256, when it was built, the notes URL. The name carries no version: the OS fetches it from the release marked latest |
| `embraos-<arch>-<engine>.manifest.json.sig` | A raw Ed25519 signature over the manifest's bytes, base64, made with `openssl pkeyutl -sign -rawin` and the operator's key |

The script refuses a tag that is not the one the tree is at or not the version `CITATION.cff` records, a dirty tree, and a slot image whose stamp names another version, architecture or engine or whose `/boot` lacks one of the five files GRUB reads from a slot (the kernel, `ucode.cpio`, `firmware.cpio.gz`, `initramfs.cpio.gz`, `embraos-slot.cfg`); it verifies its own signature against `scripts/update-signing.pub` before it prints anything. Nothing is written before every check has passed, the installer medium's and the key's among them: the six files are made in a staging directory inside the output directory and moved out of it together, so a run that is refused, or that fails while it writes, leaves none of them and leaves an earlier run's files as they were. It signs no release that would trust a certificate authority of the builder's own ([Imported_CAs/README.md](../../Imported_CAs/README.md)): a slot image that carries files under `/usr/share/embra/ca-certificates/`, a tree whose `Imported_CAs/` holds certificate files, and a slot image it cannot read for want of `unsquashfs` (Ubuntu: `squashfs-tools`; macOS: `brew install squashfs`) each stop it before anything is written, and `--allow-imported-cas` signs all the same, for a release meant for machines of one's own. With an xorriso at hand the ISO must be the medium of the same root filesystem (`ROOTFS_SHA256` in its manifest), so what was checked of the slot image holds for the installer medium. Every release uploads all four manifests (two architectures, two engines), or an instance of the missing pair reads "no manifest for … is published at this source". `--self-test` signs a fixture with a throwaway key.

### What the OS trusts

The OS verifies a manifest's signature against the keys in `/usr/share/embra/update-signing.pub` (the repository's `scripts/update-signing.pub`, baked into the image) and in the operator's drop-in `/embra/state/update-signing.pub` (`seed-state.sh --update-key <pem>`), before it reads anything of the manifest. The file may hold several keys: a new key goes in beside the old one release before the old one stops signing, so an instance on the previous release still verifies the next. Until a key is present the updater refuses every manifest. The key pair is made once with `openssl genpkey -algorithm ed25519 -out update-signing.key` and `openssl pkey -in update-signing.key -pubout`.

The signature binds the version, the tag, the build id, the architecture, the engine and the image's hash to the operator's key: the URL, a mirror, a DNS answer or a certificate cannot hand the OS an image it will boot. It does not protect against the signing host itself; rotation limits that window. A signed manifest for an older version is a downgrade and refused unless the operator asks for it with `/update apply --allow-downgrade`, which applies another build of the running version as well; one for another architecture or engine is refused before any download; the data's own engine marker is what the manifest is compared with.

### Where the manifest comes from

The default source is the GitHub releases of the public mirror, `https://github.com/Ward-Software-Defined-Systems/embraOS/releases/latest/download` (no API, no token: GitHub answers the fixed name with the latest non-draft, non-prerelease release). `/update source <url>` stores the operator's own base under `/embra/state/update-source` — `https://…`, or `http://` to a private address, such as a GitLab generic package registry behind the operator's CA (the updater trusts the certificate authorities embrad merges for every service: the image's and STATE's drop-ins) — and `/update source reset` returns to the default. The image is always fetched from the same base under the name the manifest gives, never from a URL inside the manifest, so a mirror serves the same signed manifest. `/update --tag <v…>` checks one release's own files on GitHub in place of the latest, and `/update apply --tag <v…>` applies it; with the operator's own source set the command refuses a tag, since the updater reads that source as it is and would check another release than the one named.

### Applying

`/update` reports the running release, the available one with its schema step and notes, and the verdict. `/update apply` runs the updater as a child of the brain, one at a time, its lines in the console:

1. The manifest is fetched and verified again, and the inactive slot must not be the slot GRUB may still fall back to (a staged slot untried, or a trial boot in progress).
2. The image is streamed into the inactive slot's partition, hashed as it is written, refused past its declared size, synced, read back and hashed again; both digests must equal the signed one. The slot's previous content is gone from the first byte, the one sacrifice of two slots; a half-written slot is simply unmarked and never booted.
3. `grubenv` is written: the slot staged with three tries. Nothing else moves; the running slot stays the default until the new one confirms.

`/reboot now` boots the staged slot (`embra.trial=1` on its kernel line). Before any service starts, the new release takes a snapshot of STATE and DATA (`pre-v<version>`, kept to the newest two), so the previous release has a consistent copy to come back to; a snapshot it cannot take halts, which counts the try. Its brain then migrates the knowledge graph, and once every service is healthy embrad confirms the slot: active from now on. A slot that never confirms is tried three times and then marked failed, and GRUB boots the previous one. `/update status` shows both slots; `/update rollback` makes the other slot the default by hand (`/reboot now` boots it).

A rollback onto a knowledge graph the newer release migrated: the older brain refuses to start — the halt reason names both schemas and the `pre-` snapshot — and the boot menu's Restore entry puts that snapshot back. The Guardian's dynamic tools are rebuilt with `/guardian rebuild --all` when a release moves the in-OS toolchain ([COMMAND-REFERENCE.md](COMMAND-REFERENCE.md)).

A release also publishes the installer medium, one per architecture and engine: `embraos-<tag>-<arch>-<engine>.iso` (the x86_64 one is about 900 MB with the firmware), beside it `…iso.sha256`, its `sha256sum` line, and `…iso.sha256.sig`, the same Ed25519 signature over that line as the manifests carry, made with the operator's key (`scripts/release-update.sh` writes the three and names them in its upload line; with an xorriso at hand it refuses an ISO whose own manifest names another architecture, engine or version). The aarch64 medium is validated on Apple Silicon under QEMU and under VMware Fusion (2026-11-11, a build's own `embraos.iso`; [AARCH64-BUILD.md](../BUILD/AARCH64-BUILD.md)). To check a download: `sha256sum -c embraos-<tag>-<arch>-<engine>.iso.sha256`, and `openssl pkeyutl -verify -rawin -pubin -inkey <the key from scripts/update-signing.pub> -in …iso.sha256 -sigfile <(base64 -d …iso.sha256.sig)`. The OS never downloads the ISO; it is for a fresh install, and the images it writes update from the manifests like any other.

`/update apply --allow-downgrade` applies what an apply refuses otherwise, a release older than the running one or another build of the running version; `--tag <v…>` on a check or an apply names one release of a GitHub releases source. The trial boot is the same: the snapshot first, then the brain, and an older brain on a knowledge graph a newer one migrated refuses to start, as after a rollback. The two options reach the updater from `/update` since 2026-11-11 (`update_options`, `updater_args`; the updater's own handling is unchanged); a run of each on a machine is **TBD**. The boot menu's entry takes neither.

From the boot menu, Update embraOS boots the active slot with `embra.mode=update`: embrad brings the network up, asks the time server for the time (the download checks the server's certificate against the clock) and runs the updater on both consoles (`Apply … to slot b? [y/N]`, answered on the serial line or at the display's keyboard), then reboots into the staged slot, or back to the menu with the reason.

### From the installation medium

The installer medium upgrades an installed disk in place as well, with no network and no published release: boot the medium and pick the disk. Where the installer finds an installation it says what each slot holds and asks `Upgrade in place or clean install? [u/c, q = reboot without installing]`, with no default. `u` and its confirmation (`Write <version> (build …) into slot B of <disk>? … [y/N]`) do what an apply does, from the medium:

1. The installer has read the disk before it asks: the five partitions by name, `grubenv`, each slot's release, DATA's engine marker (a read-only mount that replays no journal). The reading writes nothing.
2. The medium's image is streamed into the slot that is not the default and verified as an apply verifies it.
3. GRUB's loader and `grub.cfg` on the EFI System Partition are replaced with the medium's: each is written beside its destination and synced first, then renamed, the loader before the menu; `grubenv` stays. An apply never does this: an installed disk gets a new boot menu from a medium alone.
4. The slot is staged with three tries, as an apply stages it.

The partition table, STATE and DATA are not written. The first boot is the trial boot above: the `pre-v<version>` snapshot before any service, the confirmation once every service is healthy, three tries and then the slot before it.

The upgrade is refused before anything is written, with its reason, and the clean install stays at hand: a medium older than the installed release (an older brain halts on a newer knowledge graph; `embra.downgrade=1` on the installer's kernel line allows it, typed at the medium's menu with `e`), the build the default slot already holds, a build the other slot already holds staged and not yet booted, another architecture, another storage engine than the data's, an image larger than the disk's slots (such a disk is reinstalled clean), a default slot without a file the medium's boot menu reads from a slot, and a disk whose `grubenv` cannot be read. Another build of the same version is offered, and its confirmation says that it is one.

`embra.upgrade=<disk>` on the medium's kernel line runs the upgrade unattended; where it is refused nothing is written, and it never becomes a clean install. `embra.install=<disk>` is the unattended clean install and erases an installation as it always did; a line with both gets the upgrade. The medium is trusted as a medium is: whoever boots one at the machine can read or erase the disk already.

Validated with the new installer run in a scratch VM on the image's kernel, the built ISO as its medium and copies of the built image as its disks (2026-11-13): another build of the same version upgraded at the prompt and unattended, into slot B and, with slot B the default, into slot A; the upgraded disk booting through its own GRUB under OVMF, the staged slot tried, the snapshot taken and the slot confirmed; a staged slot that cannot pass its trial given up after three tries and the slot before it booted; every refusal and every declined question leaving each partition byte for byte as it was; the clean install chosen at the question, on a blank disk and unattended, its disk booting. The installer started from a medium built with it (the medium's menu, both consoles) is **TBD**, under QEMU and on a machine.
