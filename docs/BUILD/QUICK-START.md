# embraOS Quick Start

Build a QEMU-bootable embraOS disk image from source and boot it. The project landing page is [../../README.md](../../README.md).

> **Default UI.** The browser-based **embra-web** console is the default UI, served
> over HTTPS at **https://localhost:3345/embraOS** — open it from the URL embraOS
> prints at boot, which carries the console's access token (`?token=…`; accept the
> embraOS-CA cert on first visit, or import the CA once: `/api/ca.crt`, under
> The web console's certificate below). The token is made at the first boot and stays
> the same from then on, so the URL can be kept as a bookmark; `/web-token rotate`
> makes a new one and signs every browser out. The URL is shown at boot, after a
> rotation and in the display console's menu, and nowhere else; the first visit sets a cookie and the
> address bar loses the token, so a phone or another workstation needs the URL with
> the token once. `/` and every other path answer 404; after `/web-token rotate` an
> open tab gets 401 until it is opened from the new URL. It wraps the same conversational TUI in xterm.js over a
> PTY→WebSocket bridge. Set **`EMBRA_TUI=1`** before `run-qemu.sh` to boot the
> serial TUI instead — no image rebuild needed. The serial TUI is functional but is
> preferred for debugging; the web console is the primary interface.

## Build from Source

The build writes a self-booting x86_64 disk image for QEMU, the same disk converted for VMware, Hyper-V and Parallels, and the installer ISO: an immutable SquashFS rootfs in two slots, service supervision, and soul verification at boot.

> **Apple Silicon (aarch64) hosts:** follow [AARCH64-BUILD.md](AARCH64-BUILD.md) instead — the Buildroot tree is arch-parameterized but the Apple-Silicon build runs through `scripts/build-image-aarch64.sh`.
>
> **Intel Mac hosts:** follow [INTEL-MAC-BUILD.md](INTEL-MAC-BUILD.md).

### Ubuntu 24.04 / 26.04 (Recommended — Full Build Pipeline)

```bash
# Install dependencies
# clang + libclang-dev are required by bindgen (pulled in by the in-tree
# wardsondb crate's rocksdb dependency, rust-librocksdb-sys) to parse C headers at
# build time.
# libcrypt-dev provides crypt.h for Buildroot's host-mkpasswd build —
# Ubuntu 26.04 split crypt.h out of glibc into the standalone libxcrypt.
# xz-utils unpacks the pinned in-OS Rust toolchain that build-image.sh
# Step 3.5 bakes into the image (the Guardian dynamic-tool substrate).
# qemu-utils is qemu-img: Step 5 converts the disk for the hypervisors with
# it, and stops without it.
sudo apt-get update && sudo apt-get install -y \
  build-essential gcc g++ unzip xz-utils bc cpio rsync wget curl python3 file git \
  protobuf-compiler musl-tools clang libclang-dev \
  qemu-system-x86 qemu-utils ovmf libcrypt-dev libelf-dev libssl-dev genext2fs

# Install musl cross-toolchain (gcc+g++ with a matching musl libstdc++).
# Ubuntu's musl-tools only wraps the host gcc and drags in a glibc-linked
# libstdc++ — which won't link against musl. WardSONDB's rocksdb backend is
# C++, so we need a self-contained musl toolchain from musl.cc.
cd /tmp
curl -LO https://musl.cc/x86_64-linux-musl-cross.tgz
sudo tar -xzf x86_64-linux-musl-cross.tgz -C /opt
# Put the toolchain on PATH for ad-hoc cargo builds (build-image.sh also
# auto-detects /opt/x86_64-linux-musl-cross even if PATH isn't set).
echo 'export PATH="/opt/x86_64-linux-musl-cross/bin:$PATH"' >> ~/.bashrc
source ~/.bashrc
x86_64-linux-musl-gcc --version
x86_64-linux-musl-g++ --version

# Install Rust. The checkout pins its compiler in rust-toolchain.toml
# (1.98.1, with clippy, rustfmt, and the wasm32 + musl targets); rustup
# installs it on the first cargo run inside the repository.
curl --proto '=https' --tlsv1.2 -sSf https://sh.rustup.rs | sh
source ~/.cargo/env
rustup target add x86_64-unknown-linux-musl

# embra-web frontend (Leptos/WASM) — build-image.sh Step 0.5 builds it
# with Trunk and aborts if trunk is missing.
rustup target add wasm32-unknown-unknown
cargo install trunk --locked          # CI pins Trunk 0.21.14 — add --version 0.21.14 to match
```

```bash
# Clone and configure — use ~/projects so source + build artifacts persist
# across reboots (the /tmp toolchain step above is fine because /opt persists).
mkdir -p ~/projects && cd ~/projects
git clone https://github.com/Ward-Software-Defined-Systems/embraOS.git
cd ~/projects/embraOS

# Configure musl linker (per-machine, only needed once)
cat >> ~/.cargo/config.toml << 'EOF'
[target.x86_64-unknown-linux-musl]
linker = "x86_64-linux-musl-gcc"
EOF
```

```bash
# Build and run — pick a storage engine: rocksdb (battle-tested) or fjall (pure Rust)
./scripts/build-image.sh --storage-engine rocksdb   # Full pipeline: Rust → initramfs → Buildroot → disk image
                                                    # Leaves output/images/embraos.img (QEMU) and the same disk in a folder
                                                    # per hypervisor: vmware/embraos.ova (ESXi 8.0+, vCenter: hardware
                                                    # version 20, guest "Other 6.x or later Linux (64-bit)") with
                                                    # vmware/embraos.vmdk (a disk for Fusion, Workstation, VirtualBox),
                                                    # hyper-v/embraos.vhdx (gen 2, Secure Boot off) and parallels/embraos.vmx
                                                    # with its VMDK (the machine Parallels Desktop imports on an Intel Mac)
                                                    # (qemu-img, from qemu-utils, converts them),
                                                    # and beside the image embraos.iso, the UEFI installer for bare metal and
                                                    # the hypervisors (a DVD, or a USB stick written with dd; the aarch64
                                                    # build writes the same medium for its architecture: AARCH64-BUILD.md)

# Default UI is the embra-web console — open the URL embraOS prints at boot (https://localhost:3345/embraOS?token=…)
./scripts/run-qemu.sh                                # Boot in QEMU — OVMF, GRUB's menu (3 s), slot A, web console (default)
EMBRA_BOOT=direct ./scripts/run-qemu.sh              # Kernel and initramfs from the host: no firmware, no menu

# Or fall back to the serial TUI on this terminal (no rebuild needed; functional, preferred for debugging)
EMBRA_TUI=1 ./scripts/run-qemu.sh                    # Boot in QEMU — serial TUI

# Optional: per-request WardSONDB log lines (default: lifecycle/warn/error only)
EMBRA_DB_VERBOSE=1 ./scripts/run-qemu.sh             # embra.dbverbose=1 → wardsondb --verbose
EMBRA_LOG_LEVEL=info,kg::traversal=debug ./scripts/run-qemu.sh  # embra.loglevel=… → brain EMBRA_LOG
                                                     # (read back in-session via system_logs; no spaces)
EMBRA_TUI=1 EMBRA_GRAPHICS=sixel ./scripts/run-qemu.sh  # serial TUI image pane: halfblocks (default) |
                                                     # sixel | kitty | iterm2 | auto | off → embra.graphics=…
                                                     # (the web console's PTY is always sixel)

# The display: the VM has one only with EMBRA_VNC=1 (host side, nothing reaches the OS), or with EMBRA_KIOSK=1, which implies it
EMBRA_VNC=1 ./scripts/run-qemu.sh                    # the display on a VNC server at 127.0.0.1:5900, password embraos, with
                                                     # a USB tablet and the keyboard: the display console runs there
                                                     # (loopback only: ssh -L 5901:127.0.0.1:5900 <host>, then localhost:5901)
# The display console's knobs reach the kernel line, and act on a VM that has the display
EMBRA_VNC=1 EMBRA_KIOSK=0 ./scripts/run-qemu.sh      # the display without its console (embra.kiosk=0): boot log and banner only
EMBRA_VNC=1 EMBRA_KBD=de ./scripts/run-qemu.sh       # the display console's keyboard layout (embra.kbd=…; us)
EMBRA_VNC=1 EMBRA_KIOSK_MODE=1280x800 ./scripts/run-qemu.sh   # the display console's video mode (embra.kioskmode=…;
                                                     # 1920x1080 where the display offers it; native = the display's own)

# The clock: the OS asks a time server at boot, before any service starts, and every hour after it
# (time.cloudflare.com under QEMU, whose DHCP server names no time server)
EMBRA_NTP=off ./scripts/run-qemu.sh                  # ask none in this boot (embra.ntp=off); EMBRA_NTP=<host>[:<port>] names the one to ask

# Host-side extras (nothing reaches the OS)
EMBRA_ISO=output/images/embraos.iso ./scripts/run-qemu.sh disk.qcow2   # boot the installer onto a blank qemu-img disk
EMBRA_ISO_AS=usb EMBRA_DISK_IF=ahci ...              # the medium as a USB stick, the target on AHCI (cdrom and virtio by default)
./scripts/run-qemu.sh disk.qcow2                     # the installed disk on its own (an image named *.qcow2 is opened as qcow2)
EMBRA_DHCP_START=10.0.2.200 ./scripts/run-qemu.sh    # QEMU's DHCP leases this address: the banner's second URL
EMBRA_USB_HOST=0bda:c811 ./scripts/run-qemu.sh       # hand a USB device of this host to the VM (a Wi-Fi adapter), by the ids lsusb shows
EMBRA_MEMORY=12G EMBRA_CPUS=8 EMBRA_CPU=host ./scripts/run-qemu.sh   # the VM's memory (4G), processors (4) and processor model (QEMU's own, without AVX)
```

> **The disk boots itself:** the image is a 1 MiB-aligned GPT with the EFI System Partition (GRUB, `grub.cfg`, `grubenv`), two OS slots (`rootfs_a`, `rootfs_b`; each a SquashFS with its own kernel, initramfs, firmware and microcode under `/boot` — slot B is empty until the first OS update), STATE and DATA (the sizes and names in `buildroot/board/embraos/layout.sh`). `run-qemu.sh` boots it through UEFI by default: the `ovmf` package above provides the firmware (`EMBRA_FW_CODE`/`EMBRA_FW_VARS` name another pair; the variable store is copied per run), GRUB's menu shows on this terminal for three seconds and boots slot A, and the `EMBRA_*` knobs above reach the kernel line as one SMBIOS string, of which the menu appends the `embra.*` words, so nothing is typed. A machine's firmware has such a string of its own (a placeholder, the board's name): none of its words reaches the kernel line. The menu also offers Diagnostics (the serial TUI, a boot without the display console, debug logging, database request logging, make a slot the default, boot a slot once, clear the failed marks, the boot state, the command-line knobs — press `e` on an entry, add a knob at the end of its first line, after the title, and boot with Ctrl-x; `embra.tui=1` is the in-OS spelling of `EMBRA_TUI=1`), Update embraOS, Backup and restore, Reboot, Halt and Firmware setup. `EMBRA_BOOT=direct` keeps the old path — the kernel and the initramfs from the host, no firmware and no menu — for a kernel or embra-init change without an image rebuild.

> **Network:** at boot embraOS brings up every network card the kernel has, whatever its name, and asks for a DHCP lease on each (BusyBox `udhcpc`, one client a card; the lease's address and route apply, the resolvers of the card with the best route go into `/etc/resolv.conf`, and the clients keep renewing). The boot waits for a first address for ten seconds at most and goes on without one: a card that appears later, a cable plugged in later and a DHCP server that answers late are taken up when they come (`crates/embrad/src/net.rs`). Under `run-qemu.sh` QEMU's own DHCP server leases `10.0.2.15`. A network without DHCP: `/network static <card> <address>/<prefix> [<gateway>] [dns <server> …]` gives a card an address of its own, and `/network hostname <name>` names the machine; both are answered at the first-boot wizard's first question, on the machine's own display or its serial line ([COMMAND-REFERENCE.md](../OPERATIONS/COMMAND-REFERENCE.md)).

> **Wi-Fi:** a Wi-Fi card is a card like a wired one once it has joined a network. `/network wifi` shows the card, the network it is on and the networks in range; `/network wifi join <name> --key <passphrase>` stores a network (the passphrase is masked while it is typed and never reaches the intelligence; `--open` for a network without one, `--hidden` for one that does not announce its name), and the card joins it within seconds and again at every boot. WPA2 and WPA3 personal and open networks are joined; a company network (802.1X) is not. The drivers of the common card families (Intel, Realtek, Qualcomm Atheros, MediaTek and Ralink, Broadcom) are kernel modules, the only ones this image loads: embrad loads the one a card asks for, with the firmware linux-firmware carries for it (the MediaTek MT7922's from a later release than Buildroot's, pinned by `buildroot/package/embra-mt7922-firmware`: the kernel's driver refuses the file of Buildroot's release), and `embra.wifi=0` on the kernel line loads none. A wired card that has a link carries the traffic when both are up, and a boot that has a stored network and no wired link waits up to twenty-five seconds for the Wi-Fi address. To try a USB Wi-Fi adapter under QEMU, hand it to the VM: `EMBRA_USB_HOST=<vendor>:<product> ./scripts/run-qemu.sh`, with the two ids `lsusb` shows. QEMU needs write access to the device's node under `/dev/bus/usb`, and the host must not be using the adapter. When QEMU may not open the device it starts all the same, without the device and without a word, so on a Linux host the launcher looks for the device first and stops with the udev rule that hands the node to you. An adapter that shows itself as a driver disk when it is plugged in has other ids until it is switched (on an Ubuntu host `usb_modeswitch` does that within a second): the ids to give are the ones `lsusb` shows afterwards. Which cards come up is the pinned kernel's to decide (6.18): its driver must know the card's chip and its ids, and for a card it does not know the boot says nothing and `/network` shows no Wi-Fi card. The USB adapters on the Realtek RTL8852AU (AX1800) are driven by eighteen upstream commits that the build puts onto the pinned kernel (`buildroot/patches/linux`): the kernel's driver for that chip over USB came with 6.19, and the id of one such adapter (`3625:010d`) with 7.0. A USB adapter's radio is slow through QEMU's pass-through, where every register of the chip is a transfer the hypervisor carries: that adapter takes half a minute to come up there, and as long again before each scan while it is idle. `/network wifi` then says that the radio is busy or that the scan has not ended, and shows the list when it is asked again; the wired card's lease and the web console do not wait for it.

> **The web console's certificate:** on a bridged network or a real host the banner prints one more console URL for every address the machine holds, beside the `localhost` one (the certificate names each of those addresses, `localhost` and the machine's name, and follows them when they change; a public address and a name with a domain are not on it). The certificate is signed by a CA the machine made for itself, so a browser warns until that CA's certificate is imported once: `/network` shows the names and the route, `/api/ca.crt`, a download in the web console; with it imported the console opens without a warning at every name on the certificate. `/network hostname <name>` puts a name of your own on the certificate. A CA that limits the names it signs (every CA made by v0.23.0 or later) is issued again to admit the name, so a browser that had the CA imports it once more, and under such a CA a name a DHCP server assigns is not put on the certificate. A CA from before v0.23.0 has no such limits: it is left as it is, and the certificate carries the machine's name whoever gave it. A machine installed with v0.23.0 or v0.24.0 has its CA issued again once, with its key, at the first boot of v0.25.0 or later: a copy of the old CA certificate that was imported anywhere is replaced with the new one. To see the banner's second URL in QEMU: `EMBRA_DHCP_START=10.0.2.200 ./scripts/run-qemu.sh` leases `10.0.2.200`.

> **The display:** the kernel line names the display (`console=tty0`) before the serial line, and every boot message of embra-init and embrad goes to both, so a hypervisor with a display shows GRUB's menu, the boot log, the banner with the console URL and the reason a boot stopped there too (once the web console or the serial TUI is up embrad logs to a file; the serial TUI itself stays on the serial line); `run-qemu.sh` keeps the serial line on this terminal, and `EMBRA_VNC=1` adds the display on a VNC server at `127.0.0.1:5900` (password `embraos`, loopback only, so tunnel it with `ssh -L`; macOS Screen Sharing needs the password).

> **The display console:** on a machine with a display the display is a console of its own: once embra-web is up, embraOS renders the web console there (WPE WebKit through cog's DRM platform, drawn in software; keyboard and mouse through libinput) — the same console a browser reaches at the URL, one session shared under the same writer-and-observers rule, the display the first writer at boot; `embra.kiosk=0` on the kernel line (`EMBRA_KIOSK=0`, or GRUB's Diagnostics) boots without it. On the display the right mouse button opens the console's own menu, Copy and Paste: the clipboard is the display's own, so what is copied there is pasted there (the terminal's selection, or the page's; into the terminal while the display is the writer, or into a text field of the page), and a browser on another machine keeps its own menu and clipboard. The menu's last entry, This console's URL, shows the banner's URL with the access token again, for a browser on another machine: the display console covers the banner's copy, and the web console gives the URL to the machine's own display and to no other browser. A dropdown in one of the sidebar's forms opens on the display as it does in a browser: the launcher draws no list there, so the page draws it under the box, for a click or for the keyboard (the arrow keys, Home, End or a first letter move the mark, Enter or Space picks, Escape closes the list and leaves the form). What needs a file of yours, or hands one over, is done from a browser on another machine, and the display says so and shows this console's URL: the Attach button, a backup's upload, a click on a download row. A file the intelligence offers is one line in the terminal there, which interrupts nothing. A message of the page (a required field left empty) is shown on the display too, where the launcher has no dialog for it.

> **The display console's mode:** the display console asks for 1920x1080 wherever the display offers it, the width that holds the status row on one line: GRUB puts `video=efifb:1920x1080` on the kernel line for the firmware's framebuffer, and embrad names the mode to cog for a display with a driver of its own (QEMU's VGA and virtio-gpu, Hyper-V). `embra.kioskmode=<width>x<height>` (`EMBRA_KIOSK_MODE=`) asks for another mode and `embra.kioskmode=native` for the display's own; a mode the display does not offer leaves the display's own. A display the kernel drives through a graphics driver (on x86_64 Intel's i915, AMD's amdgpu, and radeon for the Radeons from before it) offers the modes of the display itself; on the firmware's framebuffer (a machine without such a driver) there is the one mode the firmware left. `nomodeset` on the kernel line keeps the firmware's framebuffer in place of the driver, which is the way back from a display that stays dark after GRUB's menu: `e` on the entry, the word at the end of its first line, then Ctrl-x. On a machine with more than one graphics card the display console is on the first card that has a display connected. On a laptop with two graphics cards, a Radeon that drives no display is powered off by its driver five seconds after its last use, where the laptop's firmware offers the kernel the switch for it. The mode is set once, at boot: a VM window resized later does not change it. The page is drawn at twice its size on a mode 2560 pixels wide or wider, and `embra.kioskscale=1` or `embra.kioskscale=2` on the kernel line sets the scale for a boot whatever the mode (at 2 on 1920x1080 the status row takes two lines); any other value leaves the scale to the mode. The commands for a display window under QEMU on a Mac are in [AARCH64-BUILD.md](AARCH64-BUILD.md) and [INTEL-MAC-BUILD.md](INTEL-MAC-BUILD.md). QEMU's `ramfb` comes up at 800x600 on either architecture: edk2's driver for it offers 640x480, 800x600 and 1024x768 and starts in the second, so the request for 1920x1080 leaves it there, and `embra.kioskmode=1024x768` asks for its largest. A click, a modifier key that is released with its key, the display console on Hyper-V and its choice of a card on a machine with several rest on patches the build carries on cog (`buildroot/patches/cog/`; [OPEN-PROBLEMS.md](../OPEN-PROBLEMS.md)).

> **Drivers and firmware:** the image carries the drivers other hypervisors present — AHCI, IDE, NVMe, virtio-scsi, e1000/e1000e, vmxnet3, pvscsi (the OVA's controller; QEMU's OVMF cannot boot from it), VMware's LSI Logic Parallel and SAS controllers — and Hyper-V's synthetic devices (a generation 2 VM with Secure Boot off). For bare metal it carries the wired NICs of servers and desktops with their USB cousins, the RAID and SAS controllers, SD/eMMC, NVMe behind Intel's VMD, laptop touchpads and touch panels, the TPM and the temperature sensors, every driver built in ([SYSTEM-DESIGN.md](../SYSTEM-DESIGN.md) lists them by group), with every linux-firmware family on the rootfs and the CPU microcode loaded early (the kernel's log names the revision that runs: ask the intelligence for `system_logs` with `service: kernel` and `filter: microcode`). What has been run on which hypervisor and machine is in [VALIDATION-STATUS.md](../VALIDATION-STATUS.md).

> **The clock:** the kernel takes the time from the machine's hardware clock and reads it as UTC; embrad corrects it at boot, before any service starts, and checks it again while the OS runs (`crates/embrad/src/clock.rs`). A clock that reads earlier than the image's build time (`BUILT` in `/etc/embraos-release`) has certainly lost its time — a board whose clock battery ran down wakes at its firmware's default date — and resumes first from the last time the machine saved, or from the build time on a machine that never saved one; the boot log says what it read. The saved time is the clock itself, which embrad writes to STATE once a minute while the services run and once more when the machine is stopped (`/embra/state/last-known-time`; no snapshot holds it and a restore leaves it in place), so a board with a dead battery that boots without a network starts where it left off, behind by as long as it was off, and not at the build time again. A hardware clock at or after the build time is taken as it is, whatever was saved: the date set in the firmware is never overruled. Then, with the network up, embrad asks a time server, by SNTP on UDP port 123 — one request per address of a name, three addresses at most, a request carrying nothing of the machine — with a wait of five seconds at most. It asks the time servers the DHCP lease names (option 42, two of them at most) and then `time.cloudflare.com`, so a network that lets no outside time server through and announces its own needs no setting. `/network time <server> …` stores the operator's own servers, which are then asked and no other; `/network time off` asks none and `/network time default` goes back ([COMMAND-REFERENCE.md](../OPERATIONS/COMMAND-REFERENCE.md)). `embra.ntp=<host>[:<port>]` on the kernel line names the one server of its boot and `embra.ntp=off` asks none in it (`EMBRA_NTP` under `run-qemu.sh`; on an installed machine a knob is typed at the end of a menu entry's first line in GRUB's editor, at each boot). An answer sets the clock, and the hardware clock as well when that was a second or more off, so the next boot starts right without a network; an answer earlier than the image's build time is refused. While the OS runs embrad asks again: every hour, a quarter of an hour after a check that came to nothing or after an answer more than a quarter of a second off, and within seconds when a card gets an address, a link comes back or other time servers are stored. A difference under half a second is slewed (the clock runs 0.5 ms a second fast or slow until it is made up, and no reading goes backwards); a larger one is stepped and the hardware clock written. Once a time server has set the clock in a boot, an answer more than fifteen minutes away from it is not applied: it is recorded, `/network time` and `system_status` say so, and the next boot decides; a boot that got no answer takes its first one whole. `/network time` shows the clock, the last check and the servers. When no time server answered and the clock is still the saved time or the build time, the banner says so in two lines: certificates are checked against the clock, one that begins later is refused, and the fix is the date in the machine's firmware setup, in UTC, or a network where a time server answers: the clock is set when one does. The answer is not authenticated ([OPEN-PROBLEMS.md](../OPEN-PROBLEMS.md)). The default is not a `pool.ntp.org` name: the NTP Pool's rules forbid its zone names as the default of a distributed system without a vendor zone, and embraOS has none.

> **Native models (experimental):** the image carries a model server (llama.cpp's), and a model can run on the machine itself: the first-boot wizard's third answer, or `/native` in a session ([OPERATIONS/NATIVE-MODELS.md](../OPERATIONS/NATIVE-MODELS.md)). No model's file is in the image: one is downloaded at the operator's request, to DATA. Under QEMU give the VM the memory and the processor for it, `EMBRA_MEMORY=12G EMBRA_CPUS=8 EMBRA_CPU=host ./scripts/run-qemu.sh`: the launcher's 4 GiB hold neither model at the default context window, and QEMU's own processor model has no AVX, without which a model reads a prompt several times slower. `embra.native=0` on the kernel line starts no model server in that boot.

> **Install on bare metal:** `output/images/embraos.iso`, or a release's `embraos-<tag>-x86_64-<engine>.iso` from GitHub Releases (checked with its `.sha256` line and the signature beside it, [UPDATES-AND-BACKUPS.md](../OPERATIONS/UPDATES-AND-BACKUPS.md)), boots on UEFI firmware (Secure Boot off) from a DVD or a USB stick (`dd if=output/images/embraos.iso of=/dev/sdX bs=4M status=progress` and `sync`). Its menu installs on both consoles, the serial line or the display alone. The installer first shows what embraOS is licensed under and asks: `accept` goes on, `license` shows the whole text a screen at a time and asks again, and any other answer reboots without installing, with nothing changed (the text is the file `LICENSE` at the medium's root, and the repository's). Then it lists the machine's disks, asks for a number and then the disk's name, and writes the image's layout to it — the EFI System Partition, slot A with this build, an empty slot B, STATE, and DATA to the end of the disk — then asks for the medium to be removed and reboots into GRUB's menu from the new disk. Everything on the chosen disk is erased; the other disks are not touched; the firmware boots the ESP's removable-media path, so no NVRAM entry is written. A disk that grows later (a VM's virtual disk enlarged in the hypervisor) is taken up at the next boot: when a gibibyte or more follows DATA, embrad grows the partition and the filesystem to the disk's end before the services start, and says so on both consoles. The aarch64 build writes the same medium for its architecture ([AARCH64-BUILD.md](AARCH64-BUILD.md)).

> **Upgrade an installed disk from the medium:** when the disk the installer is pointed at already holds an embraOS installation, the installer asks about the licence as it does before a clean install (the medium may carry a later text than the installation's), then says what each slot holds and asks `Upgrade in place or clean install? [u/c, q = reboot without installing]`, with no default. `c` is the clean install above, the disk's name typed as its confirmation. `u`, confirmed with `y`, upgrades in place: the medium's OS is written into the slot that is not the default and verified, GRUB's loader and `grub.cfg` on the EFI System Partition are replaced with the medium's (`grubenv` stays), and the slot is staged as an OS update stages one. The partition table, STATE and DATA are not written, so the identity, the memories, the knowledge graph and the workspace stay; the next boot is a trial of the new slot, with a snapshot taken first and the slot before it as the fallback ([UPDATES-AND-BACKUPS.md](../OPERATIONS/UPDATES-AND-BACKUPS.md)). The upgrade is offered for a medium newer than the installed release and for another build of the same version, which its confirmation says. It is refused, with its reason and the clean install still at hand, for a medium older than the installed release (`embra.downgrade=1` on the installer's kernel line allows it), for the build the disk already holds, for another architecture or storage engine, for an image larger than the disk's slots, and when the default slot lacks a file the medium's boot menu reads from a slot. `embra.upgrade=<disk>` on the kernel line runs the upgrade unattended and never becomes a clean install; `embra.install=<disk>` stays the unattended clean install and erases an installation. An unattended run asks nothing, so it needs the licence accepted on the same line, `embra.license=accept`: without it the installer refuses, names the knob and changes nothing.

> **Parallels Desktop (Intel Mac):** Parallels takes the build as a machine, not as a disk: it runs no machine from a bare VMDK and opens no OVA, and a VMware machine it converts whole. `output/images/parallels/` holds that machine, `embraos.vmx` beside a copy of the VMDK — the name embraOS, EFI with Secure Boot off, the disk on SATA, a USB controller, 4096 MiB, the guest type Linux — and Parallels converts the pair into a machine of its own:
>
> ```bash
> cd output/images/parallels
> prl_convert embraos.vmx --dst="$HOME/Parallels" --reg=n --allow-no-os --no-reconfig
> prlctl register "$HOME/Parallels/embraOS.pvm"      # the machine is in Parallels' list from here on
> ```
>
> Parallels Desktop 26.5.0's converter stops without `--dst`, and its own registration registers the machine and then ends in an error, which is why the destination is named and the registration is a command of its own. From Parallels' window the same import is New… (or the + button), then Open… and `embraos.vmx`. The converter gives the machine two vCPUs whatever the file asks (`prlctl set embraOS --cpus 4` afterwards) and, the type being Linux, Parallels' virtio network and display adapters, on which the display console comes up at 1920x1080. The installer is the other way in: a machine created for `embraos.iso` needs UEFI (`prlctl set "<VM name>" --efi-boot on`) and Secure Boot off (the boot flag `vm.efi.secureboot=0`, under Boot Order → Advanced in the machine's configuration). On Apple Silicon the aarch64 build writes the same pair, its `embraos.vmx` naming VMware's Arm guest type. Parallels' own list of what Apple silicon Macs do not support ([KB 128914](https://kb.parallels.com/en/128914)) names the import of VMware machines, so the import may be refused there; that build's installer medium ([AARCH64-BUILD.md](AARCH64-BUILD.md)) is the other way in.

> **Storage engine:** The `--storage-engine` flag is required and is baked into the embrad binary at build time. WardSONDB locks the choice into the DATA partition on first boot via a `.engine` marker file — switching engines later requires wiping DATA.

> **A Buildroot tree from before `v0.24.0-phase2`:** Buildroot never rebuilds a package whose options changed. On a tree that built the image before the display console, run `make util-linux-libs-dirclean util-linux-dirclean mesa3d-dirclean eudev-dirclean` in `buildroot-src` once (e2fsprogs needs the libuuid that the older util-linux build left out; Mesa and eudev take their new options), then build as usual. A fresh tree needs nothing. A patch added or changed under `buildroot/patches/` needs no step either: the image scripts clean its package before `make`.

> **Buildroot version:** `2026.02.1` (LTS), and the tree builds on that release alone. The firmware check compares the 134 `linux-firmware` families the tree selects with the release's own list, the defconfigs name its 6.18 kernel-headers series, and the patches under `buildroot/patches/` are written for its cog, Mesa and libpsl (those under `buildroot/patches/linux/` are for the pinned kernel, whatever the Buildroot release). `BUILDROOT_VERSION` names another checkout — the script switches `buildroot-src` to it and wipes `output/` — for a port to a newer release. An older one does not build this image: 2024.02 offers 110 families and has no 6.18 headers series.

> **Linux kernel:** The image runs a pinned kernel from the 6.18 longterm line (`6.18.60`, supported upstream to the end of 2028), not Buildroot's own "latest": Buildroot 2026.02's latest is the 6.19 series, which is end of life and was never fixed for CVE-2026-98432. The version is named in three places that the scripts check against each other — `LINUX_KERNEL_VERSION` in `scripts/lib/image-common.sh`, `BR2_LINUX_KERNEL_CUSTOM_VERSION_VALUE` in both defconfigs (with the headers series `BR2_PACKAGE_HOST_LINUX_HEADERS_CUSTOM_6_18`, which follows the first two digits), and the hash line in `scripts/linux-kernel.sha256`. Buildroot checks no hash for a custom kernel version, so Step 4 downloads `linux-<version>.tar.xz` from `cdn.kernel.org` into `buildroot-src/dl/linux/` and verifies it against the pinned line (kernel.org's own, from the signed `sha256sums.asc`) before Buildroot unpacks it; a tarball that does not match is removed and the build stops. To move the kernel: set the three places, take the new line from `https://cdn.kernel.org/pub/linux/kernel/v6.x/sha256sums.asc`, rebuild both architectures. The kernel is built with the patches under `buildroot/patches/linux`: upstream commits newer than the pinned line, each naming its own (today the eighteen that bring the RTL8852AU over USB). A patch the pinned line has taken since no longer applies and stops the build: it is removed then; `CONFIG_RTW89_8852AU=m` in the fragment is read back, so a kernel built without them stops it as well. `KERNEL_MIRROR` overrides the download base. The QEMU scripts boot with `quiet`, which keeps the kernel's own `Linux version` banner off the serial console; the running kernel is named by `system_status` (`kernel`), `/status` and `uptime_report` (`Kernel:`). Every frequency policy starts under `performance` (the shared kernel fragment): a core that is awake runs at the top of its range, on a CPU that is handed a frequency and on one that governs itself with hardware P-states alike; an idle core sleeps as before, and the kernel's thermal limits still lower the ceiling. A CPU that Intel's idle driver has a table for sleeps by the kernel's own idle states for the model (the x86_64 kernel fragment); any other machine keeps the states its firmware declares. The aarch64 kernel builds in the five frequency drivers its base configuration leaves as modules, since the image loads no module but a wireless driver: the Raspberry Pi's (a board started with a device tree), ACPI's CPPC (a machine whose tables declare `_CPC`), and three of single chip families (Allwinner's, NXP's for the i.MX 8M, and MediaTek's for the chips that change frequency through a hardware engine).

> **CPU microcode:** Intel's microcode bundle is pinned by a recipe of its own, `buildroot/package/embra-intel-microcode`: the version in `embra-intel-microcode.mk` (`20261110`) and the archive's sha256 in `embra-intel-microcode.hash`. Buildroot's own `intel-microcode` package names one release per Buildroot version (2026.02.1: `20260210-rev1`) and is not selected. Buildroot downloads the archive of Intel's tag from GitHub and stops the build when its sha256 is not the pinned one or the hash file has no line for it; the recipe writes `intel-ucode` in the images directory whole and installs Intel's licence under `/usr/share/licenses/intel-microcode`, and the build's checks refuse an image whose `/boot/ucode.cpio` or licence is not that bundle's. To move the bundle: set the version, put the sha256 of the archive of Intel's tag `microcode-<version>` on the hash file's line (and the licence's, when the text changed), compare the two bundles' `intel-ucode` directories, rebuild. AMD's microcode comes with linux-firmware.

> **Wi-Fi firmware, MediaTek MT7922:** the card's firmware and its ROM patch are pinned by a recipe of their own, `buildroot/package/embra-mt7922-firmware`: a release tag of linux-firmware in `embra-mt7922-firmware.mk` (`20261019`) and the sha256 of the two files and of MediaTek's licence text in `embra-mt7922-firmware.hash`. The linux-firmware release Buildroot 2026.02 carries (`20251011`) has a file for this card whose power table the kernel's driver refuses: the card is found, its driver loads, and no interface comes up. Buildroot downloads the three files from linux-firmware's repository on gitlab.com at that tag, stops the build when a sha256 is not the pinned one, and installs the two files over the ones of its own linux-firmware package; the build's checks refuse an image whose two files are not the pinned ones or whose licence text is not that release's, and walk the power table of every firmware of that driver's family (MT7920, MT7921, MT7922) the way the driver does. To move it: set the tag, put the three sha256 on the hash file's lines, rebuild. The recipe goes when Buildroot's linux-firmware is `20251021` or later.

> **In-OS Rust toolchain:** Guardian dynamic tools compile inside the image, so `build-image.sh` Step 3.5 downloads a pinned toolchain (musl host + `wasm32` std, SHA-256-verified against the pins in `scripts/rust-toolchain.sha256`) from `static.rust-lang.org`, caches it under `vendor/rust-toolchain`, and bakes it into the rootfs at `/opt/rust`. The first build needs network for this. The toolchain and the firmware are the two largest items in the image: the toolchain is about 320 MiB of a root filesystem of about 920 MiB, as compressed in the SquashFS (the firmware, the Wi-Fi cards' included, is about 310 MiB of that, and the copy of the built-in drivers' blobs in the boot archive about 40 MiB more; the wireless drivers are under 5 MiB and the display console's stack about 90 MiB) (measured on x86_64). The pin is `1.98.1` — the same version as the host compiler in `rust-toolchain.toml`, but a separate setting (the pins, the download check and the post-Buildroot checks of the root filesystem live in `scripts/lib/image-common.sh`, which both image scripts source); to move it, set `RUST_TOOLCHAIN_VERSION` and add the new version's three hash lines to `scripts/rust-toolchain.sha256` (the `xz_hash` values of the channel manifest); a version without its lines stops the build at the download check. The brain loads a Guardian tool only when it was built by the toolchain the image carries, so an image with a different pin leaves the existing tools unloaded (`/guardian list` marks them `NOT LOADED`) until the operator runs `/guardian rebuild --all`.

> **Three tools ship ready:** the image carries the prompt-injection-hardened `web_search` Guardian tool, `http_request`, a guarded curl for pages, resources and API work, and `websocket`, a client whose connections stay open between calls, and the brain builds them at boot. `web_search` stays inert until you set a Brave Search key with `/guardian key brave <token>` ([GUARDIAN-ADVANCED-EXAMPLE.md](../GUARDIAN/GUARDIAN-ADVANCED-EXAMPLE.md)). `http_request` needs no key: a credential for a host goes in with `/guardian secret <host> <header> <value>` and is injected host-side, and a private host is admitted with `/guardian egress allow <host>` ([GUARDIAN-HTTP-REQUEST-EXAMPLE.md](../GUARDIAN/GUARDIAN-HTTP-REQUEST-EXAMPLE.md)). `websocket` takes the same two commands, the credential on its handshake, and `/guardian connections` lists and closes what it holds open ([GUARDIAN-WEBSOCKET-EXAMPLE.md](../GUARDIAN/GUARDIAN-WEBSOCKET-EXAMPLE.md)).

> **Embedding model:** Semantic knowledge-graph retrieval runs in-process, so `build-image.sh` **Step 3.6** downloads `BAAI/bge-small-en-v1.5` (~133 MB, SHA-256-verified against a pin), caches it under `vendor/embedding-model`, and bakes it into the rootfs at `/usr/share/embra/models/`. Like the toolchain above, the first build needs network for it; later builds skip the download when the cached copy still matches the pin. The build **fails** if the model is missing from the rootfs rather than shipping an image whose retrieval silently falls back to keyword-only. Operators can override the baked copy per instance by seeding `/embra/state/models/<name>` on STATE.

> **Lockfiles:** The image scripts build with `--locked` (`trunk build` in Step 0.5, `cargo build` in Step 1), so an image is always built from the committed `Cargo.lock` and `crates/embra-web-ui/Cargo.lock`. After a dependency change, update and commit the lockfile first — a lock that no longer matches its manifest stops the build instead of being re-resolved.

> **Source paths:** a panic's location and some log lines name a source file, and a program would otherwise carry the full path it was compiled under: the builder's home directory, several thousand times across the image. The image scripts hand the compiler a stand-in for each directory of the build host (`scripts/lib/build-paths.sh`): a crate from the registry reads `/cargo/registry/src/…/<crate>-<version>/…`, the checkout `/embraOS/…`, the compiler's own files `/rustup/…`, anything else under the builder's home `/builder/…`. After the cross-build the scripts read every program and the web console's bundle back and stop on one that names a directory of the host; after Buildroot they read the whole root filesystem the same way, from which `post_build.sh` has removed the records of the build that nothing reads at run time (the in-OS toolchain's install log and manifests, ICU's build tools, two helper scripts). Buildroot's own directory lies under the builder's home on a Linux host, and three of its packages would compile it in: sqlite's shell and WebKit's library are handed a stand-in for it (`/buildroot`, in `buildroot/external.mk`), and libpsl's table is written without the name of the list it was made from (`buildroot/patches/libpsl`). A tree that built one of them before that builds it again, once: the scripts find it in the target directory the last build left. WebKit is one of the three, and its build is the longest of the image. A Mac build runs Buildroot in a container, where its directory is `/work/buildroot-src` on every Mac: the scripts build nothing again for that name, and a volume that compiled sqlite and WebKit before the stand-in keeps it in sqlite's shell and in WebKit's library. The kernel's banner (the first line of its log, `/proc/version`) would name the login and the host that built it; its build is told `embraos` for both, and a kernel built before that is linked again. Cargo takes the stand-ins from the environment (`CARGO_ENCODED_RUSTFLAGS`), which it reads in place of a configuration file's `rustflags`: a builder's own `RUSTFLAGS` are kept in front of them, and flags kept in a cargo configuration for the musl target go into `RUSTFLAGS` for an image build.

> **Build overrides:** `build-image.sh` reads a few environment knobs — `JOBS` (Buildroot parallelism, default all cores: the make-based packages take it through make's jobserver, the cmake ones, WebKit and LLVM, as `BR2_JLEVEL`; lower it on a memory-constrained host, since WebKit's compile wants about 3.5 GiB per job, the figures in [AARCH64-BUILD.md](AARCH64-BUILD.md)), `MUSL_CROSS` (musl toolchain root, default `/opt/x86_64-linux-musl-cross`), `BUILDROOT_DIR` (default `buildroot-src`), the `BUILDROOT_VERSION`, `LINUX_KERNEL_VERSION` and `RUST_TOOLCHAIN_VERSION` pins above (the kernel's and the toolchain's move with their hash lines, as their notes say: the value alone stops the build), and `RUST_DIST_BASE` / `KERNEL_MIRROR` / `EMBED_BASE` (mirror bases for the Step 3.5 toolchain, the Step 4a kernel and the Step 3.6 model downloads). Prefix the command: `JOBS=4 ./scripts/build-image.sh --storage-engine rocksdb`.

On first boot, the Config Wizard runs — it first shows what embraOS is licensed under and asks, with three choices and no default: the first accepts nothing (the setup waits at the question, and the console is free for `/license`, `/reboot` and `/backup`), the second shows the whole text, and the third accepts, which is recorded on STATE (`/license` shows the text at any time). Then name your intelligence, say whether the providers are reached directly, through WSDS Local AI Gateway (its unified listener must identify itself; [OPERATIONS/LOCAL-AI-GATEWAY.md](../OPERATIONS/LOCAL-AI-GATEWAY.md)) or not at all, with a model that runs natively on this machine (experimental; [OPERATIONS/NATIVE-MODELS.md](../OPERATIONS/NATIVE-MODELS.md)), choose your LLM provider (Anthropic Claude, Google Gemini, Ollama, or LM Studio), enter the corresponding credentials (API key for Anthropic/Gemini; endpoint URL + optional bearer + selected model for the OpenAI-compat presets), set your timezone. The native answer has no provider and no key: it asks which model, downloads its file when it is not on the machine, and that model leads Learning Mode. Each field is validated before commit — an invalid API key, unreachable endpoint, or garbage timezone re-prompts instead of persisting. Nothing is stored before the wizard's last question is confirmed: a console that disconnects earlier (a tab closed, a phone that locks) leaves nothing behind, and the next console starts at the first question. The Ollama / LM Studio sub-flow probes `GET /v1/models` against your endpoint, or through the gateway's `/ollama` or `/lmstudio` prefix when one was given (the endpoint may then be `none`), and presents a model selector populated from the live server response. After setup, you're in a full TUI conversation with styled text, thinking indicators, and tool execution.

> **After the soul is sealed, run `/embeddings backfill` once.** The seed knowledge packs load at first boot, before the Config Wizard has written a configuration, so their nodes carry no vectors and semantic similarity cannot find them. Nothing embeds them later on its own. The backfill runs locally (about 55 ms per node) and `/embeddings` shows the coverage before and after.

### Notes

The following apply once the image is built. They are not part of the build pipeline.

> **Terminal Size (serial TUI only):** With `EMBRA_TUI=1`, `run-qemu.sh` reads your terminal size once (`stty size`) and passes it to the guest on the kernel command line (`embra.cols`/`embra.rows`) — maximize the terminal before launching; resizing it afterwards does not update the TUI layout. The web console has no such limit: it follows the browser window.

> **Image Search Order:** `run-qemu.sh` (and `run-qemu-aarch64.sh`) resolves the disk image in this order — the same precedence `seed-state.sh` and `embraos-backup.sh` use, so the image you seed or back up is the one you boot:
> 1. Explicit path passed as the argument: `./scripts/run-qemu.sh /path/to/embraos.img`
> 2. `$EMBRAOS_IMAGE` — the escape hatch when a stale `buildroot-src/` shadows a newer image
> 3. `buildroot-src/output/images/embraos.img` (Buildroot output, always freshest)
> 4. `output/images/embraos.img` (alternative output location)
>
> On the direct path (`EMBRA_BOOT=direct`) the kernel (`bzImage`) is looked for beside the image first, then in the two default locations, and the initramfs is always `./initramfs.cpio.gz`; the UEFI path loads both from the slot inside the image. The default paths are relative to the current directory — run the script from the repository root.

> **Clean First Boot:** To reset and trigger the Config Wizard again (e.g., to change API key):
> ```bash
> ./scripts/seed-state.sh --wipe state,data       # macOS: ./scripts/seed-state-mac.sh
> ```
> Reformats the named partitions in place as ext4 with their original labels, after a
> typed confirmation. Wiping STATE destroys the soul hash, PKI, API keys, the network's settings with the stored Wi-Fi networks and the web console's access token; wiping DATA
> destroys WardSONDB — all memory, sessions, the workspace and the in-OS backups under
> `/embra/data/backups`. Neither is reversible, and
> the VM must be stopped. `--wipe data` alone also removes STATE's `soul.sha256`: a sealed
> hash with no soul document halts the next boot (the tamper check), and a wiped DATA is
> meant to start over.
>
> Use `--wipe state` or `--wipe data` to reset just one (`--wipe all` = `state,data`), `--yes` to skip the prompt, and
> combine with the seeding flags to reset and re-seed in a single pass:
> ```bash
> ./scripts/seed-state.sh --wipe state,data --ca-dir /path/to/dir-with-rootCA.pem
> ```
> Partition geometry is read from the GPT at run time, so this stays correct as partitions
> shift between builds.

> **Halted boot:** embrad (PID 1) never exits. A failed soul verification, a fatal boot error (a partition that does not mount, a service that cannot start) or a panic in embrad halts the machine and writes the reason to `/embra/state/halt_reason` on STATE. After the next boot, ask the intelligence to read `/embra/state/halt_reason` (`file_read` reaches that file; the rest of STATE is refused to the tools, except three more plain files that hold no secret and the operator's drop-in directories). When the machine does not boot at all, stop the VM and take a backup — `sudo ./scripts/embraos-backup.sh backup --label halted` — and read `state/halt_reason` in it under `~/embraOS_BACKUPS/<timestamp>_halted/`.

> **Port Forwarding:** QEMU forwards 8443 (REST) on the host's loopback only, and 3345 (the HTTPS web console — https://localhost:3345/embraOS, behind the console's access token) on every host interface, in both UI modes; only the launch banner differs. The gRPC ports (50000 to 50002), the database's (8090) and the model server's (8091, there while a native model is kept loaded; experimental) bind the machine's loopback and are not forwarded. Other machines on the host's network reach the web console and nothing else, and only with the URL embraOS printed at boot; the per-port table is in [SYSTEM-DESIGN.md](../SYSTEM-DESIGN.md#network-exposure). apid's REST surface is `/health`, `/version` and `/status` — `/status` proxies the brain's `GetSystemStatus` (2-second timeout, HTTP 503 while the brain is away) and carries the active LLM provider's last endpoint probe as `llm-provider` / `llm-provider.detail`. Test with:
> ```bash
> curl http://localhost:8443/health
> curl http://localhost:8443/status
> ```

> **OS updates:** the image carries two OS slots; `/update` fetches a release's signed manifest from the GitHub releases, `/update apply` writes the release into the inactive slot and GRUB tries it at the next boot, falling back if it does not come up ([OPERATIONS/UPDATES-AND-BACKUPS.md](../OPERATIONS/UPDATES-AND-BACKUPS.md)). `scripts/release-update.sh` prepares and signs a release's artifacts; `scripts/update-signing.pub` holds the keys the image trusts (the operator's release signing key; several keys may sit there across a rotation).

> **Backup & Restore:** the OS takes its own backups too — `/backup create` in a session or the boot menu's Backup and restore, snapshots under `/embra/data/backups` that the web console streams to the browser and takes back as an upload ([OPERATIONS/UPDATES-AND-BACKUPS.md](../OPERATIONS/UPDATES-AND-BACKUPS.md)). An install starts with empty STATE and DATA: a backup downloaded before it is uploaded through the web console after the first boot and restored with `/backup restore <name>` and `/reboot now`, which are answered at the first-boot wizard too, or from the boot menu. The host script below is the path across an image rebuild and off the machine. Its copy of DATA leaves out the OS's own snapshots (`backups/`) and the files of the native models (`models/`, experimental), both at DATA's root alone: a directory of either name inside the workspace is copied like any other. Its copy of STATE leaves out what belongs to the machine and to no backup, as the OS's own snapshot does: the web console's access token and the saved clock. A restore leaves all four as the image has them, so a rebuilt image makes a token of its own and the console's URL changes with it, and the snapshots the OS took on an image are still there after a restore from the host; the rest of STATE and of DATA is replaced. `embraos-backup.sh self-test` checks both rules on scratch directories, without root. `scripts/embraos-backup.sh` preserves STATE and DATA partitions across image rebuilds. This is a file-level backup — WardSONDB does not need to be running. The VM must be stopped.
> ```bash
> # Before rebuilding the image
> sudo ./scripts/embraos-backup.sh backup --label pre-rebuild   # or a bare label: backup pre-rebuild
>
> # After rebuilding — latest backup, or restore <name> for a specific one
> sudo ./scripts/embraos-backup.sh restore
>
> # List available backups
> ./scripts/embraos-backup.sh list
>
> # Verify disk image has valid data
> sudo ./scripts/embraos-backup.sh verify
>
> # Target a specific image (default: the one run-qemu.sh boots)
> sudo ./scripts/embraos-backup.sh --image /path/to/embraos.img verify
> ```
> Backups are stored in `~/embraOS_BACKUPS/` by default — under `sudo` that is still the invoking user's home, resolved from `$SUDO_USER` (override with `EMBRAOS_BACKUP_DIR`). `restore` prints the backup's metadata, asks `Continue? [y/N]`, then empties the image's STATE and DATA partitions before copying the backup in — a fresh image's seed contents are replaced, not merged. Each backup includes STATE (soul hash, PKI certs), DATA (WardSONDB collections, workspace), and metadata with the SHA-256 of the source image and the database engine (`data_engine`). The summary after the copy, and `verify`, describe the database by its `.engine` marker — fjall's collections by name, RocksDB's SST files — and assume neither engine. To target another image pass `--image <path>`; `EMBRAOS_IMAGE` works too, but it must come *after* `sudo` (`sudo EMBRAOS_IMAGE=… ./scripts/embraos-backup.sh …`) — sudo's default `env_reset` drops a variable set before it, and the script would silently back up the default image.
>
> **After restoring onto a rebuilt image:** Guardian dynamic tools are compiled inside the OS, and the brain loads one only if it was built by the toolchain the image carries. When a new image has a different in-OS toolchain, the tools come back `NOT LOADED` (`/guardian list`). `/guardian rebuild --all` builds them again from their stored modules; each passes validation and the replicant check before it compiles.

## Self-hosted git servers (private CA)

To let the git tools reach a self-hosted GitLab/Gitea whose HTTPS certificate chains to a private root CA (e.g. an mkcert development CA), the CA's certificate goes into `/embra/state/ca-certificates/`. On a running machine that is the `/ca` command: `/ca import <url | uploads/<file>>` shows the certificate and `/ca import <source> sha256:<fingerprint>` imports it ([COMMAND-REFERENCE.md](../OPERATIONS/COMMAND-REFERENCE.md)); the git tools and the OS updater trust it after the next boot. From the build host, drop the CA's `*.pem`/`*.crt` file(s) into the directory of a disk image, via:

```bash
./scripts/seed-state.sh --ca-dir /path/to/dir-with-rootCA.pem
# macOS (no losetup/ext4 — runs the same script in a privileged container):
./scripts/seed-state-mac.sh --ca-dir /path/to/dir-with-rootCA.pem
```

The same drop-ins are trusted by the brain's HTTP clients beside the compiled-in roots — the GitLab and GitHub tools, the Guardian transport of `http_get` and `http_request`, the TLS of a Guardian WebSocket connection, and the providers while `/local-ai-gateway` routes them through an HTTPS gateway with its own certificate authority ([OPERATIONS/LOCAL-AI-GATEWAY.md](../OPERATIONS/LOCAL-AI-GATEWAY.md)) — read at the first client a boot builds and again after `/ca import` and `/ca remove`, so a seeded certificate takes effect at the next boot and an imported one at once. One client is the exception: `web_search`'s reaches `api.search.brave.com` on the compiled-in roots alone.

`seed-state.sh` reaches a raw disk image on the build host. A machine installed from the ISO, a hypervisor's converted disk and bare metal have no such step: there a CA is imported with `/ca import` once the machine runs (the first-boot wizard answers the command), or it travels in the image, for a machine that has to trust it from its first boot: drop the same `*.pem`/`*.crt` files into `Imported_CAs/` in the repository root before the build ([Imported_CAs/README.md](../../Imported_CAs/README.md)). The build checks the folder before anything is compiled — a private key, a file that is no PEM certificate and a file the OS would skip each stop it — lists each certificate's subject, SHA-256 fingerprint and expiry, and bakes the files read-only into `/usr/share/embra/ca-certificates/`, which embrad and the brain trust beside STATE's folder from the first boot. The folder's contents are not in git (every push is public), so each build host keeps its own copy. That trust follows the image: a machine updated to an image built without a file no longer trusts that CA, and `scripts/release-update.sh` signs no release from an image that carries any ([UPDATES-AND-BACKUPS.md](../OPERATIONS/UPDATES-AND-BACKUPS.md)).

With no image argument, `seed-state.sh` resolves the same one `run-qemu.sh` boots
(`$EMBRAOS_IMAGE`, then `buildroot-src/output/images/`, then `output/images/`), so you
cannot seed one image and boot another. Pass a path — positional or `--image <path>` — to
override. The VM must be stopped — seeding an image QEMU has open corrupts it, and the
script refuses. `./scripts/seed-state.sh --help` lists every flag. Beyond `--ca-dir`,
`--seed-dir` (your own knowledge packs — the OS's are in the image, and a copy in STATE is ignored), `--import-dir` (intelligence graphs) and `--wipe`:
`--phase0-data <dir>` copies `<dir>/wardsondb/` onto DATA (size-checked first; its `.engine`
marker must match the image's `--storage-engine`), `--soul-hash <hash>` writes STATE's
`soul.sha256`, `--update-key <pem>` copies an Ed25519 public key to STATE's
`update-signing.pub`, a release signing key of your own trusted beside the image's
([UPDATES-AND-BACKUPS.md](../OPERATIONS/UPDATES-AND-BACKUPS.md); `seed-state-mac.sh` takes
the flag as well), and `EMBRAOS_ROOT` re-anchors the default
image paths when the script runs from another directory.

At the next boot, embrad merges the drop-ins with the stock CA bundle (public hosts like github.com keep working) and exports `GIT_SSL_CAINFO`/`SSL_CERT_FILE` for every service, so `git_clone`/`git_push`/`git_pull` trust the server. embrad's line on the serial console names each accepted cert file (`Operator CA trust: merged N cert(s) from M file(s) […]`); it is printed before embrad's log file exists, so `system_logs` does not show it. In a session, the brain's own count is in `system_logs` (`operator CA drop-ins: N certificate(s)`). Scope: the git/OpenSSL path and the OS updater through embrad's bundle, and the brain's HTTP clients as listed above. For private repos, set a per-host token with `/git-token <host> <token>` after boot; the same token authenticates the `gl_*` issue/merge-request tools.
