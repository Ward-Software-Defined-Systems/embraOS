# embraOS — Open Problems

Unresolved design questions tracked at the architecture level rather than as code comments. Each is something that will need a decision during Phase 1–3 implementation. Implementation bugs go in the Embra_Debug tracker — this list is design-state tracking, not defects.

Extracted from `ARCHITECTURE.md` (a local design record, not in the repository) — `### Architectural Tensions (Known Open Problems)` — on 2026-05-23. Wording verbatim. A dated note under an entry says what has happened since; the entry itself is left as it was written.

---

## Module trust escalation

Operator-authored modules start sandboxed. How do they earn broader access? A trust ladder is needed: sandbox → internal-only → governed-egress → full-egress. Each step requires governance approval plus operational history. The ladder design is not yet specified.

**2026-10-03.** The first rungs exist for dynamic tools (`embra-guardian`). A tool runs in a `wasmtime` sandbox with no ambient authority and reaches out only through the host imports it declares: `http_get` (https, public addresses only) and `web_search` (`KNOWN_CAPS` in `crates/embra-guardian/src/abi.rs`; the rules in `caps.rs`). A declaration is granted when the tool passes the replicant check and, for a proposal of the intelligence, the operator's `/guardian approve`; the one tool the image ships (`web_search`) holds its declarations by the project's review, at install. That is approval per definition, not a ladder: nothing is earned from operating history, and there is no internal-only rung — a private or loopback address is refused outright. The ladder is still not specified.

**2026-10-09.** An internal-only rung, by the operator: `/guardian egress allow <host>` admits a private host (a name with its subdomains, or an IP literal) to the `http_get` and `http_request` guards, and a loopback, link-local, multicast or reserved address is refused whatever the list says (`AddressClass` in `caps.rs`). A credential for a host is stored with `/guardian secret` and injected by the host on a matching request only, so a tool holds no secret. Both are still approval per definition; nothing is earned from operating history.

## Resource contention: LLM vs modules

Local LLM inference is resource-intensive. Module containers also need CPU and memory. embrad needs to arbitrate. The Continuity Engine should reason about "more inference capacity" vs "more module capacity" as a scheduling decision — but the scheduling policy is not yet designed.

## Governance latency

Every governed operation goes through embra-guardian. If governance evaluation involves LLM reasoning, this adds latency to the hot path. Proposed dual-path: deterministic rule-engine for hot-path governance (fast), LLM-based evaluation for complex or novel requests (slow but thorough). The threshold between paths is not yet defined.

**2026-10-03.** Dynamic tools settled on the dual path, split by time instead of by request. The evaluation that needs a model, the replicant check, runs when a tool is defined, proposed or rebuilt (`run_replicant_check` in `crates/embra-brain/src/guardian/mod.rs`) and never when it is called. A call meets deterministic limits only: the sandbox's epoch timeout and memory cap, and the capability broker's rules. The threshold between the paths is still undefined for an operation that is governed at the moment it runs, as a proxied MCP call would be.

## WardSONDB as single point of failure

WardSONDB is a core OS service. If it fails, the brain can't read state and the feedback loop halts. Mitigations: WAL-based crash recovery (fjall's built-in durability), read replica for continuity during recovery, snapshot-based restore as last resort. The replica architecture is not yet designed.

**2026-10-03.** Two of the three mitigations exist. Crash recovery is the storage engine's — fjall or rocksdb, chosen when the image is built (`--storage-engine`) — and `embrad` restarts the database with backoff under a burst budget (`crates/embrad/src/supervisor.rs`). Snapshot restore is `scripts/embraos-backup.sh` (`backup`, `restore`, `list`, `verify` of STATE and DATA), a file-level copy taken from the host with the VM stopped. There is still no replica, and no design for one.

**2026-10-24.** The brain's side of a database that is away: its client has a connect timeout and a read-idle timeout (`788a412`), and a read that fails is reported as a failure — an Error frame at a turn, an attach or a `/switch`, a tool reply that says the read failed — never as empty state (`f2e44b9`, `4edd79b`, `af1c8fd`). The brain stays up and says so. The replica is still undesigned.

## Bare metal vs K8s isolation parity

In bare metal mode, module containers share the same kernel as embraOS. In K8s mode, modules run in a separate namespace with network policies. Bare metal needs stronger containerd-level isolation (seccomp, AppArmor/SELinux profiles, user namespaces) to match K8s-level isolation. The seccomp/AppArmor profiles are not yet written.

## Module image provenance

If module source originates inside the OS (operator-authored via Guardian, or — under future governance design — brain-proposed), the provenance chain must be auditable end-to-end: source code → `modules.source` → sandboxed build → image signing → governance review → allowlist → deploy. Each step must be logged and verifiable. The sandboxed build pipeline is not yet designed.

**2026-10-03.** Part of the chain exists for dynamic tools, and the source this entry calls future — a proposal of the intelligence — has existed since `guardian_propose`. The record of a tool (`ToolDoc` in `crates/embra-guardian/src/store.rs`, collection `guardian.tools`) keeps its source and the SHA-256 of it, the verdict of the replicant check with the model that judged and the time, the toolchain version it was built with, and the tail of the build log. A tool has no third-party dependency, so its build runs no code but the compiler's. Not kept: a record of the operator's approval (building a proposal is the approval), a hash or a signature of the built artifact, and a log of each step that can be verified afterwards. Modules as images, with signing and an allowlist, are still not designed.

**2026-10-24.** `/guardian approve` builds a proposal only when its stored source still matches the hash recorded with it (`257ae9b`), and `/guardian show` prints that digest (`d23b48a`), so the approval is bound to the source the operator saw.

## Does the auto-derived edge layer still earn its cost?

Opened 2026-09-08, when retrieval's graph-expansion step was deleted. `same_session`, `temporal` and `tag_overlap` account for **405,429 of production's 408,046 edges (99.36%)**, growing ~1.7x faster than the node layer (edges +44.5% against nodes +26% over 19 days), and 21% of sampled nodes now exceed the 500-edge auto window — up from 10.8% a month earlier.

That layer's headline justification was per-turn depth-2 expansion during retrieval: density was the substrate expansion needed to find adjacent nodes. Measurement retired that argument. Expansion reached a 1,000-node slab (42% of the graph) that was 97.7–99.6% auto-reached, cost ~96% of retrieval latency, and contributed **nothing** to the injected top-20 on any query tested.

What remains is `knowledge_traverse`, which the intelligence invokes deliberately rather than on every turn — and the control case is instructive: identity nodes carry no auto edges, and a traversal from one is **100% meaningful**. The graph is useful exactly where the auto layer does not drown it.

Options, none taken: decay `same_session`/`temporal` weights with age and prune below a floor; stop double-writing auto edges; cap per-node auto degree at write time; or accept the growth as the cost of a traversal tool used a few times a session. The decision needs a measurement of what `knowledge_traverse` actually returns in practice, which does not exist yet. Related: the WardSONDB traverse endpoint stays deferred precisely because the step it would accelerate was the one deleted (the measurements are in [KNOWLEDGE-GRAPH.md](MULTI-GRAPH/KNOWLEDGE-GRAPH.md), under retrieval).

**2026-10-03.** The proportion holds: 430,271 of 433,325 edges are automatic (99.3%, the backup of 2026-10-02). `remember` now promotes a memory when it is created, so every memory derives twice — once for its entry and once for its node, which carries the same text, tags and session. That was already the practice (1,264 of 1,294 entries were promoted); it is the rule now. It adds an option to the list above: derive for the node alone. A memory would then add about half of what it adds today. The price is in retrieval, whose session step walks `same_session` edges from the session's entries (`retrieval.rs`, step 2) and would have to be examined again.

## Credentials on disk and the unjailed file tools

Opened 2026-10-09, with the Guardian `http_request` capability. The OS holds credentials for the intelligence's own use: the provider key, `github_token`, `git_tokens`, the Brave key, and now `guardian_secrets` (`config.system`, injected into a request by the host so that a token never enters a tool's input, the turn trace, the session history or a guest). That keeps a secret out of the model's context. It does not keep it off the disk the model can read: `file_read` takes an absolute path by design and the services run as one user, so a STATE file and the database's own files under `/embra/data/wardsondb` are readable with a tool, and every credential the OS holds shares that property. A read jail for the file tools would close it and would also take from `file_read` the uses it has today outside the workspace (logs, service state); a split of the file tools by path class is another option; neither is designed. The decision is separate from `http_request` and was taken out of its pass on purpose.

**Resolved 2026-10-18.** The model's readers (`file_read`, `file_copy`'s source, `image_view`, `image_generate`'s references, `guardian_call`'s `data_file`) judge the real path and refuse `/proc`, the STATE partition except the operator's drop-in directories and four plain files, the database files and the workspace SSH key; `get` returns the configuration with its credential fields redacted; the input of an outbound tool and a Guardian request that carry a stored secret are refused by value, naming the kind. `file_read` keeps its uses outside the workspace: `/etc`, the service logs, the rest of the system. The boundary that stays: the provider sees the conversation, and a secret pasted into it and never stored is not in the set. [SYSTEM-DESIGN.md](SYSTEM-DESIGN.md), "Trust boundaries".

## The web console's certificate on a leased address

Opened 2026-11-05, with DHCP. embraOS now takes a lease on `eth0` and, when the lease is an address of the machine's own (a bridged network, a real host), prints a second console URL on it beside the `localhost` one. The certificate `embra-trustd` mints for `embra-web` names `localhost`, `embraos`, `buildroot`, `127.0.0.1` and `10.0.2.15` (`crates/embra-trustd/src/pki.rs`, `SERVICE_IPS`; a Root CA generated on a fresh install carries name constraints to that set), so a browser on the leased address accepts the embraOS-CA chain and then warns about the name, once per address.

Options, none taken: add the leased address as a subject alternative name at every start (the certificate is minted per start already, but the CA's name constraints would have to admit it, and a Root CA generated before keeps its constraints until `/embra/state/pki/` is removed); a stable name instead of an address — mDNS (`embraos.local`), which the roadmap defers — with the name in the constraint set; or leave the warning, as the operator already accepts the private CA. The decision belongs with the templates wave, where the first bridged instances appear.

## The clock: one unauthenticated answer per boot

embrad sets the clock at boot: a hardware clock that reads earlier than the image's build time is set to it, and a time server is asked once, by SNTP, before any service starts (`crates/embrad/src/clock.rs`; [QUICK-START.md](BUILD/QUICK-START.md), The clock). Three things are open.

- **The answer is not authenticated.** embrad ties an answer to its request with a random value the server returns, which stops a forger off the path, and refuses a time earlier than the image's build time. A host on the path can still forge a later time. NTS (RFC 8915) would authenticate the answer; it is not implemented.
- **The source.** The default is one name, `time.cloudflare.com` (`DEFAULT_TIME_SERVER`). The NTP Pool's zone names are not used: its rules for vendors forbid them as the default of a distributed system without a vendor zone, and embraOS has none; with one, the default becomes that zone. The DHCP lease's NTP option is not read.
- **The clock is not kept.** One exchange per boot. A machine that stays up drifts with its hardware clock, and a boot without an answer is not asked again until the next. An installed machine has no stored setting for the server: `embra.ntp=` is typed in GRUB's editor at each boot, as every kernel-line knob is. A board whose clock battery is dead (the bare-metal machine of 2026-11-12) loses its time whenever power is removed: after that it has the right time only in a boot where the time server answers. Without one it resumes from the last time it saved (the clock, written to STATE once a minute), behind by as long as the power was off: the clock never restarts before where it stopped, and it is not right until a time server answers.

## An interactive console on the display

Opened 2026-11-07, with the boot messages on both consoles (`cb5865c`, after the ESXi run that showed a blank screen where embra-init had halted). The display is a boot console now: GRUB's menu, the boot log, the banner with the console URL and the reason a boot stopped all appear on it, so a hypervisor or a bare-metal machine without a serial port shows what happened. Input does not come back the same way. `/dev/console` is the serial line, the last `console=` on the kernel line, and that is where the serial TUI (`embra.tui=1`) draws and reads, and where the updater's prompts in the Update, Backup and Restore menu entries wait for an answer: on a display-only machine the Restore entry shows its list and cannot be answered, and the serial TUI is unreachable. The web console is the primary interface and needs neither console, so this concerns the fallback and the maintenance boots.

Options, none taken: run `embra-console` on `/dev/tty1` as well as, or instead of, the serial line when the kernel has a framebuffer (the kernel carries the keyboard drivers — atkbd, USB HID, Hyper-V's keyboard; the TUI would need the Linux console's terminal type and no serial graphics protocol); make the maintenance boots' prompts answer on whichever console the operator types on (both opened, the first key wins); or move the maintenance jobs' confirmations into GRUB's menu, where keyboard input on the display works already, and leave the OS side non-interactive. Phase 2 drives both consoles for output (William, 2026-11-07); the interactive half is a follow-up of its own.

**2026-11-08.** The dead console reaches further than the boot log. A machine without a serial port has a `/dev/console` that opens and refuses every write — the kernel line names a UART that is not there — and `d91ef4c` keeps embrad from stopping on it: the boot log, the banner and the console URL are on the display, and the web console comes up. The updater in a maintenance boot still prints its progress and its prompts with `println!`, which panics on such a console, so the Update, Backup and Restore entries would fail back to the menu there, with only embrad's lines around the job on the display. The web console is unaffected. William's direction, 2026-11-08: a wave of its own after the ESXi run, the display as a complete console with keyboard and mouse, so a machine with a display alone is fully operable.

**2026-11-08, later.** The maintenance half is closed: `embra-update` speaks and listens through one operator channel (`console::Operator`), which under `--console` is `BootConsole::prompt_line` over `/dev/console` and `/dev/tty0` at once — the prompt on both, the first line typed on either answering, a console that refuses to be read or written skipped — and embrad passes `--console` to every job it runs before the services (the Update, Backup and Restore entries, the trial and scheduled snapshots, the scheduled restore). No print macro of the updater touches a console that may refuse a write. What remains of this entry is the running system's display console, the kiosk of the wave in progress.

**2026-11-08, the display console.** The operator half lands: after the banner, embrad starts eudev and cog (WPE WebKit's DRM platform) on the display, which loads the web console with the boot's token, keyboard and mouse through libinput, the session shared with every browser under the existing arbiter. Software rendering end to end (Mesa's kms_swrast and wayland-swrast, cog's dumb-buffer scanout), because the displays this image meets (the firmware's framebuffer, QEMU's standard VGA, Hyper-V's video) have neither a DRM render node nor a cursor plane; three patches under `buildroot/patches/` (one on Mesa, two on cog) make that path work and are to be carried upstream. Validated under QEMU on the standard VGA and virtio-gpu displays. What is left of the entry: the runs on ESXi, Hyper-V, Parallels and bare metal; the loopback page is loaded with TLS errors ignored, and trusting embra-trustd's CA through GIO instead is the follow-up; a Compose table for xkbcommon (the kernel of a dead-key layout) is not shipped.

**2026-11-09, clicks.** William's run on ESXi 8.0 U2: the display console comes up and the keyboard works; the pointer moves, and a click does nothing. The cause is in cog's DRM platform and holds on every machine. `input_handle_pointer_button_event` (`platform/drm/cog-platform-drm.c`) hands WPE the button as libinput names it, the evdev code (`BTN_LEFT` is 0x110), with no button modifiers; WebKit knows the buttons as 1, 2 and 3 (`WebEventFactory.cpp`, `createWebMouseEvent`), so a press and a release arrive as mouse events without a button, and WebCore sends `click` for the left button alone (`EventHandler.cpp`). The pointer, hover, the wheel and a drag that selects text in the terminal need no `click` and work; a tab, a command group and every button need it and stay as they were. It reproduces under QEMU with a USB tablet and with QEMU's emulation of VMware's mouse, and the statement of 2026-11-08 that the mouse was validated under QEMU was wrong for clicks: its proof was a screen dump of a hovered control. cog's Wayland platform numbers the buttons from one; the same numbering in the DRM platform, with the held buttons as modifiers, is the fix, `buildroot/patches/cog/0003-drm-pointer-buttons-in-WPE-s-numbering-the-held-ones-as-modifiers.patch`, proven with the patched plugin in a scratch image (the tab, the group, the Commands button, a drag and a double click act, on both pointer devices). An image built before the patch keeps the dead click. What is left of this paragraph: a build with the patch, and the click on ESXi.

**2026-11-09, Hyper-V.** William's test of the installer ISO on Hyper-V: the machine boots, and the display console does not appear. cog's DRM platform took its card from libdrm's `drmGetDevices2()` alone. libdrm tells a card by the bus of the device behind it (PCI, USB, platform, virtio, host1x, faux) and leaves out every other one; Hyper-V's synthetic video (`hyperv_drm`) is a VMBus device, so the list is empty there and cog finds no display on a machine whose `/dev/dri/card0` works (the boot console on it is the kernel's own). `buildroot/patches/cog/0004-drm-a-card-libdrm-does-not-enumerate-is-opened-by-its-node.patch` tries the card nodes themselves when the list yields none. QEMU has no VMBus video, so the proof here is the patched plugin with libdrm's list emptied: the console comes up through the node on the standard VGA and on a firmware framebuffer, and the unpatched path is unchanged on both. What is left of this paragraph: the run on Hyper-V.

**2026-11-09, the runs.** William's build of `de419f5`, which carries both patches and asks for 1920x1080 ([QUICK-START.md](BUILD/QUICK-START.md)), under QEMU, on ESXi 8.0 U2 and on Hyper-V generation 2: the display console comes up on all three, on Hyper-V for the first time, at 1920x1080, and a click acts on all three. The Hyper-V machine was installed from the ISO, and its keyboard types in the display console. That closes the two paragraphs above. What is left of the entry: the runs on Parallels and bare metal; the loopback page loaded with TLS errors ignored; the Compose table for xkbcommon.

**2026-11-10, aarch64.** William's run under QEMU on Apple Silicon, a virtio-gpu display with a USB keyboard and tablet on xHCI ([AARCH64-BUILD.md](BUILD/AARCH64-BUILD.md)): the display console comes up after the boot log at 1920x1080 and takes the keyboard, the pointer and a click. On the firmware's framebuffer (`-device ramfb` in the same command) the display console comes up after the boot log as well, at 800x600, and takes the keyboard, the pointer and a click (2026-11-10): edk2's `ramfb` driver offers 640x480, 800x600 and 1024x768 and starts in the second, so the request for 1920x1080 does not take there.

**2026-11-10, the Intel Mac.** William's runs in QEMU's window on the Intel Mac, a virtio-gpu display with a USB tablet on xHCI ([INTEL-MAC-BUILD.md](BUILD/INTEL-MAC-BUILD.md)): the display console comes up after the boot log and takes the keyboard, the pointer and a click, at 1280x800 on an image of `22022ff` and at 1920x1080 on one of `1ba8df5`, by default and with `embra.kioskmode=1920x1080`. The mode was embrad's reading: it took the display's modes from sysfs, where a connector's list is the one its last reader left, and the kernel's own console reads it again after every display event with its framebuffer's size as the limit. QEMU's window reports its size to virtio-gpu a second after each resize, which is such an event; on x86 it arrives after the kernel's console has set 1280x800, and 1920x1080 leaves the list. From `1ba8df5` embrad writes `detect` to each connector's `status` when the mode is missing and reads once more (never on a kernel line whose `video=` option forces a connector). The same sequence under QEMU on Linux, with a VNC client reporting its size as the window does and the VM slowed down, gives 1280x800 before the change and 1920x1080 after it.

**2026-11-11, Parallels.** On Parallels Desktop 26.5 (Intel Mac) the display console follows the display adapter the machine's type brings. The machine imported from `embraos.vmx` ([QUICK-START.md](BUILD/QUICK-START.md)) is typed Linux and has Parallels' virtio adapter: the display shows the boot log at 1024x768 and then the display console at 1920x1080 (embrad: `Display console: asking the display for 1920x1080`). A machine typed "Other" has Parallels' own adapter and stays at the firmware's 1024x768 (embrad: `Display console: the display's own video mode`). Letters sent as key events from the host arrive in the console's input. On bare metal the entry is run on one machine, a YouYeeToo X1: the console on its HDMI display, the keyboard, the pointer and a click ([OPERATION.md](OPERATIONS/OPERATION.md)). What is left of the entry: the pointer and a click on Parallels; the loopback page loaded with TLS errors ignored; the Compose table for xkbcommon.
